Chapter nine

9Daily readings and dosha alerts

Twice a day a scheduled job writes each person a reading for the half of the day they are in, and sends a push only when something in their sky actually changed. The clock is the user's, not the server's; the astrology is decided in code, not by the model; and a condition that merely continues is never announced twice.

This chapter describes the code on main on 30 September 2026, version 0.3.0. It is the one feature in Astrya that runs with nobody looking. A chat route that misbehaves is seen and retried by the person in front of it; a cron job that misbehaves wakes people at night, bills a model call nobody asked for, or says "Mangal Dosha has begun" to someone whose chart has not changed since the day they were born. Most of the design below exists to make each of those impossible rather than unlikely.

9.1Intent

Two things are pushed to a person, both written from their own chart against today's sky. A reading, morning and night, kept by date so the app shows an archive rather than a notification that vanishes. And a dosha alert, sent only when an affliction starts or ends: a Sade Sati stepping from rising to peak, Saturn leaving the eighth from the Moon, a node arriving over the ascendant. A standing condition is recorded and shown, but it does not nag.

Three decisions shape everything else. The slot a reading belongs to is decided by the user's local hour, so one fixed UTC schedule serves every timezone. The dosha engine (lib/astrology/doshas.ts) decides deterministically which conditions hold, and Claude only writes the words. And natal conditions, fixed at birth, never alert after a user's first read, because a change in one is an artifact of the computation moving under them and never an event.

9.3Model

A condition and its signature

// lib/astrology/doshas.ts
export type Severity = "info" | "caution" | "warning";

export type Condition = {
  kind: string;
  signature: string;
  label: string;
  severity: Severity;
  scope: "natal" | "transit";
  /** A plain factual sentence, the grounding the model is allowed to interpret. */
  detail: string;
};

The signature is the whole mechanism. It folds in the phase and the sign involved, so that Saturn moving on, or Sade Sati stepping from rising to peak, reads as a new condition rather than the same one continuing. Natal detectors produce signatures such as mangal_dosha:7 or kaal_sarp:<sign>; transit detectors produce sade_sati:<phase>:<sign>, kantaka_shani, node_over_moon_<node>, ashtama_surya, guru_6_8_12, retrograde_<planet> and the rest, each suffixed with the sign that makes it specific. The sweep never compares labels or kinds. It compares signatures against the set of open rows, and the difference is the news.

The copy

// lib/alerts/compose.ts
export type AlertCopy = {
  title: string;
  body: string;
  detail: string;
};

// lib/alerts/slots.ts
export type Slot = "morning" | "night";
export const NIGHT_STARTS_AT_HOUR = 14;

One copy type serves both a reading and an alert: a title, one plain sentence for the lock screen, and a markdown detail ending in a section titled "In simple words". The prompt asks for under 38 characters of title and under 140 of body; the parser cuts at 60 and 200, so a reply a few characters over is trimmed rather than discarded.

Every table has Row Level Security on, and every policy is owner-only. The jobs write with the service-role client, which bypasses RLS; the policies let the app read its own inbox and mark things read through PostgREST with no route handler in between. transit_conditions is the state the feature hangs on: a row is open while ended_on is null, and the partial unique index allows one open row per signature per user, so two runs racing cannot open a condition twice. daily_readings.for_date is the user's own local date, with the migration's reason: "my reading for the 26th" has to mean their 26th.

Why ended_on and not a delete A closed row is history. The unique index is partial precisely so a condition can end, stay on record with its dates, and open again under the same signature when Saturn returns. The table is a ledger of every affliction the engine has seen, not a set of current ones.

9.4The server side

Two routes, one current

// vercel.json
"crons": [
  { "path": "/api/cron/daily", "schedule": "30 2 * * *" },
  { "path": "/api/cron/daily", "schedule": "30 15 * * *" }

Both schedules hit /api/cron/daily, at 02:30 and 15:30 UTC, which is 08:00 and 21:00 in India. The handler runs runDuePredictions(), then runDailyAlerts(), and answers with both summaries. /api/cron/alerts is the older route: it runs only the dosha sweep, is not named in vercel.json, and survives for running that half by hand. Its docstring still says the cron fires it, and the comment in 0004_alerts_push.sql names it too; both are out of date. Read vercel.json as the truth about what is scheduled.

Vercel sends Authorization: Bearer $CRON_SECRET on scheduled invocations, and the same header runs the job by hand with curl. A missing secret refuses everything; "no secret means open" would expose a job that spends model tokens for every user to anyone who finds the path. The runtime is Node because the Swiss Ephemeris runs as WebAssembly, and the five-minute maxDuration is the budget for up to 500 users, each of whom may cost a chart computation and a model call.

Slots

// lib/alerts/slots.ts
export function slotForHour(localHour: number): Slot {
  return localHour < NIGHT_STARTS_AT_HOUR ? "morning" : "night";
}

export function isSlotDue(localHour: number, alreadyWritten: Slot[]): Slot | null {
  const slot = slotForHour(localHour);
  return alreadyWritten.includes(slot) ? null : slot;
}

Anything before 14:00 local is that day's morning reading; anything after is that night's. isSlotDue asks one question: does this user still need the reading for the slot they are in right now? It does not backfill. A user in the evening with no morning reading gets tonight's, not a stale "good morning" hours late, which the test does not backfill a slot the user has moved past pins.

The reading

runDuePredictions selects every birth_profiles row with a computed chart, up to 500, and calls writeDueReading for each inside its own try; one user failing is counted and logged, and the loop continues. Per user:

  1. The Vedic chart is required; a profile without one counts as skipped.
  2. The zone is profile.timezone, or UTC when null. nowLocal and forDate come from Luxon in that zone.
  3. The slots already written for that user and date are read from daily_readings, and isSlotDue(nowLocal.hour, slots) decides. Null means nothing to do.
  4. transitChart computes today's sky at the user's birthplace, and detectConditions(chart, transits) finds the same afflictions the alert job tracks, so the reading and the alerts never contradict each other.
  5. composePrediction writes the copy and the row is inserted with tradition: "vedic". A unique violation (Postgres code 23505) is returned as null, "already done", not thrown: the index is the safety net for two runs racing.
  6. The reading is pushed to every device with kind: "daily" and a thread id of sanchara-daily-morning or sanchara-daily-night.

The prompt has three parts. The stable block is the same chart system prompt the chat uses, with the derived facts and numerology, marked for a one-hour prompt cache. The today block is the gochara description, called with includeAfflictions: false because the job lists the flagged conditions itself; asking for them twice was the double-listing fixed in 0.3.0. The task is one of two briefs, morning ("look forward, not back") or night ("reflect on the day, then say what tomorrow morning opens with"), followed by at most four flagged conditions, to be worked in only where they bear on the day and without alarm. Natal conditions are left out of that list for the same reason they never alert: they are not about today. The model is READING_MODEL (claude-sonnet-5) at LOW_EFFORT with 1,600 output tokens. If the call fails or the reply cannot be parsed, fallbackPrediction stores a plain reading that greets the user by first name and points at the app, so the slot is never empty.

The dosha sweep

runDailyAlerts has the same outer shape: the same profile query, a per-user try, and a summary of processed, alerted, pushesSent, failures and pushConfigured. Per user, runAlertsForUser works in a fixed order, and the order is the correctness.

  1. Compute today's sky with computeChart at the user's latitude and longitude, the same way the chat route does. Then detectConditions(natal, transit), indexed by signature.
  2. Count the user's natal rows in transit_conditions. This is the only fact that decides whether a natal condition may alert, and it fails closed (below).
  3. Load the open rows (ended_on is null). started is every current condition whose signature is not open; ended is every open row whose signature is not current.
  4. Insert every started row with started_on as the user's local date, and close every ended row the same way. The code warns at each step that these are the raw, unfiltered lists: a natal filter inlined here would stop natal rows being written, and the same condition would re-detect as "starting" forever.
  5. Only now partition. partitionForAlerts keeps everything when the user had no natal rows (a first read, where the whole natal set is genuinely news) and otherwise routes natal conditions to silent. Then keep only caution and warning (NOTIFIABLE), and at most six (MAX_CONDITIONS_PER_ALERT), because past that an alert becomes a list.
  6. If nothing is left, return without an alert. Otherwise the severity is the highest among the started conditions, or the ended ones if nothing started; composeAlert writes the copy; one row goes into alerts with the kinds involved; and the push goes out.
// lib/alerts/run.ts
export function deriveHadNatalRows(result: { count: number | null; error: { message: string } | null }): boolean {
  if (result.error) return true;
  return (result.count ?? 0) > 0;
}

Supabase returns count: null alongside an error, so the naive (count ?? 0) > 0 would read a failed count as "no natal rows", treat an existing user as a first-time reader, and let their natal conditions through unfiltered. That is the bug the 0.3.0 move to whole-sign houses would have caused: the detectors shifted, some natal signatures changed, and "Mangal Dosha has begun" would have gone to people whose chart has not changed since birth. On error the function assumes the opposite of the naive read. It does not throw, because suppressing a natal alert costs nothing real (the condition still shows in the app and the next run reconciles), while aborting the user would drop their legitimate transit alerts for the day.

Composing the alert

composeAlert uses DEEP_READING_MODEL (claude-opus-4-8), again at low effort and 1,600 tokens; an alert is a title, a sentence and about 180 words, so the thinking budget is kept short on purpose. The system prompt gives the model a short chart summary (ascendant, Sun and Moon signs, the running dasha, every planet with sign and house), the conditions under "Newly active now" and "No longer active" with their factual detail lines, and four rules: never invent a placement, dosha, date or number not listed; no guaranteed outcomes and no medical, legal or financial guarantees; calm and practical, a heads-up and not doom; a remedy that is traditional and harmless. 

// lib/alerts/compose.ts
export function parseAlertCopy(text: string): AlertCopy | null {
  const title = text.match(/^\s*TITLE:\s*(.+)$/m)?.[1]?.trim();
  const body = text.match(/^\s*BODY:\s*(.+)$/m)?.[1]?.trim();
  const detailIndex = text.search(/^\s*DETAIL:\s*$/m);
  const detail = detailIndex === -1 ? undefined : text.slice(text.indexOf("\n", detailIndex) + 1).trim();
  if (title && body && detail) {
    return { title: title.slice(0, 60), body: body.slice(0, 200), detail };
  }
  return parseAlertJson(text);
}

The reply is line-delimited rather than JSON because detail is markdown. Asked for JSON, the model sometimes writes real newlines inside the string, which is not valid JSON, and the reply is lost; the comment records two of a batch of seven live readings coming back that way. Delimited text has no escaping to get wrong. JSON is still accepted as a second parse for the old shape. When neither parses, or the call throws, fallbackCopy still names the condition: "Sade Sati (peak phase) is active", or "has eased" when only endings remain.

The APNs client

lib/push/apns.ts talks to Apple directly over HTTP/2 with token-based authentication; there is no push library. isPushConfigured() is true only when all of APNS_KEY_ID, APNS_TEAM_ID, APNS_BUNDLE_ID and APNS_PRIVATE_KEY are set. Without them the jobs still write readings and alerts; they just send nothing, and the summary says pushConfigured: false. APNS_PRIVATE_KEY is the full text of the .p8 file; the env accessor turns literal \n sequences back into newlines so the key survives a single-line variable.

    key,
    dsaEncoding: "ieee-p1363",
  });
  ...
}

The provider token is a JWT signed with the .p8 key: kid in the header, iss (the team id) and iat in the payload. Apple accepts one for an hour and rate-limits regeneration, so the module keeps it for 45 minutes across sends and warm invocations. The one subtlety is dsaEncoding: "ieee-p1363": ES256 wants the raw r and s pair, and Node signs DER by default. ApnsClient keeps one HTTP/2 session per environment, so a run that notifies many users pays for one TLS handshake; the session's error handler exists because an unhandled socket error would take the process down.

send posts to /3/device/<token> with apns-topic set to the bundle id, apns-push-type: alert and apns-priority: 10. The payload is an aps block (title and body, the default sound, a thread-id defaulting to sanchara-alerts, interruption-level: active) plus two custom keys the app reads on a tap: alert_id and kind. A ten-second timeout cancels the stream. The result reports unregistered: true on a 410 or the reasons Unregistered and BadDeviceToken; both jobs delete those tokens after the loop, because Apple only tells you a token is dead when you use it.

The job never chooses the environment. Each device_tokens row carries the environment the app reported at registration, and send opens the session for that row. A sandbox token and a production token for the same user coexist, each going to the only host that will accept it.

Registering a device

POST /api/devices takes { token, environment }. The token must match /^[0-9a-fA-F]{64,200}$/: APNs token length has grown over the years, so the route checks the alphabet and a sane range rather than pinning 64 characters. The environment is sandbox only when the body says exactly that; anything else becomes production. The row is upserted on token with platform: "ios" and the user id from the verified session, never from the body. It is written with the admin client on purpose: a device handed from one account to another has to change owner, and the owner-only RLS policy would correctly refuse that update. DELETE matches both the token and the session user, so one account cannot unregister another's device.

9.5The clients

The web app

There is no web surface for readings or alerts in 0.3.0: nothing under app/ or components/ reads daily_readings or alerts. The web app's part is the route handlers it hosts. The inbox is an iOS feature, and the phone reads the tables straight through PostgREST under RLS.

PushStore and the entitlement

Push.swift holds three things. PushStore is a @MainActor observable singleton with the device token, an authorization flag, and pending, the notification just tapped. SancharaAppDelegate exists because SwiftUI has no hook for APNs callbacks: it receives the token, turns a tap into a TappedNotification (an id and a kind, daily or alert, from the payload's custom keys), and shows a banner even when the app is open, since these are infrequent and time-relevant. And ApsEnvironment answers the one fact the server needs right about a device. 

// mobile/Sanchara/Sources/Services/Push.swift
static func parse(profileText: String) -> String {
    guard let open = profileText.range(of: "<plist"),
          let close = profileText.range(of: "</plist>", range: open.upperBound..<profileText.endIndex)
    else { return sandbox }
    let plist = String(profileText[open.lowerBound..<close.upperBound])
    guard let data = plist.data(using: .utf8),
          let root = try? PropertyListSerialization.propertyList(from: data, format: nil) as? [String: Any],
          let entitlements = root["Entitlements"] as? [String: Any],
          let value = entitlements["aps-environment"] as? String
    else { return sandbox }
    return value == production ? production : sandbox
}

The environment is read from the signing entitlement, not the build configuration. The 0.2.0 changelog records why: a Release build run from Xcode still carries aps-environment: development and mints a sandbox token, and reporting "production" for it made every push to that device fail silently. So the app reads embedded.mobileprovision from its own bundle, which is what APNs reads too. That file is a CMS-signed blob with a plist inside. Rather than parse CMS, the code decodes the bytes as Latin-1 (every byte maps to a character, so the binary envelope cannot make the decode fail), finds the span between <plist and </plist>, and reads the entitlements dictionary. production is returned only when the profile says exactly that; a simulator build has no profile and cannot receive pushes, so sandbox is the harmless answer for every failure. mobile/project.yml sets the entitlement to development; the README and the TestFlight workflow switch it to production before archiving, and the app reports whichever it finds.

Registration is asked for in ChatView, not at launch, with the reason in the code: by then the user has a chart, so "we'll tell you when a dosha starts" means something. requestAuthorization asks once and calls registerForRemoteNotifications; the delegate hands the token to received, which formats it as hex and calls register, which posts it with ApsEnvironment.current whenever there is a session. A failed registration is swallowed; the next launch retries. AuthStore.signOut calls unregister before the session is gone, so the next person to sign in on that phone does not receive the previous account's readings.

The two stores

DailyStore loads the newest 60 rows of daily_readings, ordered by for_date then created_at, both descending, and groups them into DailyReadingDay values: newest day first, morning above night within a day, each labelled "Today", "Yesterday" or a long date. After every successful load it saves the newest reading into the App Group cache as a CachedReading and calls WidgetRefresh.reload(), because the widget and the Siri snippet read this and neither can run the query themselves. AlertsStore loads the newest 50 alerts. Both stores expose unreadCount, open(id:) and markRead. open looks in the loaded list first and reloads only on a miss, because the push usually arrives before the app has reloaded. markRead writes read_at, the only write RLS allows the app, and a failure leaves the badge until the next load.

The inbox

InboxView is one sheet with two tabs, Daily and Alerts, each with an unread badge, so the bell means "things for you". The Daily tab is sectioned by day with a sun or moon glyph per row; the Alerts tab is a flat list with a severity dot (severityColor: the accent for warning, amber for caution, muted otherwise). A tap opens DailyReadingView or AlertDetailView, which render the markdown detail and end with one button, "Ask Astrya about this", that closes the inbox, starts a new reading and sends a question built from the title and body. The sheet's .task marks the item read as it opens.

9.6How it works

A scheduled run

  1. Vercel Cron sends GET /api/cron/daily with the bearer secret. The handler checks it and calls the two jobs in order: readings first, then the sweep.
  2. Each job opens one admin client and one ApnsClient, loads up to 500 profiles with a chart, and loops. The readings job decides a slot per user and writes and pushes only when it is due; the sweep diffs, records, partitions, and alerts only on a change.
  3. Both clients are closed in finally, and the handler answers with the two summaries. A top-level error becomes a 500 with a logged cause; a per-user failure is only a count.

What the two UTC runs mean in other places

The schedule was chosen for India, where the two runs land at 08:00 and 21:00. Everyone else gets whatever those two instants are on their own clock, run through slotForHour (offsets as of late September):

A user far enough east has both runs land in the morning half of two consecutive local days: the second writes tomorrow's morning reading just after midnight, and the next morning's run finds it written and skips. They never get a night reading. The London user's morning reading is written at 03:30 and waits on the lock screen until they wake. docs/PUSH_ALERTS.md names the remedy: on a Vercel plan that allows sub-daily crons, 0 * * * * makes every timezone exact at no extra model cost, because each hourly run writes only for users whose current slot is missing. The code is already written for that schedule; only vercel.json would change.

A condition starts

Saturn enters the sign twelfth from a user's natal Moon. detectConditions now returns a sade_sati signature carrying the phase and the sign, a warning with scope transit. No open row has that signature, so it is in started and is inserted with today's local date; it is transit, so the partition keeps it; it is notifiable; Opus writes a title, a sentence and a page; the alerts row is inserted with kinds: ["sade_sati"]; and every device gets the push in the sanchara-alerts thread. Tomorrow the same signature is open and current, so it is in neither list and nothing happens. When Saturn moves on, the row is closed, the next phase's signature opens, and the alert reads as a change of phase rather than a repeat.

A tap

The delegate's didReceive reads alert_id and kind from the payload and sets PushStore.shared.pending. ChatView observes it, clears it, switches inboxTab to match, calls the store's open(id:), and presents the inbox. Because open sets selected, the detail sheet is already up when the inbox appears.

9.7Performance and cost

  • Idempotent by construction. The unique index on daily_readings and the partial unique index on transit_conditions mean an extra run, a retry, or two runs racing write nothing twice. The route's own comment says it: extra runs mostly find nothing to do.
  • No model call for a skipped slot. The slot check happens before the transit chart and before the model, so a run that lands in an already-written half of a user's day costs one small query.
  • The chart block is cached. The stable system prompt carries cache_control with a one-hour TTL and is byte-identical for a user on every run, and it matches the chat's chart block, so a reading and a conversation in the same hour share it.
  • Sonnet for the reading, Opus for the alert. The reading runs twice a day for everyone; the alert runs only on a change, so the more expensive model is reserved for the rarer message. Both run at low effort with a 1,600-token cap.
  • One APNs session per environment per run, and one provider token per 45 minutes, shared across every device in the loop.
  • Dead tokens are pruned as they are found, so the loop does not grow with every uninstalled app.
  • Bounded work. Both jobs cap the profile query at 500 and the route at five minutes. There is no pagination; past 500 users with charts, the limit is the next thing to change.
  • The phone caches the newest reading in the App Group so the widget and Siri answer with no network, and the cache's isFresh keeps a widget from insisting on yesterday's morning reading.

Check yourself

Why is the slot decided by the user's local hour rather than by which cron fired?

One fixed UTC schedule then serves every timezone, and the same code works unchanged under an hourly schedule. The cron decides when to look; the user's clock decides what is due.

Why are natal rows still inserted into transit_conditions if they can never alert?

The diff is against open rows. A natal condition never recorded is absent from the open set on every run, so it would be in started forever. Recording it once is what makes it silent.

What does deriveHadNatalRows return when the count query fails, and why?

True. That routes natal conditions to silent, which costs nothing; the other direction is a push saying a birth condition began today.

Why does the reply use TITLE:, BODY: and DETAIL: lines instead of JSON?

The detail is markdown with real newlines, and the model sometimes writes them raw inside a JSON string, which does not parse. Delimited lines have no escaping to get wrong.

Where does the job learn which APNs host to use for a device?

From the environment column of that device's row, set at registration from the aps-environment entitlement in the app's embedded provisioning profile. Neither the job nor the build configuration guesses.

Why does the device route write with the admin client when RLS already lets a user manage their own tokens?

A phone that changes hands has to move its token to the new account, and an owner-only policy correctly refuses that update. The user id still comes from the session, never the body.

A user in Tokyo never gets a night reading. Why, and what fixes it?

Both UTC runs land before 14:00 local on two consecutive days, so both are morning slots and the second is skipped. An hourly cron fixes it with no code change, because isSlotDue already writes only what is missing.
