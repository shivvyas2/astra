Chapter five

5Intake and the birth profile

Everything Astrya does starts from one row: a name, a date, a time, a place and the two charts computed from them. Intake is the form that fills it, on the web and on the phone, and the birth profile is the row that every other feature reads. The one idea that shaped it is that the chart is computed once, at save time, and stored beside the details that produced it.

This chapter describes the code on main on 30 September 2026, version 0.3.0. A person who signs in has, at first, nothing but an auth user. The web app and the iOS app both notice that and send them to intake. When they submit, the server geocodes nothing and guesses nothing: the form has already resolved a place to coordinates and an IANA timezone, and the route hands those to the Swiss Ephemeris, computes a Vedic and a Western chart, and writes all of it into birth_profiles in one upsert. From then on the chat, the kundli, the timeline, the daily readings and the widget all read that stored chart. Nothing recomputes it unless the details change, or the chart's schema falls behind.

5.1Intent

A birth chart is only as good as the moment and place it is cast for. The intake form therefore refuses to submit until it holds a real latitude, longitude and timezone, and it gets them from a geocoder rather than from the person. Typing "Mumbai" produces a list of candidates with their timezones already attached, and picking one fills four hidden fields. Someone whose village the geocoder does not know can type coordinates by hand, and the timezone is still derived for them, offline, from the coordinates.

The second intent is that the computed chart belongs with the details. birth_profiles carries a chart jsonb column holding both traditions. Readers never call the ephemeris; they read the column. This is what lets the iOS app cache the chart in the App Group and answer Siri, App Intents and the widget without a network, and it is what makes a chart upgrade a read-time concern rather than a migration.

The third intent is that the two clients do the same work through the same function. The web form submits to a server action, the iOS form posts multipart form data to a route handler, and both end in saveBirthProfile. The route exists only because a native client cannot invoke a Next.js server action; its own comment says so.

5.3Model

The table

-- supabase/migrations/0001_init.sql
create table public.birth_profiles (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  first_name text not null,
  last_name text not null,
  birth_date date not null,
  birth_time time not null,
  place_name text not null,
  lat double precision not null,
  lng double precision not null,
  timezone text not null,
  chart jsonb,
  updated_at timestamptz not null default now(),
  unique (user_id)
);
alter table public.birth_profiles enable row level security;

create policy "birth self" on public.birth_profiles
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());

One row per user, enforced by unique (user_id), which is also the conflict target of the upsert. chart is nullable so that a row can in principle exist without one, though nothing in the current code writes a row that way: saveBirthProfile always writes the details and the chart together. The policy is owner-only for every verb. The iOS app reads this table directly through supabase-swift with the user's own session, and that policy is the whole reason it can.

Migration 0002 adds avatar_url text, nullable. Migration 0003 is not a column on this table at all: it drops and recreates the check constraint on conversations.tradition so that a chat can run in numerology mode alongside vedic and western. It belongs to this chapter only in that numerology is computed from the birth date and name stored here; the chat mode itself is in chapter 6. The full schema is catalogued in chapter 13.

The row, in TypeScript and in Swift

// lib/data/birthProfile.ts
export type BirthProfileRow = {
  id: string;

  first_name: string;

};

Postgres hands birth_time back as HH:mm:ss, while every form and the ephemeris input use HH:mm. That is why ensureCurrentChart and the kundli route both slice(0, 5) before use, and why the Swift struct carries a birthTimeShort computed property doing the same prefix(5). The Swift side, BirthProfileDetails, decodes the same columns under snake-case coding keys and adds fullName. It is deliberately dependency-free, because project.yml compiles it into the widget extension as well as the app.

What goes into the chart

// lib/astrology/types.ts
export type BirthInput = {
  birthDate: string; // YYYY-MM-DD
  birthTime: string; // HH:mm
  lat: number;
  lng: number;
  timezone: string; // IANA
};

Five values, all of which the form must resolve before its submit button enables. The result of computeChart(birth, tradition) is a Chart carrying the ascendant, twelve house cusps, the planets with sign, degree, house, retrograde flag and (Vedic only) nakshatra, the Moon and Sun signs, the ayanamsa, the running dasha, a schemaVersion, and the derived facts. How those are computed is chapter 2; this chapter cares only that the column holds { vedic, western } and that schemaVersion is what decides whether the stored copy is still current.

5.4The server side

Geocoding

// lib/geo.ts
export async function geocodePlace(query: string): Promise<GeoResult[]> {
  const q = query.trim();
  if (q.length < 2) return [];
  const url = `https://geocoding-api.open-meteo.com/v1/search?name=${encodeURIComponent(q)}&count=5&language=en&format=json`;
  const res = await fetch(url, { headers: { accept: "application/json" } });
  if (!res.ok) return [];
  ...
  return (data.results ?? []).map((r) => ({
    name: [r.name, r.admin1, r.country].filter(Boolean).join(", "),
    lat: r.latitude,
    lng: r.longitude,
    timezone: resolveTimezone(r.latitude, r.longitude),
    country: r.country ?? "",
  }));
}

The geocoder is Open-Meteo's, which needs no key and returns up to five candidates. The timezone does not come from the geocoder. resolveTimezone wraps tz-lookup, a table of timezone polygons that runs in process, so every candidate arrives with the IANA name the ephemeris needs. The same function runs in the browser for manually typed coordinates. The package ships no types, hence the @ts-expect-error on its import. A query under two characters and any non-2xx from Open-Meteo both return an empty list rather than an error, so the typeahead never shows a failure state; it simply shows nothing.

app/api/geocode/route.ts is three lines: read q, call geocodePlace, return the array. It does not check for a session. The iOS client's comment says why that matters: "The route is public, so this call carries no token." A birthplace search happens before a chart exists and reveals nothing about the account.

The native door: POST /api/profile

// app/api/profile/route.ts
export const runtime = "nodejs";

const REQUIRED = [
  "first_name", "last_name", "birth_date", "birth_time",
  "place_name", "lat", "lng", "timezone",
] as const;

The route runs on the Node runtime because swisseph-wasm is loaded inside saveBirthProfile; the comment above the export says exactly that. The handler resolves the caller with createRouteSupabase(request), which returns a bearer-token client for a native caller and falls back to the cookie client for the web, so RLS evaluates as the user either way. No user is a 401. Then it reads formData() and checks each required field is a non-blank string, answering { error: "Missing required field: <name>" } with a 400 for the first one that is not. lat and lng are parsed with Number and must be finite, or the 400 reads "lat and lng must be numbers".

A photo part is optional. It is used only if it is a File, has a size, and has an image/ content type. uploadAvatar picks an extension from the type (png, webp, otherwise jpg), writes the bytes to the avatars bucket at <userId>/avatar.<ext> with upsert: true, and returns the public URL with a ?v=<timestamp> query so a replaced photo is not served from cache. The upload uses the service-role client, which bypasses RLS; the storage bucket has no per-user policy in the migrations, and the path is fixed to the authenticated user's id by the route, not by the caller. An upload error returns null and the save proceeds without a photo rather than failing.

Finally the route calls saveBirthProfile inside a try. A thrown error is logged and answered with a 500 and the text "Could not compute your chart. Please try again." Success is { ok: true }. The iOS client shows the error string from any non-2xx body verbatim, which is why the messages are written for a person.

The web door: saveIntake

app/(app)/app/intake/actions.ts is the same procedure as a server action. It gets the user from the cookie client, redirects to /login if there is none, runs an identical uploadAvatar, calls saveBirthProfile with the eight fields coerced by String and Number, and redirects to /app. It does not validate presence: the browser form marks the visible inputs required and its submit button is disabled until a place is resolved, so the action trusts the form. The two uploadAvatar functions are copies, not a shared import.

saveBirthProfile

// lib/data/birthProfile.ts
const [vedic, western] = await Promise.all([
  computeChart(birth, "vedic"),
  computeChart(birth, "western"),
]);
const row: Record<string, unknown> = {
  user_id: input.userId,
  ...
  chart: { vedic, western },
  updated_at: new Date().toISOString(),
};
// Only overwrite the avatar when a new one was uploaded.
if (input.avatarUrl) row.avatar_url = input.avatarUrl;

const { error } = await supabase.from("birth_profiles").upsert(row, { onConflict: "user_id" });
if (error) throw new Error(error.message);

Both traditions are computed concurrently and written in one upsert keyed on user_id. Because it is an upsert, a first save and an edit are the same call. The avatar is the one column that is conditionally set: an edit without a new photo leaves the stored URL alone, which is the behaviour the iOS BirthProfileInput documents from its side ("leaving this nil keeps the existing photo"). A rejected write resolves with error rather than throwing, so the function turns it into a throw; the route's catch and the action's error boundary depend on that.

getBirthProfile and the whole-sign upgrade

getBirthProfile selects the caller's row with maybeSingle(), throws on a read error, returns null when there is no row, and otherwise passes the row through ensureCurrentChart. Three server-component pages read through it: home, chat and profile. The chat page redirects to /app/intake when !profile?.chart; the profile page redirects when there is no row; the home page renders an "Enter birth details" call to action instead of redirecting. 

// lib/astrology/derived.ts
export function isChartStale(chart: Chart): boolean {
  return (chart.schemaVersion ?? 1) < CHART_SCHEMA_VERSION || !chart.derived;
}

CHART_SCHEMA_VERSION is 2. The constant's comment explains the bump: a chart stored below this version "has house numbers that disagree with the rashi labels every renderer draws", because house assignment for Vedic charts moved to whole-sign counting from the ascendant (houseFrom(ascSign, signOf(lon)) in computeChart) while Western charts keep Placidus cusps. A chart with no derived block is also stale, since the readings in 0.3.0 cite lords, aspects and dignity from it.

ensureCurrentChart is the upgrade path, and its comment is the design in four sentences. Readers could always derive correct facts in process, but the kundli, the PDF and the iOS app draw from the stored chart, so it has to be rewritten for them to agree. Doing it on read means no migration and no backfill: a chart corrects the first time its owner uses the app. Both traditions are recomputed together, so a profile is never half upgraded. And a failure is swallowed, because an upgrade that cannot be written is not a reason to fail the request that triggered it. 

// lib/data/birthProfile.ts
let stage: "compute" | "write" = "compute";
try {
  const birth: BirthInput = { ..., birthTime: String(profile.birth_time).slice(0, 5), ... };
  const [vedic, western] = await Promise.all([
    computeChart(birth, "vedic"),
    computeChart(birth, "western"),
  ]);
  stage = "write";
  const { error } = await supabase
    .from("birth_profiles")
    .update({ chart: { vedic, western } })
    .eq("user_id", profile.user_id);
  if (error) throw new Error(error.message);
  return { ...profile, chart: { vedic, western } };
} catch (err) {
  const reason = stage === "compute" ? "recompute failed" : "write failed";
  console.error(`chart upgrade skipped (${reason})`, err);
  return profile;
}

The stage variable exists so the log says which half failed. The check on the resolved error is the subtle line: without it, a write rejected by RLS would fall through to the return and the function would claim an upgrade it never wrote. The test that pins this is named for exactly that failure mode.

Where the upgrade runs Only where the stored chart is read as a whole. getBirthProfile runs it for the three web pages, and app/api/kundli/route.ts calls ensureCurrentChart itself before rendering the PDF. The iOS app reads the column directly from Supabase and does not run it; a stale chart on a phone corrects the next time its owner opens the web app or downloads the PDF, and the next ProfileStore.load() picks up the rewritten row.

5.5The clients

Web: IntakeForm

components/IntakeForm.tsx is a client component wrapping a plain HTML form whose action is the server action. It takes an optional initial, and editing = !!initial changes the button text from "Save & build my chart" to "Update my details". The place is held in state as a GeoResult and mirrored into four hidden inputs, place_name, lat, lng and timezone. The submit button is disabled={!geo}, so the action can only ever receive a resolved place.

Three parts of the form are worth reading.

  • PlaceAutocomplete fetches /api/geocode?q= on every change once the query has two non-blank characters, with no debounce, and lists each result as "name · timezone". Picking one calls onPick, sets the input text to the picked name and clears the list. Typing again clears the pick, which sets geo back only when a new result is chosen.
  • TimePicker is three selects (hour 1 to 12, minute 0 to 59, AM or PM) that compute a 24-hour HH:mm into a hidden birth_time input. The comment says why: it "avoids the flaky native <input type="time">". parseTime reverses the mapping for editing, and defaults to 12:00 PM when there is nothing to parse, matching the hint "noon is fine if unknown".
  • ManualCoords replaces the autocomplete when the person clicks "Can't find your birthplace?". It takes an optional place name and two decimal inputs, and on every change calls resolveTimezone(lat, lng) in the browser, so even a hand-typed place gets a real timezone. A non-finite pair clears geo and disables submit again. The name falls back to "lat, lng" when none was typed.

The photo control is a hidden file input behind a circular label, accepting png, jpeg and webp, with a preview from URL.createObjectURL. The date input is native, with a "Selected: Monday, February 9, 1998" echo under it, because a bare date field on a dark theme is easy to misread.

app/(app)/app/intake/page.tsx renders the form with no initial value under the heading "Your birth details". app/(app)/app/profile/page.tsx renders the same component with initial built from the row (slicing birth_time to five characters) and the same saveIntake action, so editing is intake with defaults. The profile chapter, chapter 11, covers the rest of that page.

iOS: RootView decides who sees intake

// mobile/Sanchara/Sources/RootView.swift
struct SignedInView: View {
    @State private var profile = ProfileStore()

    var body: some View {
        Group {
            switch profile.state {
            case .loading:      LoadingScreen()
            case .needsIntake:  IntakeView { await profile.load() }
            case .ready:        ChatView(profile: profile)
            case .failed(let message): ... "Try again" and "Sign out"
            }
        }
        .task { await profile.load() }
    }
}

RootView switches on AuthStore.state; a signed-in user lands in SignedInView, which owns a ProfileStore and switches on its state. needsIntake shows IntakeView with an onSaved closure that simply reloads the store, and a successful reload flips the state to ready, which swaps the whole screen for ChatView. There is no navigation push and no flag to clear: the store's state is the router.

iOS: ProfileStore

load() first fills chart and details from ChartCache if they are nil, so a cold launch with a cached chart draws immediately. It then selects the nine detail columns from birth_profiles with .not("chart", operator: .is, value: "null") and limit(1): a row without a chart counts as needing intake. If there is a row it saves the details to the cache and calls loadChart(), a second select of only the chart column, decoded as ChartBundle, of which the vedic half is kept and cached. The comment on the class gives the reason for two queries: the jsonb is roughly 4 KB and changes only when the details are re-saved, and the details are needed to decide the route before the chart is needed to draw anything.

The catch is where the offline story lives. If the network call throws and both a cached chart and cached details exist, the state is ready; only a device that has never loaded a profile gets failed with "Could not load your chart. Check your connection and try again." A failure inside loadChart is silent: "Keep whatever the cache gave us."

iOS: IntakeView and IntakeStore

IntakeView is the native counterpart of IntakeForm and its doc comment says so, posting to the same route. It takes an optional initial: BirthProfileDetails, an optional onCancel (present only when shown as a sheet from the profile) and the onSaved closure. The form state is an @Observable IntakeStore:

  • Names default to empty, or to AppleSignIn.rememberedName on a first run, so a person who signed in with Apple does not retype what Apple already gave.
  • birthDate defaults to 25 years ago and is bounded by earliestBirthDate (1 January 1900) and today; birthTime defaults to 12:00. Both use wheel pickers, and the time picker carries the hint "A wrong hour moves the ascendant."
  • placeQuery has a didSet that calls scheduleSearch(), which cancels the previous task, ignores queries under two characters, sleeps 300 ms, then calls SancharaAPI.geocode. The comment: "Debounced so a typed city name is one request, not one per keystroke." A picked GeoResult replaces the search field with a card showing name and timezone and a "Change" button.
  • isComplete requires non-blank first and last names and a picked place. The save button is disabled and faded otherwise.
  • prefill(from:) fills the form from saved details, parsing the date and the five-character time with en_US_POSIX formatters, and builds the place from the stored coordinates and timezone rather than searching again, because "the birthplace has not moved".
  • save() formats the date as yyyy-MM-dd and the time as HH:mm in the device's own calendar, since the picked values are wall-clock at the birthplace exactly as the web form sends them, builds a BirthProfileInput, and calls SancharaAPI.saveProfile. On failure, errorMessage is the API error's description, shown above the button.

SancharaAPI.saveProfile attaches the Supabase access token as a bearer header and sends a hand-built multipart body: the eight text parts, then, if photoJPEG is non-empty, a photo part named avatar.jpg with type image/jpeg. A 401 becomes APIError.unauthorized ("Your session expired. Please sign in again."); any other non-2xx becomes APIError.server carrying the response body as the message.

iOS: the photo

SancharaPhotoField wraps PhotosPicker, which runs out of process, so the app never requests photo library permission; it receives one image. The store's photoItem setter loads the item as Data, decodes a UIImage and runs avatarJPEG(), which scales the longest side down to 1024 points and encodes at quality 0.8. The comment gives the reason: a phone photo is several megabytes and is shown at 72 points. photoJPEG stays nil unless a new image was chosen, which is what lets an edit keep the existing photo. The field shows the new image if there is one, else the existing avatar URL through AsyncImage, else "Add photo".

iOS: editing from the profile

ProfileView presents IntakeView(initial: profile.details, onCancel: ...) as a sheet, with an onSaved that reloads the store and dismisses. Because the store's load() refetches both the details and the chart and rewrites the cache, an edited birth time reaches the kundli, Siri and the widget through the same path as a first save.

5.6How it works

First intake

  1. A signed-in user with no row is routed to intake. On the web, /app shows the "Enter birth details" link, and /app/chat and /app/profile redirect. On iOS, ProfileStore.load() finds no row with a chart and SignedInView renders IntakeView.
  2. They type a city. The web fetches on every change; iOS waits 300 ms after the last keystroke. Both hit GET /api/geocode, which calls Open-Meteo and stamps a timezone on each candidate with tz-lookup.
  3. They pick a candidate. The web fills four hidden inputs; iOS sets place. Submit becomes enabled.
  4. They submit. The web posts the form to saveIntake with the session cookie; iOS posts multipart to /api/profile with a bearer token. Either handler uploads a photo if there is one and calls saveBirthProfile.
  5. saveBirthProfile converts local birth time to UT in the given zone, runs the ephemeris for both traditions, and upserts the row.
  6. The web redirects to /app, which now finds a profile and greets the person by first name. iOS receives { ok: true }, calls profile.load(), which fetches the details and the chart, writes both to ChartCache, and sets ready; the root switches to ChatView.

Editing

The same path with defaults. The web profile page passes initial; iOS passes the cached BirthProfileDetails. A submit without a new photo carries no photo part, so avatarUrl is null and the stored URL survives the upsert. A submit with changed birth data recomputes both charts, which both pages tell the person in advance: "Changing your birth data recomputes your chart."

The upgrade on read

A row written before version 2 of the chart schema is read by getBirthProfile or the kundli route, found stale by isChartStale, recomputed from its own stored details, and updated in place. The caller gets the new chart in the same request. If the recompute or the write fails, the caller gets the old row and a log line naming the stage. No cron job, no migration, and no request ever fails because of it.

5.7Performance and cost

  • Two ephemeris runs per save, in parallel. Promise.all over the two computeChart calls. The WebAssembly module is loaded once per function instance through getSwe(); the save is the only place in intake that touches it.
  • The Node runtime, not Edge. The route declares runtime = "nodejs" because the WASM ephemeris needs it. The geocode route makes no such declaration, since it only fetches and runs a lookup table.
  • Geocoding is free and keyless. Open-Meteo's search endpoint takes no API key, and tz-lookup resolves timezones in process, so a search costs one outbound HTTP call and no third-party account.
  • Request volume differs by client. The web autocomplete fetches per keystroke after two characters; a six-letter city is up to five requests. iOS debounces to one. Neither caches results.
  • The photo is shrunk on the phone. 1024 points on the long side at JPEG 0.8 before upload. The web sends whatever the file input received; the bucket stores it as-is.
  • One read, one small column. The iOS store fetches the details and the chart in two selects but caches both, so a warm launch reads from disk and the network refresh is additive. The chart is about 4 KB.
  • Upgrades are amortised. A stale chart costs one extra pair of ephemeris runs and one update, once, on the first read after the schema bump, and only for the rows that are actually read.

Check yourself

Why does the form, not the server, resolve the timezone?

Because the person must see and confirm it. The candidate list shows the timezone beside each place, and the manual path derives one in the browser, so what reaches the ephemeris is what the person saw. The server trusts the five values it is given and never geocodes.

Why are both charts recomputed when only the Vedic house rule changed?

So a profile is never half upgraded. ensureCurrentChart writes { vedic, western } as one value; a partial rewrite would leave two charts from two different computations under one schemaVersion check.

What would go wrong if ensureCurrentChart ignored the resolved error?

supabase-js resolves rather than throws on a rejected write. The function would return the recomputed chart as if it were stored, the PDF would draw from it, and the row would still hold the stale one; the next read would repeat the whole recompute.

Why does ProfileStore fetch the details and the chart separately?

The details decide the route (intake or chat) and are small; the chart is about 4 KB and only needed to draw. Fetching them apart lets the screen appear before the chart lands, and lets a chart fetch fail quietly while the cached copy stands in.

Why does getBirthProfile throw on a read error instead of returning null?

Three pages treat null as "never completed intake" and send the person to the form. A database outage rendered as null would ask an existing user to re-enter their birth details.

Why is the avatar column only written when a new photo arrived?

The save is an upsert of the whole row. Writing avatar_url: null on every edit would erase the photo whenever someone corrected a birth time.
