Chapter thirteen

13The data model

Twelve tables in seven numbered SQL files, one storage bucket, and two keys. Every table hangs off auth.users and cascades when the user goes. Every table has Row Level Security on, and the shape of its policies says who may write it: the person, or only the server.

This chapter reads supabase/migrations/ in order, as it stands on main on 30 September 2026, version 0.3.0. Migrations are the schema's history, and reading them in sequence is reading the product's: a chat with a chart, then a photo, then numerology, then push alerts, then twice-daily readings, then the life timeline and its explanations. After the seven files there is a summary of every table with its RLS shape and every piece of code that reads or writes it, a section on the avatars bucket that no migration creates, and an explanation of the two Supabase keys in terms of the policies. Where a policy and a route handler disagree about who should write a table, the route handler's comment usually says why, and the comment is quoted.

The files are plain SQL with a four-digit prefix. There is no migration runner in the codebase and no CI step that applies them. The README gives two ways to apply them: supabase link followed by supabase db push, or pasting each file into the dashboard's SQL editor, "lowest number first". docs/SUPABASE_SETUP.md still describes running only 0001_init.sql; the README's instruction is the current one and it means all seven.

Migrations are applied by hand, before the code that needs them The README states the rule: "After deploying a version that adds a migration, apply it to the production Supabase project before traffic reaches the new code." docs/GO_LIVE_CHECKLIST.md records what happens when that is missed. As of 16 September 2026 the production database did not have the tables from 0006_life_events.sql and 0007_period_readings.sql, although the timeline code that reads them had shipped. The checklist's fix is to run the two files in the SQL editor, in order, exactly as they are in the repo, and confirm with a query against information_schema.tables for life_events, life_event_scans and period_readings. Since main deploys to production on every push (chapter 15), a commit that adds 0008 is live before anyone has had a chance to apply it, and every route that touches the new table returns an error until someone does.

13.2The migrations, in order

0001 · init

The first file enables pgcrypto (for gen_random_uuid()) and creates the five tables the original product needed: who is an admin, a profile row per auth user, the birth details with the computed chart beside them, and conversations with their messages.

TableColumnsKeys and indexes
adminsuser_id uuid, created_at timestamptzPK user_id, references auth.users(id) on delete cascade
profilesid uuid, display_name text, created_atPK id, references auth.users(id) on delete cascade
birth_profilesid uuid, user_id uuid not null, first_name, last_name, birth_date date, birth_time time, place_name, lat, lng double precision, timezone text, chart jsonb, updated_atPK id default gen_random_uuid(); unique (user_id); FK to auth.users cascade
conversationsid uuid, user_id uuid not null, tradition text check in ('vedic','western'), title text, created_atPK id; index (user_id, created_at desc); FK cascade
messagesid uuid, conversation_id uuid not null, role text check in ('user','assistant'), content text not null, created_atPK id; index (conversation_id, created_at); FK to conversations(id) on delete cascade

Two functions and one trigger. is_admin() is language sql stable security definer with set search_path = public, and returns whether a row in admins matches auth.uid(). handle_new_user() is a plpgsql security definer trigger function that inserts a profiles row for a new auth user, taking display_name from raw_user_meta_data->>'display_name' or, failing that, the part of the email before the @. The trigger on_auth_user_created fires after insert on auth.users for each row. This is the only code anywhere that writes profiles, and, as the summary in 13.4 shows, nothing reads it either. 

-- supabase/migrations/0001_init.sql
-- RLS: owner-only. Admin reads happen via the service-role client, which bypasses RLS.
create policy "profiles self" on public.profiles
  for all using (id = auth.uid()) with check (id = auth.uid());

create policy "birth self" on public.birth_profiles
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());

create policy "conv self" on public.conversations
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());

create policy "msg self" on public.messages
  for all using (
    exists (select 1 from public.conversations c
            where c.id = messages.conversation_id and c.user_id = auth.uid())
  ) with check (
    exists (select 1 from public.conversations c
            where c.id = messages.conversation_id and c.user_id = auth.uid())
  );

-- admins table: readable only by admins; never writable via API (no insert/update/delete policy).
create policy "admins read self-or-admin" on public.admins
  for select using (user_id = auth.uid() or public.is_admin());

Four tables get one for all policy each, which covers select, insert, update and delete with the same predicate. messages has no user_id of its own; its policy reaches through conversations, so a message is yours if its conversation is. admins gets a select policy only. There is no insert policy and none is meant to exist: the file's first comment says "presence in this table = admin. No self-service path", and docs/SUPABASE_SETUP.md has the first admin row inserted by hand in the SQL editor. The is_admin() function is used nowhere in TypeScript; it exists for that one policy, and the application checks adminship with the service-role client instead (13.6).

0002 · avatar

One statement: alter table public.birth_profiles add column if not exists avatar_url text. The column holds a public URL into the avatars bucket (13.5), not the object path, and it is nullable because a photo is optional. The if not exists makes the file safe to run twice.

0003 · numerology_mode

-- supabase/migrations/0003_numerology_mode.sql
alter table public.conversations drop constraint if exists conversations_tradition_check;
alter table public.conversations
  add constraint conversations_tradition_check check (tradition in ('vedic','western','numerology'));

The check constraint from 0001 is dropped by its generated name and recreated with a third value. This is the whole database side of the numerology mode (chapter 6): a conversation records which of the three lenses it was read through, and the constraint is what stops a typo in a client from creating a fourth.

0004 · alerts_push

The first migration written for the iOS app and the scheduled job. Its header comment sets the pattern every later table follows: "The daily job (/api/cron/alerts) writes both tables with the service-role client, which bypasses RLS. The policies below exist so the app can read its own alerts and manage its own device tokens directly."

TableColumnsKeys and indexes
device_tokenstoken text, user_id uuid not null, platform text default 'ios' check in ('ios'), environment text default 'production' check in ('sandbox','production'), updated_atPK token; index (user_id); FK cascade
transit_conditionsid uuid, user_id, kind text, signature text, label text, severity check in ('info','caution','warning'), scope check in ('natal','transit'), detail text, started_on date default today in UTC, ended_on datePK id; unique partial index transit_conditions_open_signature (user_id, signature) where ended_on is null; index (user_id, ended_on); FK cascade
alertsid uuid, user_id, severity check as above, kinds text[] default '{}', title, body, detail, created_at, read_at timestamptzPK id; index (user_id, created_at desc); FK cascade

The token is the primary key of device_tokens, not the user, because one person can have several phones and one phone can change hands. environment exists because a token minted by a development build is only valid against the APNs sandbox host and vice versa; the comment on the column says so, and the go-live checklist notes that rows registered before the app reported its environment correctly may carry the wrong value.

transit_conditions is the state table behind "this changed today". A row is open while ended_on is null, and the partial unique index guarantees at most one open row per (user_id, signature). The daily diff in lib/alerts/run.ts compares the engine's current conditions against the open rows, inserts the new ones, and sets ended_on on the ones that stopped (chapter 9). The default for started_on is (now() at time zone 'utc')::date, so the date is the server's, not the user's; daily_readings makes the opposite choice on purpose. 

-- supabase/migrations/0004_alerts_push.sql
create policy "device tokens self" on public.device_tokens
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());

create policy "conditions self read" on public.transit_conditions
  for select using (user_id = auth.uid());

create policy "alerts self read" on public.alerts
  for select using (user_id = auth.uid());

-- Marking an alert read is the only write the app makes.
create policy "alerts self update" on public.alerts
  for update using (user_id = auth.uid()) with check (user_id = auth.uid());

Three shapes in one file. Device tokens are fully owner-writable. Conditions are owner-readable and nothing else. Alerts are owner-readable and owner-updatable, so the app can set read_at, but no client can insert one; the cron job inserts with the service role. Note that the update policy is on the whole row, not on the column: a client could rewrite an alert's title with its own session. The policy states an intent ("the only write the app makes") that the database does not enforce column by column.

0005 · daily_readings

TableColumnsKeys and indexes
daily_readingsid uuid, user_id, for_date date, slot text check in ('morning','night'), tradition text default 'vedic', title, body, detail, created_at, read_atPK id; unique (user_id, for_date, slot); index (user_id, for_date desc); FK cascade

The two comments in this file are the design. On for_date: "The user's own local date, not UTC: 'my reading for the 26th' has to mean their 26th." On the unique constraint: "One reading per slot per day. This is also what makes the job safe to run more often than expected, or twice by accident." The job in lib/alerts/predictions.ts reads which slots already exist for the user's local date and inserts the missing one; a second run the same morning finds the row and does nothing. Policies are select and update for the owner, the same shape as alerts, and for the same reason: the app marks a reading read, the server writes it.

0006 · life_events

TableColumnsKeys and indexes
life_eventsid uuid, user_id, occurred_on date, precision text default 'day' check in ('day','month','year'), title text check length 1 to 120, note text check length at most 2000, source text default 'manual' check in ('manual','extracted'), created_atPK id; index (user_id, occurred_on); FK cascade
life_event_scansuser_id uuid, scanned_at timestamptz, found_count integer default 0PK user_id; FK cascade

The header comment marks this as "the one table in the schema holding what the user tells us about their own life rather than what the ephemeris computes, so it is owner-only in both directions: no admin read policy, no service-role writes outside the extraction job acting for that same user." Both tables get a single for all owner policy, and in code they are written only through the bearer-or-cookie client, never the admin one. precision exists because people remember "March 2021", not an hour; source distinguishes a typed event from one proposed by mining the person's own chat history, "so a bad extraction run can be undone without touching hand-entered events". life_event_scans is one row per user remembering that the mining ran and how many candidates it found, so the offer to scan appears once (chapter 8).

0007 · period_readings

TableColumnsKeys and indexes
period_readingsuser_id, lord text, period_start date, theme text check length 1 to 80, meaning text check length 1 to 800, events_hash text, generated_atPK (user_id, lord, period_start); FK cascade

One row per mahadasha, plus one row with lord = 'now' for the current mahadasha and antardasha pair, keyed on the antardasha's start "so it goes stale by itself when the sub-period changes". events_hash records which pinned moments the text was written against; when the events inside a period change, the hash no longer matches and the explain route rewrites that period on the next open. The composite primary key is what the explain route's upsert(rows, { onConflict: "user_id,lord,period_start" }) relies on. The policy is one for all owner rule, with the comment "Written by the explain route acting as the user, never by admin tooling." No table in the schema has a touch_updated_at style trigger; every timestamp is a column default or a value the application writes.

13.3The entity relationships

The shape matters for two operations. Account deletion (app/api/account/route.ts) is one call, admin.auth.admin.deleteUser(user.id), and the cascades do the rest; the route's comment lists profiles, birth profiles, conversations and messages, and the same on delete cascade is on every other table too. And any query the application makes needs at most one join, messages to conversations, which is the join the msg self policy performs on every access to a message.

13.4Every table, its RLS shape, and who touches it

The table below was built by reading every .from("...") call under app/ and lib/, excluding tests, and noting which client made it. "User client" means the cookie client (lib/supabase/server.ts) or the bearer client (lib/supabase/route.ts), both of which evaluate RLS as the signed-in user. Four things in that table are worth a second look.

  • profiles is write-only. The trigger fills it and nothing reads it. The name the app shows comes from birth_profiles.first_name; the admin page shows the email from auth.users. The table is a leftover from the first design and costs one insert per sign-up.
  • device_tokens has an owner policy that no code uses. The devices route writes with the admin client, and its comment explains: "a device handed from one account to another has to change owner, and the owner-only RLS policy would (correctly) refuse that update. The user id still comes from the verified session, never from the body." The policy remains so a client could read its own registrations; today none does.
  • alerts is never read on the web. Only the iOS app lists alerts and marks them read, directly against PostgREST. The web has no inbox (chapter 9).
  • The timeline tables are the only ones written as the user from a route handler. life_events, life_event_scans and period_readings are inserted, upserted and deleted through the bearer-or-cookie client, so RLS is the authorisation. Every other server-side write goes through the admin client, and every one of those routes takes the user id from the verified session first.
A rejected write does not throw supabase-js resolves with an error field when RLS or a constraint rejects a write; it does not throw. The comment in lib/data/birthProfile.ts spells this out and is why every write in lib/data/ checks error and turns it into a throw. A read blocked by RLS is worse: it returns an empty result that looks exactly like "no rows yet". That is what a missing policy, or a missing session on a bearer client, looks like from a route handler, and it is the first thing to suspect when a signed-in user sees an empty home.

13.5The avatars bucket

The one piece of storage is not in any migration. The README's architecture sketch lists "Storage (avatars)" beside Postgres and Auth, and points at docs/SUPABASE_SETUP.md for "the storage bucket", but that document has no bucket step, so the bucket is created in the dashboard by hand. The code tells you what it must look like. 

// app/(app)/app/intake/actions.ts (the same function is in app/api/profile/route.ts)
async function uploadAvatar(userId: string, file: File): Promise<string | null> {
  const ext = file.type === "image/png" ? "png" : file.type === "image/webp" ? "webp" : "jpg";
  const path = `${userId}/avatar.${ext}`;
  const bytes = Buffer.from(await file.arrayBuffer());
  const admin = createAdminSupabase();
  const { error } = await admin.storage
    .from("avatars")
    .upload(path, bytes, { contentType: file.type, upsert: true });
  if (error) return null;
  const { data } = admin.storage.from("avatars").getPublicUrl(path);
  // cache-bust so a replaced photo shows immediately
  return `${data.publicUrl}?v=${Date.now()}`;
}

Four facts follow. The upload is made with the service-role client, so the bucket needs no storage policies for writes and none exist in the repo. The object name is {user id}/avatar.{ext} with upsert: true, so each person has at most one photo per extension, and a person who uploads a PNG after a JPEG has two objects with only the newer one referenced. The URL stored in birth_profiles.avatar_url comes from getPublicUrl, which only works if the bucket is public; the home page, the profile page and the admin list all render it in a plain <img> with no token. And a failed upload returns null, which saveBirthProfile reads as "keep the old photo": the comment there says "Only overwrite the avatar when a new one was uploaded". The same function is duplicated in app/api/profile/route.ts for native clients, byte for byte. Nothing in the code deletes an object, on account deletion or otherwise.

13.6The anon key and the service-role key

Supabase issues two keys for a project and the code names them by their environment variables. NEXT_PUBLIC_SUPABASE_ANON_KEY is public by design; the README says it is "safe to ship in the iOS binary", and the NEXT_PUBLIC_ prefix means Next inlines it into browser bundles. SUPABASE_SERVICE_ROLE_KEY is read only through lib/env.ts, which imports server-only so any client component that reaches for it fails the build. The policies in this chapter are what make the first key safe and the second one necessary.

ClientFileKeyRuns asUsed from
Browserlib/supabase/client.tsanonThe signed-in user, via the session in cookiesNothing today; no client component imports it
Cookielib/supabase/server.tsanonThe signed-in user, via the session in cookiesServer components and server actions; lib/supabase/middleware.ts builds the same kind of client over the request's cookies
Bearerlib/supabase/route.tsanon, plus Authorization: Bearer forwardedThe user whose JWT the iOS app sent; falls back to the cookie clientEvery app/api/* route that acts for a user; cron has no session and geocode needs none
Adminlib/supabase/admin.tsservice roleNobody: RLS is bypassedCron jobs, admin pages, device registration, avatar upload, account deletion

With the anon key, every query runs as the authenticated role if a valid JWT is attached, or as anon if none is. Every policy in the schema compares a column to auth.uid(). For the anon role that function returns null, no row matches, and every table reads as empty and refuses every write. So the anon key on its own can do nothing, which is what makes it publishable. With a JWT attached the same key sees exactly the rows whose user_id (or id, or conversation) is the token's subject, which is why listConversations and getBirthProfile need no user filter and why the iOS stores can query PostgREST directly.

The service role bypasses RLS entirely. Reading the policies tells you where it is unavoidable:

  • transit_conditions, alerts and daily_readings have no insert policy. Their writer is the cron job in lib/alerts/, which has no user session because no user is present at 02:30 UTC. It runs as the service role and iterates every birth_profiles row, which an owner policy would never let one session do.
  • admins has no write policy, and its read policy calls is_admin(). requireAdmin() could read it as the signed-in user; instead isAdminUser uses the admin client, and lib/admin/data.ts then reads other people's birth_profiles, conversations and messages, which no policy allows and which is the point of an admin page. Every admin function calls requireAdmin() first; the service role is behind a check, never in front of one.
  • device_tokens needs to change owner, and the owner policy forbids that, so the devices route uses the admin client after verifying the session.
  • Account deletion and the avatar upload are Auth and Storage operations, not table writes; auth.admin.deleteUser exists only on the service role, and the bucket has no policies because only the service role writes it.

Everything else runs as the user. The rule in the code is simple to state and easy to check with a grep for createAdminSupabase: outside tests it appears in ten files, every one of them either imports server-only itself or is a route handler or server action, and the comment in lib/supabase/admin.ts is the rule in one line: "Bypasses RLS. Only ever import from server code behind an admin auth check."

What the policies do not check An owner policy proves the row belongs to the caller. It does not check columns: the update policies on alerts and daily_readings permit rewriting the title as well as read_at, and the for all policy on birth_profiles lets a client write any chart JSON it likes. The application writes chart only from the Swiss Ephemeris on the server, but the database would accept a hand-made one from a valid session. The schema trusts its owners with their own rows completely; it trusts them with nobody else's at all.

Check yourself

Why can the cron job not use the cookie or bearer client?

It has no session: no user is signed in when Vercel calls the route, and it must read every user's birth_profiles row and insert readings for each. Only the service role sees across users, so the job is written for it and the tables it writes have no insert policies at all.

A user's listConversations() returns an empty list although they have chats. What are the first two suspects?

A missing or expired session on the client that made the call (RLS returns nothing, not an error), or a policy that does not match the row. Neither throws; both look like "no data".

Why is the token, not the user, the primary key of device_tokens?

One person can have several phones and one phone can be signed into a different account later. A token must belong to exactly one user at a time, and moving it is an upsert on the token, which is why the route writes it as the service role.

What does unique (user_id, for_date, slot) on daily_readings buy?

Idempotence for the twice-daily job. A second run for the same local date and slot finds the row and writes nothing, so running the job more often, or twice by accident, is safe.

Which tables does the service role never touch, and why does that matter?

life_events, life_event_scans and period_readings. They hold what the person said about their own life, so the migration deliberately gives them no admin path; their routes act as the user and RLS is the whole authorisation.

Why does deploying a commit that adds a migration need a manual step, and in what order?

Nothing applies migrations automatically and main deploys on push. The SQL must be run against production, lowest number first, before the code that reads the new table takes traffic; otherwise every route that touches it errors until it is.
