Chapter two

2The chart engine

Nothing about a chart is guessed. lib/astrology/ turns a date, a time and a place into planets, houses, nakshatras, dashas, doshas and transits with the Swiss Ephemeris, and every later chapter reads from that output. Claude interprets these numbers; it never produces them.

This chapter describes the engine as it is on main on 30 September 2026, version 0.3.0. It is a pure computation layer: no database, no network beyond one geocoding call on the input side, no interpretation. The same nine files serve the web app, the iOS app, the kundli PDF, the timeline, the twice-daily alerts job and the chat. If a number in a reading is wrong, this is where it went wrong, and the tests in section 2.10 are how you find out.

2.1What a chart is here

A birth chart is the sky at one moment, seen from one place on Earth, projected onto the ecliptic and cut into twelve signs of 30 degrees. The engine computes it in two traditions, and almost everything that follows depends on which one is asked for.

  • Tropical and sidereal. Western astrology measures longitude from the vernal equinox (tropical). Vedic astrology measures it from the fixed stars (sidereal). The two zodiacs drift apart by about 50 arcseconds a year and the gap today is roughly 24 degrees. That gap is the ayanamsa; the engine uses Lahiri's value, the one Indian almanacs use. A Sun at 10 degrees Capricorn tropical is at about 16 degrees Sagittarius sidereal, which is why one birth has a different Sun sign in each tradition.
  • The ascendant (lagna in Vedic usage) is the point of the ecliptic rising in the east at the birth moment. It passes through all twelve signs every day, which is why the birth time matters.
  • Houses divide the sky into twelve regions of life, counted from the ascendant. In the whole-sign system the ascendant's sign is house 1, the next sign house 2, and so on. In Placidus the houses are unequal arcs computed from the latitude and the sidereal time, and one can span parts of two signs. Vedic charts here are whole-sign, Western charts Placidus; section 2.4 explains why the engine once got that wrong and how a stored chart is corrected.
  • Nakshatras are the 27 lunar mansions of the sidereal zodiac, each 13 degrees 20 minutes wide. The Moon's nakshatra at birth decides the dasha.
  • Dashas are planetary periods. The Vimshottari system assigns 120 years of life to nine lords in a fixed order; the mahadasha is the major period and the antardasha the sub-period inside it. Where you are in that sequence is what "which dasha am I in" asks.
  • Doshas (and the yogas the code files alongside them) are named afflictions read from positions: Mars in certain houses, every planet on one side of the nodes, and so on.
  • Gochara is transit: today's sky read against the birth chart, by the house each moving planet occupies counted from the ascendant and from the natal Moon. Sade Sati, Saturn's seven and a half years around the natal Moon, is the best known.

The whole output is one JSON value, typed in lib/astrology/types.ts:

// lib/astrology/types.ts
export type Chart = {
  tradition: Tradition;                 // "vedic" | "western"
  ascendant: { sign: string; degree: number };
  houses: number[];                     // 12 cusp longitudes
  planets: Planet[];                    // name, sign, degree, house, retrograde, nakshatra?
  moonSign: string;
  sunSign: string;
  ayanamsa?: number;
  dasha?: DashaInfo;                    // Vedic only: current mahadasha and antardasha
  /** Bumped when the computation changes in a way that moves stored values. */
  schemaVersion?: number;
  /** Classical readings of the positions above. See lib/astrology/derived.ts. */
  derived?: Derived;
};

Three things about this shape decide the rest of the chapter. A planet is stored as a sign and a degree within that sign (0 to 30), not as an absolute longitude; every module that needs the longitude rebuilds it as signIndex(sign) * 30 + degree. The houses array is always the twelve Placidus cusps, even for a Vedic chart, and nothing renders from it. And dasha and derived exist only for Vedic, because every technique in them is Vedic doctrine.

The engine's input is a BirthInput: a date as YYYY-MM-DD, a time as HH:mm, a latitude, a longitude and an IANA time zone name. The place name a person types never reaches the engine. lib/geo.ts turns it into those numbers. 

// lib/geo.ts
export function resolveTimezone(lat: number, lng: number): string {
  return tzlookup(lat, lng);
}

Two choices are worth naming. The geocoder is Open-Meteo's free endpoint, called without a key and capped at five results, and any failure (a short query, a non-2xx response) returns an empty list rather than an error. And the time zone is not taken from the geocoder: tz-lookup resolves it offline from the coordinates, so the zone is consistent with the point actually chosen. That is why the only test in lib/geo.test.ts is two coordinate pairs, New Delhi to Asia/Kolkata and New York to America/New_York. The offset in force on the birth date, daylight saving included, is then luxon's job inside computeChart.

2.3Positions: the ephemeris

The Swiss Ephemeris is the standard high-precision planetary library, here as the swisseph-wasm package, which compiles it to WebAssembly so that it runs inside a Next.js route handler with no native binary. chart.ts initialises it once per server process and keeps the promise, so concurrent first requests share one initialisation rather than racing to build two: 

// lib/astrology/chart.ts
let swePromise: Promise<InstanceType<typeof SwissEph>> | null = null;
async function getSwe() {
  if (!swePromise) {
    swePromise = (async () => {
      const swe = new SwissEph();
      await swe.initSwissEph();
      return swe;
    })();
  }
  return swePromise;
}

computeChart(input, tradition) then runs four numbered steps, which the file itself labels.

1. Local time to Universal Time

luxon parses "${birthDate}T${birthTime}" in the input's IANA zone, converts it to UTC, and the engine asks for the Julian day of that instant with swe.julday(year, month, day, decimalHour). A birth at 06:30 in Kolkata and one at 06:30 in New York are different skies, and luxon knows what offset was in force on that date.

2. Flags

Every call passes SEFLG_SWIEPH | SEFLG_SPEED: use the Swiss Ephemeris data files, and return velocities, because retrograde is read from speed. For a Vedic chart the engine also calls set_sid_mode(SE_SIDM_LAHIRI, 0, 0), adds SEFLG_SIDEREAL, and records get_ayanamsa_ut(jd) to three decimals as the chart's ayanamsa. A Western chart is tropical and has none.

3. Houses and the ascendant

houses_ex(jd, iflag, lat, lng, "P") returns thirteen cusps (index 1 to 12 used) and an ascmc array whose first element is the ascendant longitude. The letter is Placidus, in both traditions. The file's comment records the subtlety that makes this usable for Vedic: "In sidereal mode swisseph applies ayanamsa to cusps too", so the ascendant comes back sidereal and signOf(ascLon) is the lagna sign. The cusps become chart.houses, rounded to two decimals; for Vedic they are carried but never used to place a planet.

4. Planets

Eight bodies are asked for, in the order Sun, Moon, Mercury, Venus, Mars, Jupiter, Saturn and Rahu, where Rahu is SE_MEAN_NODE, the mean lunar north node. Each calc_ut returns [lon, lat, dist, lonSpeed, ...]; the engine keeps the longitude and the longitude speed, and a planet is retrograde exactly when that speed is negative. The Moon's normalised absolute longitude is kept aside for the dasha calculation. Each planet is stored as: 

planets.push({
  name: body.name,
  sign: signOf(lon),
  degree: Number(degreeInSign(lon).toFixed(2)),
  house: tradition === "vedic" ? houseFrom(ascSign, signOf(lon)) : houseOf(lon, cusps),
  retrograde: speed < 0,
  nakshatra: tradition === "vedic" ? nakshatraOf(lon) : undefined,
});

Ketu is not an ephemeris body. It is the south node, always exactly opposite Rahu, so the engine rebuilds Rahu's longitude from its stored sign and rounded degree, adds 180, and pushes a ninth planet with retrograde: true (the mean nodes always move backwards). Rounding first can move Ketu by up to a hundredth of a degree, well below anything rendered.

The helpers in constants.ts are one-line modular arithmetic on a longitude normalised into 0 to 360: signOf divides by 30, degreeInSign takes the remainder, nakshatraOf divides by 360/27. The chart then records sunSign and moonSign, the dasha for Vedic, the schema version, and, for Vedic only, the derived block (section 2.6).

Cost A chart is eight calc_ut calls and one houses_ex on an in-process WASM module: milliseconds after the first request, more on the cold start that initialises the module. chart.test.ts computes six full charts in about 50 ms. There is no per-chart cost beyond CPU.

2.4Houses: whole-sign and Placidus

Two functions place a planet in a house, and which one runs is decided by the tradition.

// lib/astrology/constants.ts
/** The 1-indexed house of `sign` counted from `from`, the classical "Nth from". */
export function houseFrom(from: string, sign: string): number {
  const a = signIndex(from);
  const b = signIndex(sign);
  if (a < 0 || b < 0) return 0;
  return ((b - a + 12) % 12) + 1;
}

// lib/astrology/chart.ts
function houseOf(longitude: number, cusps: number[]): number {
  const lon = ((longitude % 360) + 360) % 360;
  for (let i = 0; i < 12; i++) {
    const start = cusps[i];
    const end = cusps[(i + 1) % 12];
    if (start <= end) {
      if (lon >= start && lon < end) return i + 1;
    } else {
      // wraps past 360°
      if (lon >= start || lon < end) return i + 1;
    }
  }
  return 1;
}

houseFrom is whole-sign counting and it is the most-called function in the engine: the chart, the derived facts, every dosha detector and every transit line use it, with the ascendant sign or the natal Moon's sign as from. It returns 0 for an unknown name so a caller can tell the failure apart from house 1. houseOf walks the Placidus cusps, handling the one pair that wraps through 0 degrees Aries, and is used only for Western charts.

The upgrade of stored charts

Until the change recorded in docs/design/2026-09-17-specific-readings.md, section 0, Vedic planets were placed by houseOf too. The kundli renderers and the PDF had always drawn the houses whole-sign (house 1 labelled with the lagna's sign) and then filled them by the stored Placidus number, so a planet could be drawn inside a house labelled with a sign it was not in. Placidus also lets two houses carry the same sign and one sign appear in none, which leaves "the lord of the 7th" undefined, and every technique in derived.ts rests on lordship. So Vedic became whole-sign: 

// lib/astrology/constants.ts
/**
 * Version 2 moved Vedic charts from Placidus to whole-sign houses. A stored
 * chart below this version has house numbers that disagree with the rashi
 * labels every renderer draws, so readers upgrade it before use.
 */
export const CHART_SCHEMA_VERSION = 2;

A chart written before then carries no schemaVersion at all, which isChartStale reads as 1. The rule in derived.ts is that a chart is stale when its version is below 2 or it has no derived block. Two mechanisms then cooperate so the app ships without a migration or a backfill job:

  • Readers recompute houses from the sign, never from planet.house. deriveFacts builds its own house map with houseFrom(asc, p.sign), and the dosha detectors do the same, so a stale chart still derives correct facts in memory. Both test files pin it with fixtures whose stored house is deliberately 99.
  • The stored row is rewritten on read. ensureCurrentChart in lib/data/birthProfile.ts runs on every getBirthProfile. If the stored Vedic chart is stale it recomputes both traditions together, so a profile is never half upgraded, writes the pair back and returns the fresh row. A compute or write failure is logged and swallowed: an upgrade that cannot be written is not a reason to fail the request that triggered it. The rewrite is needed because the kundli, the PDF and the iOS app draw from the stored numbers.
A visible change Whole-sign moves planets. One in the lagna's sign at a degree below the lagna's degree moves from house 12 to house 1, and similar shifts happen throughout. The design note records that users' charts change when next computed and that whether to say so in the app is a product decision. It also records the consequence for alerts: a house change alters which natal doshas are detected, and the alerts job suppresses natal conditions for anyone who already has a natal row so the migration cannot push "Mangal Dosha has just begun". See chapter 9.

2.5Nakshatras and dashas

The 27 nakshatras are listed in constants.ts in zodiacal order from Ashwini at 0 degrees Aries. Each is 360/27 degrees, and nakshatraOf is just the floor of the longitude over that span. The names, nine per row, are:

The virtual start

Nobody is born at the start of a mahadasha. The Moon at birth is some fraction of the way through its nakshatra, and that fraction of the first lord's period has already elapsed. The first span therefore begins at birth and runs for the balance, years * (1 - fractionElapsed). But the antardashas inside it must be laid out from where the mahadasha would have begun, not from birth, or every sub-period for the rest of that mahadasha lands in the wrong place. dasha.ts carries that point as virtualStart: 

// lib/astrology/dasha.ts
const first = ORDER[startLordIndex];
const spans: Span[] = [{
  lord: first.lord,
  start: birthUt,
  // The first period is the *balance* of the one already running at birth.
  end: addYears(birthUt, first.years * (1 - fractionElapsed)),
  virtualStart: addYears(birthUt, -(first.years * fractionElapsed)),
  fullYears: first.years,
}];
for (let i = 1; i < 12; i++) {
  const o = ORDER[(startLordIndex + i) % 9];
  const start = spans[i - 1].end;
  spans.push({ lord: o.lord, start, end: addYears(start, o.years), virtualStart: start, fullYears: o.years });
}

Twelve spans, not nine: the cycle is 120 years and the engine lays out a third of a second cycle so a long life still has a current period. Each span's nine antardashas run in the same order starting from the span's own lord, each lasting fullYears * subYears / 120 of the parent, laid out from virtualStart. A sub-period that ended before birth is dropped; one straddling birth is clipped to start at birth. As the comment puts it, a chart has nothing to say about time the native was not alive for.

Two exported functions share this layout. computeVimshottari(moonLon, birthUt, now) answers "where am I now": it finds the span containing now (the current UTC instant by default, injectable so tests are deterministic), then the antardasha containing it, and returns both as ISO dates in the DashaInfo the chart stores; outside every span it falls back to the first, which keeps the function total. vimshottariTimeline(moonLon, birthUt) returns all twelve spans with their antardashas nested, and is what lib/timeline/build.ts draws the life timeline from, rebuilding the Moon's longitude from the stored sign and degree. The chart itself carries only the current pair, because that is the only part that ages.

2.6Derived facts

derived.ts exists because a model handed nine planet lines and a lagna writes sign-level prose. What makes an answer specific is which house a planet rules, whether it is strong or weak where it sits, whom it aspects, and where the current dasha lord actually is. The module's header states the scope: "a fixed classical table applied to positions the ephemeris already produced. There is no I/O and no interpretation: the output is the grounding a reading is written from, not the reading."

The debilitation sign is not a table; it is oppositeSign of the exaltation sign. The moolatrikona ranges use a half-open interval, from <= degree < to.

Dignity, and the one three-way case

dignityOf(name, sign, degree) returns one of exalted, debilitated, moolatrikona, own or neutral, plus fromDeepPoint, the distance in degrees from the exact exaltation degree, reported only when the planet is in its exaltation or debilitation sign. Exaltation and debilitation are read by sign, not by degree, so the Sun at 29 Aries is still exalted; the deep point is extra information, not a threshold. The precedence is exalted, then moolatrikona, then own, then debilitated, then neutral.

Two planets break the simple chain: Mercury's exaltation and moolatrikona are both Virgo, and the Moon's are both Taurus. For them a dedicated block owns the whole sign: below the moolatrikona range's from the planet is exalted, inside it moolatrikona, above it own sign if the planet rules the sign (Mercury rules Virgo; the Moon's range runs to 30 so the question never arises). The comment above that block warns that it "must return on every path", because falling through would hit the unconditional exaltation check, and asks the reader not to simplify it into a plain if/else chain. So Mercury at 14 Virgo is exalted, at 18 moolatrikona, at 25 own, and at 15.5 exalted, because 15.5 is below from: 16 even though it is past the deep degree of 15.

Combustion and aspects

A planet is combust when its shorter arc from the Sun is at or within its orb, and the orb depends on whether it is retrograde: Mercury tightens from 14 to 12 and Venus from 10 to 8, the others do not change. The Sun and the nodes are never combust. arcFromSun rebuilds both longitudes from sign and degree and takes the shorter way round, so Venus at 4 Leo is 6 degrees from a Sun at 10 Leo, and Venus at 5 Cancer is 35 degrees away, not 325.

Aspects (graha drishti) are by house, not by degree. Every planet aspects the 7th house from its own; Mars adds the 4th and 8th, Jupiter the 5th and 9th, Saturn the 3rd and 10th. The nodes get the 7th only: the second deliberately absent rule, because the tradition does not agree on a nodal 5th and 9th. aspectedHouses(name, house) wraps past 12, so Saturn in the 12th aspects the 2nd, 6th and 9th.

deriveFacts

deriveFacts(chart) assembles four lists. For each planet a PlanetFact: its whole-sign house (recomputed from the sign, as section 2.4 explained), the houses it rules (its signs, each counted from the ascendant, sorted), its dignity and deep-point distance, whether it is combust and how far it is from the Sun, the houses it aspects, the planets in those houses, and the planets it is conjunct with (same house, itself excluded). For each of the twelve houses a HouseFact: its sign, its lord, where that lord sits and in what dignity, its occupants, and which planets aspect it. For the dasha, two DashaFact entries (mahadasha and antardasha) each carrying its lord's own PlanetFact as placement, which is what lets a reading say the Jupiter period is running from the 8th house rather than just "Jupiter period". And conditions, the natal doshas from section 2.7.

The third absent rule is friendship. Dignity never consults planetary friendship, because, in the header's words, friendship is a compound judgement, natural plus temporal, and half of it is misleading rather than partial. (Numerology does use a natural friendship table, for a different purpose; see section 2.9.)

Two small functions decide who gets these facts:

// lib/astrology/derived.ts
export function isChartStale(chart: Chart): boolean {
  return (chart.schemaVersion ?? 1) < CHART_SCHEMA_VERSION || !chart.derived;
}

export function factsFor(chart: Chart): Derived | undefined {
  if (chart.tradition !== "vedic") return undefined;
  return chart.derived ?? deriveFacts(chart);
}

factsFor is what the chat route and the alerts job call. A Western chart gets undefined, and the callers fall back to plain chart data rather than resurrecting Vedic technique for a tropical chart. The comment at the end of computeChart says the same thing from the other side: "Every technique in derived.ts is Vedic. Western continues to use Placidus houses and gets no derived block at all."

2.7Doshas

doshas.ts reads afflictions from a chart, and from today's chart against a birth chart, into one shape: 

// lib/astrology/doshas.ts
export type Condition = {
  kind: string;
  signature: string;
  label: string;
  severity: "info" | "caution" | "warning";
  scope: "natal" | "transit";
  /** A plain factual sentence, the grounding the model is allowed to interpret. */
  detail: string;
};

The signature is what makes the alerts job possible. It folds in the phase and the sign, so Saturn moving to the next sign, or Sade Sati stepping from rising to peak, reads as a new condition rather than the same one continuing. The daily job diffs signatures against the rows it stored last time; one that appears has started, one that disappears has ended, and only those two events send a push. The detail is a sentence of fact with the ordinal already in it, and it is the only text the model is given about the condition.

2.8Transits (gochara)

A transit chart is a birth chart for now: the same computeChart, with today's date, and the user's birthplace as the location. transits.ts adds a cache and a renderer around it. 

// lib/astrology/transits.ts
const cache = new Map<string, Promise<Chart>>();
const MAX_ENTRIES = 200;

export async function transitChart(args) {
  const day = args.day ?? utcDayKey();
  // One degree is ~111km; users in the same city share an entry.
  const key = `${day}|${args.tradition}|${args.lat.toFixed(0)}|${args.lng.toFixed(0)}`;
  const hit = cache.get(key);
  if (hit) return hit;
  const pending = computeChart(
    { birthDate: day, birthTime: "12:00", lat: args.lat, lng: args.lng, timezone: "UTC" },
    args.tradition,
  );
  if (cache.size >= MAX_ENTRIES) cache.clear();
  cache.set(key, pending);
  try { return await pending; }
  catch (err) { cache.delete(key); throw err; }
}

The sample point is midday UTC, for two reasons the file gives. The obvious one is no ephemeris run per message. The one that pays is that the text built from this chart is identical for the whole UTC day, so it can sit in the cached half of the system prompt (chapter 3) instead of being billed on every turn. Only the Moon moves enough within a day to show at sign resolution, and sampling the middle halves its worst-case drift. The key rounds the coordinates to whole degrees so a city shares one entry; the cache holds promises so concurrent misses share one computation; it clears itself at 200 entries rather than hold stale days; and a failed computation is evicted, never cached.

One caller does not use this cache. The alerts job's condition diff in lib/alerts/run.ts calls computeChart directly with the actual UTC time of the run, since it is deciding whether an affliction has started at that moment. The reading text the same job writes goes through transitChart, for the prompt-cache reason.

describeGochara

The old transit text was "Saturn in Pisces, Jupiter in Gemini", which the file notes "was true of everyone alive on that date and related to the reader not at all". What makes a transit mean anything is the house it falls in from the lagna and from the natal Moon. describeGochara(natal, transit, { includeAfflictions }) writes one line per transiting planet: its sign and retrograde flag; for a Vedic chart its house from the ascendant and its ordinal from the Moon; and any natal planets it sits on by sign, joined so three names read "a, b, and c". For a Vedic chart it then appends a line per transit affliction. The flag exists because the alerts job renders the afflictions itself, filtered by severity, and false avoids saying the same thing twice in one prompt; the chat route has no other source and takes the default.

A Western chart gets no house counting and no afflictions, and the comment says why: the house numbers would be whole-sign where Western is Placidus, and Sade Sati has no meaning in that tradition. It keeps the plain sky, where each body is and which natal body it sits on. describeToday is the last export: a weekday, a date and one of morning, afternoon, evening or night (thresholds 12, 17 and 21) in the user's zone, coarse enough to stay identical for hours.

2.9Numerology

numerology.ts is the one module with no ephemeris in it. Everything is digit arithmetic on the birth date string, and the core operation is reduceToDigit, which sums the digits of a number repeatedly until one digit remains. It never preserves the "master numbers" 11 and 22 some systems keep; every result here is 1 to 9.

Two comments explain design choices. The personal year changes once a calendar year, which is why the prompt carries it in the half that varies rather than the cached half. personalCycle exists because personalYear and personalMonth take identical arguments, so a caller building the pair from two positional calls could transpose them with every test still passing; one function a test can assert against by name moves that risk out of every call site. The Lo Shu grid is, in its own comment, "the most concrete thing numerology has": three 1s and no 4 is specific in a way a root number never is.

Number relationships

Numbers 1 to 9 are ruled by planets, and the relationship of two numbers is the natural friendship of their rulers. The rulers are Sun 1, Moon 2, Jupiter 3, Saturn 4, Mercury 5, Venus 6, Mercury 7, Saturn 8, Mars 9. The comment is candid that 4 and 7 belong to Rahu and Ketu, who have no friendships the tradition agrees on, and that giving them Saturn's and Mercury's rows is a convention kept in one place so it can be corrected in one place.

Read only the first number's row and numberRelationship(2, 6) is neutral while numberRelationship(6, 2) is enemy, and the prompt renders the result as a reciprocal sentence, so two users would get opposite claims about the same pair. The function resolves it compoundly: the same ruler is a friend; enemy if either direction says enemy; friend only if both directions say friend; neutral otherwise. Sun and Moon are friends, Sun and Venus enemies, Sun and Mercury neutral (the Sun does not list Mercury, so one direction fails).

2.10Tests

Six test files sit beside the modules, 78 tests, all run by vitest run with no network and no database. Only chart.test.ts touches the ephemeris; everything else is fixtures. The reference birth for the ephemeris tests is 1 January 1990, 12:00 in New Delhi. prompt.test.ts also lives here but tests the rendering for the model, which is chapter 3's subject.

Check yourself

Why are Vedic houses whole-sign but Western houses Placidus?

Every Vedic technique in derived.ts rests on lordship, and Placidus can put one sign in two houses and another in none, leaving "the lord of the 7th" undefined. Placidus is correct for the Western tradition, which uses none of those techniques.

A stored chart has schemaVersion missing and Mars with house: 12. What does detectNatalDoshas do with that 12?

Nothing. It computes houseFrom(ascendant.sign, mars.sign) and ignores the stored number, so the answer agrees with the whole-sign facts. The row is then rewritten by ensureCurrentChart the next time its owner is read.

Why does the first mahadasha have a virtualStart before birth?

Because the antardashas must be laid out from where the period would have begun, not from birth; otherwise every sub-period for the rest of that mahadasha is misplaced. Sub-periods that ended before birth are dropped and one straddling birth is clipped.

Mercury at 15.5 degrees Virgo: exalted or moolatrikona?

Exalted. The shared-sign block gives exaltation to everything below the moolatrikona range's from of 16, even past the deep degree of 15.

Why is the transit chart sampled at midday UTC rather than at request time?

So the gochara text is identical for the whole day and can sit in the cached half of the system prompt. Only the Moon moves enough within a day to matter at sign resolution, and midday halves its worst-case drift.

Which three rules does derived.ts refuse to encode, and why?

Nodes ruling signs, nodes aspecting the 5th and 9th, and friendship in dignity. The tradition does not agree on them, and a contested claim repeated in every reading is worse than a missing one.
