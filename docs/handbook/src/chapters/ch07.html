Chapter seven

7Kundli

The kundli is the chart as a thing to look at: a North Indian diagram of twelve fixed houses with the rashis rotating through them, drawn from the stored chart and never interpreted. The same JSON becomes a two-page PDF on the server and a tappable SwiftUI drawing on the phone, and the one idea that shaped both is that the lagna is the only input the layout needs.

This chapter describes the code on main on 30 September 2026, version 0.3.0. Nothing here is generated by a model. Every number on the page or the screen comes from the vedic half of birth_profiles.chart, which chapter 5 showed being computed and stored at intake. The server renders that JSON with pdf-lib into a document meant to be printed and kept. The iOS app decodes the same JSON into NatalChart, resolves it into twelve KundliHouse values, and draws them with a geometry table that is, polygon for polygon, the one the PDF uses. On the web there is no on-screen diagram: the home and profile pages link to the PDF.

7.1Intent

The PDF renderer's own comment states the intent for the document: "A birth chart is not a report; in most families it is a piece of paper that gets kept, and this is the version people print, mail to a relative, or hand to an astrologer." So it is set like a document, a serif for the name and the data, a sans for labels, one accent used sparingly, in two pages ordered by the questions people ask. Page one is the diagram and the three values a chart is identified by. Page two is the full table, read both ways: by graha and by house.

The screen's intent is narrower and KundliView states it: "help someone find where a planet sits and what a house holds." The diagram shows glyphs and rashi numerals only; degrees, nakshatras and retrogrades live in the table under it and in the sheet that opens when a house is tapped. The table repeats everything the diagram encodes in plain rows that take unbounded Dynamic Type, so nobody has to read the diagram to get at the numbers.

A third intent runs under both: the diagram must be correct in the way that does not look wrong. KundliTests puts it plainly: "a chart with the signs rotated one house off is still a perfectly handsome diagram." The tests therefore pin the rotation rule and the geometry, and leave the pixels to a snapshot that only checks something was drawn.

7.3Model

The input to the PDF

// lib/pdf/kundli.ts
export type KundliInput = {
  name: string;
  birthDate: string;
  birthTime: string;
  place: string;
  timezone: string;
  chart: Chart; // the vedic chart
  numerology: { mulank: number; bhagyank: number; namank: number };
};

Chart is the type from lib/astrology/types.ts: ascendant sign and degree, the planets with sign, degree, house, retrograde flag and nakshatra, Moon and Sun signs, the optional ayanamsa and the optional dasha. The renderer uses the house field on each planet as stored; it does not recompute houses from longitudes, which is why the route runs ensureCurrentChart first. The three numerology values are computed by the route from the birth date and the full name.

The same JSON in Swift

// mobile/Sanchara/Sources/Features/Kundli/ChartData.swift
struct ChartBundle: Decodable, Equatable, Sendable {
    let vedic: NatalChart
    let western: NatalChart?
}

struct NatalChart: Codable, Equatable, Sendable {
    let tradition: String
    let ascendant: Ascendant
    let planets: [ChartPlanet]
    let moonSign: String
    let sunSign: String
    let ayanamsa: Double?
    let dasha: DashaInfo?
    let derived: DerivedFacts?
    ...
}

The file's comment says it "mirrors lib/astrology/types.ts field for field", with one deliberate omission: the twelve cusp longitudes in the TypeScript houses array are not decoded, because the drawing needs house numbers, not cusps, and houses on the Swift side is a computed property that resolves them. derived is optional at the top level so a chart cached before the derived facts shipped still decodes; the comment's rule is that "a widget or a Siri intent must never fail to decode a chart it has already stored."

ChartPlanet adds three computed views of a row. glyph maps each graha to an astronomical symbol, with Rahu and Ketu borrowing the ascending and descending node signs, and a long comment on why the Moon is U+263D rather than U+263E: on iOS the latter resolves to the emoji font and draws a solid crescent heavier than the eight line-art glyphs beside it, and the text-presentation selector does not fix it. degreeText prints 14°32', the form every printed kundli uses. spokenDescription is one sentence with no abbreviations, used for VoiceOver and handed to the on-device model as a fact.

Rashis and houses

// mobile/Sanchara/Sources/Features/Kundli/ChartData.swift
extension NatalChart {
    var ascendantRashi: Rashi { Rashi(english: ascendant.sign) ?? .mesha }

    var houses: [KundliHouse] {
        let ascIndex = ascendantRashi.rawValue
        return (1...12).map { number in
            let rashi = Rashi(rawValue: (ascIndex + number - 1) % 12) ?? .mesha
            return KundliHouse(
                number: number,
                rashi: rashi,
                planets: planets.filter { $0.house == number }
            )
        }
    }
}

This is the whole rule of a North Indian chart, and the comment above it says so: houses are fixed on the page and the rashis rotate, so house 1 always holds the lagna's rashi and each house after it takes the next sign. Rashi is an enum from mesha (0) to meena (11) carrying both the English name the ephemeris returns and the Sanskrit name a kundli is labelled with, plus number, the 1 to 12 numeral printed in each house. The PDF has the same two tables as constants, SIGNS and RASHI, and the same modular arithmetic in drawChart and the bhava table.

KundliHouse carries the number, its rashi, the planets filed under it, isLagna, a one-line domain ("Self, body, how you begin" for house 1, and so on), and an accessibilityLabel that ends in "Empty." for an unoccupied house. The twelve domain strings are duplicated in the PDF as BHAVA_MEANING, and the PDF's comment gives the reason: "so the paper and the screen say the same thing."

7.4The server side

GET /api/kundli

The route runs on the Node runtime. It resolves the caller through createRouteSupabase, so a bearer token from the phone and a cookie from the browser both evaluate as the user under RLS, and answers 401 with no user. It then selects the profile row with maybeSingle(). A read error is logged and answered 500 with "Something went wrong loading your profile. Please try again." A row without a chart, or no row, is a 400: "Complete your birth details first." Then ensureCurrentChart runs, so a chart stored before the whole-sign change is rewritten before it is drawn. 

// app/api/kundli/route.ts
const chart = (p.chart as { vedic: Chart }).vedic;
const fullName = `${p.first_name} ${p.last_name}`.trim();
const num = computeNumerology(String(p.birth_date));

const pdf = await generateKundliPdf({
  name: fullName,
  birthDate: String(p.birth_date),
  birthTime: String(p.birth_time).slice(0, 5),
  place: String(p.place_name),
  timezone: String(p.timezone),
  chart,
  numerology: { mulank: num.mulank, bhagyank: num.bhagyank, namank: computeNameNumber(fullName) },
});

return new Response(Buffer.from(pdf), {
  headers: {
    "content-type": "application/pdf",
    "content-disposition": 'attachment; filename="sanchara-kundli.pdf"',
    "cache-control": "no-store",
  },
});

Only the Vedic chart is rendered; there is no Western kundli. The response is an attachment named sanchara-kundli.pdf with no-store, since the document is personal and the chart may have been upgraded moments before. The README describes this folder as "Chart JSON and PDF", but on 30 September 2026 the handler has a single GET that returns the PDF. The chart JSON reaches the iOS app by a direct Supabase read, described in 7.5, not through this route.

The page

generateKundliPdf creates a document with four standard fonts, Times Roman and Helvetica in regular and bold, and sets the title to the name followed by "Vedic kundli", the author to "Astrya" and the subject to "Vedic birth chart". Pages are 595 by 842 points (A4) with a 56-point margin; those three numbers are the constants W, H and M. The palette is written with its contrast ratios: the brand orange (ACCENT) is 3.3:1 on white and is used only for rules and fills; text in orange uses ACCENT_TEXT, a darkened variant at 5.3:1; MUTED grey is 5.4:1. The inner chart lines are a mid grey, GRID, because full ink at 1.2 points "drew a heavy black cage around type set at 9pt".

pdf-lib has no character-spacing control, so the small-capital labels are drawn by tracked(), one character at a time, advancing by each glyph's width plus a spacing. trackedWidth() computes the same sum so a label can be centred or right-aligned. Every page gets a header (a 4-point accent band along the top, "ASTRYA" tracked at the left, a right-hand label, a rule) and a footer (a rule and one line of 7.5-point text).

Page one

  1. The name at 27 points serif bold, then "Born 12 September 1994 at 04:35" and a provenance line: place, timezone and, when the chart has an ayanamsa, "Lahiri ayanamsa 24.17°".
  2. identityBand: a 62-point tinted band with a 3-point accent bar at its left edge, split into three columns headed LAGNA, CHANDRA and SURYA. Each shows the Sanskrit rashi at 15 points serif bold with the English name beneath; the lagna's caption also carries its degree.
  3. drawChart, a 414-point square centred horizontally with its bottom edge 168 points from the foot of the page.
  4. Two captions under the square explaining that houses hold fixed positions with the top diamond always first, that the numeral in each house is its rashi from 1 Mesha to 12 Meena, and that an asterisk marks a retrograde graha.
  5. The footer: "Computed with the Swiss Ephemeris by Astrya. For guidance and reflection, not a substitute for professional advice."

Drawing the square

// lib/pdf/kundli.ts
const HOUSE_POLY: [number, number][][] = [
  [[0.25, 0.75], [0.5, 1], [0.75, 0.75], [0.5, 0.5]],   // 1  top kite
  [[0, 1], [0.5, 1], [0.25, 0.75]],                      // 2
  [[0, 1], [0.25, 0.75], [0, 0.5]],                      // 3
  [[0, 0.5], [0.25, 0.75], [0.5, 0.5], [0.25, 0.25]],    // 4  left kite
  ...
  [[1, 1], [0.75, 0.75], [0.5, 1]],                      // 12
];

The twelve houses are unit-square polygons with y running up, pdf-lib's convention. The comment says they are "the same twelve polygons the iOS app draws (KundliGeometry), expressed for the other coordinate system." anchor(house) gives the point a house's contents are centred on: the centroid for the four kites, and for the eight triangles the centroid pulled 14 percent of the way towards the middle of the square, because a triangle's centroid sits two-thirds of the way out to its long outer edge and contents centred there overhang the border. The comment calls this "the same trap the app's chart fell into on its first render."

drawChart first washes the lagna house with a pale tint using drawSvgPath (flipping y with H - p.y because the SVG path convention runs down), so the orientation is legible without a caption. It strokes the border in ink at 1 point, then the two diagonals and the four diamond edges in GRID at 0.6. For each house it computes the rashi number as ((ascIndex + house - 1) % 12) + 1, prints it at 9 points serif 7 points above the anchor (accent text for the lagna, muted otherwise), and then lays the occupants out two to a row, 11 points per row, as 7.5-point bold sans labels such as Sa* 11° Ju 17°. Two per row is so "a four-graha house has to fit inside the narrowest triangle without the abbreviations shrinking below legibility." The abbreviations come from ABBR (Su, Mo, Me, Ve, Ma, Ju, Sa, Ra, Ke).

Plain ASCII on purpose The standard PDF fonts are WinAnsi-encoded, and pdf-lib throws on a character outside that set rather than substituting one. The retrograde symbol and a superscript r are both outside it, so the chart marks retrograde with an asterisk and the table with "(R)". A single stray character would not degrade the page; it would fail the whole route with a 500. The test named for this feeds the renderer every retrograde, every house occupied and a name with accented letters.

Page two

The header's right-hand label is the name in capitals. Four sections follow, each opened by section(), a tracked accent-text label with a rule running from it to the margin.

  • GRAHAS AND NAKSHATRAS. Five columns at fixed offsets from the margin (graha at 0, rashi at 104, degree at 214, house at 274, nakshatra at 324), 19-point rows, alternate rows tinted because "a tint on alternate rows does the work five vertical rules would". A row reads Sa Saturn (R), the Sanskrit rashi, 11°36' from degreeText, the house number, and the nakshatra in muted sans, or a dash when absent.
  • BHAVAS. The same data the other way round: twelve 17-point rows, one per house, giving the rashi by the rotation rule, the grahas in it joined by commas (or a dash), and the BHAVA_MEANING line. House 1 is printed "1 · Lagna" in accent text. The comment says this table answers "what's in my seventh", the question people bring to a printed chart, and fills the lower half of the page that the first draft left empty.
  • VIMSHOTTARI DASHA, only when the chart has a dasha: two rows, Mahadasha and Antardasha, with the lord at 12 points serif bold and the span right-aligned as "Apr 2012" to "Apr 2032" via shortDate.
  • NUMEROLOGY. Three columns, MULANK, BHAGYANK and NAMANK, each a 22-point serif bold number in accent text with a note beside it: "Root, from the day of birth", "Destiny, from the whole date", "Name, from its letters".

The footer repeats the identity line: "Astrya · name · born date at time, place."

Dates

// lib/pdf/kundli.ts
export function prettyDate(iso: string) {
  const [y, m, d] = iso.slice(0, 10).split("-").map(Number);
  if (!y || !m || !d) return iso;
  // Constructed in UTC and read back in UTC: a bare date formatted in a local
  // zone west of Greenwich comes back as the day before.
  return new Date(Date.UTC(y, m - 1, d)).toLocaleDateString("en-GB", {
    day: "numeric", month: "long", year: "numeric", timeZone: "UTC",
  });
}

prettyDate and shortDate are exported "for the test, not for callers": the UTC pinning is the kind of thing that silently regresses, and it cannot be asserted through the finished PDF because pdf-lib compresses its content streams. A malformed date is passed through unchanged rather than printed as "Invalid Date".

7.5The clients

Web

The web app has no chart drawing. app/(app)/app/page.tsx shows "Download your kundli (PDF)" under the "Start a reading" button once a profile exists, and app/(app)/app/profile/page.tsx shows "Download kundli (PDF)" above the edit form. Both are plain anchors to /api/kundli; the browser sends the session cookie, the route answers with an attachment, and the browser saves it.

iOS: where the chart comes from

ProfileStore.loadChart() selects the chart column from birth_profiles for rows where it is not null, decodes it as ChartBundle, keeps the vedic half as NatalChart and writes it to ChartCache.shared.save(chart:). The cache is a JSON file named chart.json in the App Group container, written atomically with complete file protection, and read back on the next launch before any network call. ChatView and ProfileView both present KundliView(details:chart:) as a sheet, guarded by if let details = profile.details, let chart = profile.chart, so the sheet cannot open on a device that has never loaded a chart.

iOS: KundliView

The screen is a NavigationStack titled "Your kundli" with a Done button, holding five blocks in a scroll view capped at 480 points wide.

  • Summary. The full name in a serif title, a birth line built from the details ("12 September 1994 at 04:35" using the device's long date style) and the place, then three stat columns, Lagna, Chandra and Surya, each with the Sanskrit rashi and an English caption; the lagna's caption is its degree. Lagna leads "because the whole diagram is oriented from it."
  • Rashi chart. KundliChartView bound to selectedHouse, under a caption that teaches the diagram: houses sit in fixed places, the numeral in each is its rashi counted from Mesha, tap a house to see what it holds.
  • Vimshottari dasha, when present: Mahadasha and Antardasha with "until Apr 2032", formatted by ChartFacts.calendarDay in UTC.
  • Grahas. One row per planet: glyph, name with a retrograde mark, nakshatra, then "Vrishchika 2°42'" and "House 1" on the right. Each row is a button that opens the house the planet sits in. This table is "the accessible path through the chart and the one that survives the largest text sizes."
  • Footer. "Export as PDF", an error line, and when the chart has an ayanamsa, "Sidereal, Lahiri ayanamsa 24.17°. Computed with the Swiss Ephemeris."

Tapping a house, on the diagram or through a planet row, sets selectedHouse, and a sheet(item:) presents HouseDetailSheet at medium or large detents: the house number (or "House 1 · Lagna"), the Sanskrit and English rashi, the domain line, and either the planets with degree and nakshatra or the sentence "No graha sits here. An empty house is read through its lord and the aspects reaching it", pointing the person back to the reading.

iOS: KundliChartView

// mobile/Sanchara/Sources/Features/Kundli/KundliChartView.swift
enum KundliGeometry {
    static func polygon(house: Int) -> [CGPoint] {
        let tl = CGPoint(x: 0, y: 0), tr = CGPoint(x: 1, y: 0)
        let bl = CGPoint(x: 0, y: 1), br = CGPoint(x: 1, y: 1)
        let t = CGPoint(x: 0.5, y: 0), r = CGPoint(x: 1, y: 0.5)
        let b = CGPoint(x: 0.5, y: 1), l = CGPoint(x: 0, y: 0.5)
        let c = CGPoint(x: 0.5, y: 0.5)
        let tlq = CGPoint(x: 0.25, y: 0.25), trq = CGPoint(x: 0.75, y: 0.25)
        let blq = CGPoint(x: 0.25, y: 0.75), brq = CGPoint(x: 0.75, y: 0.75)

        switch house {
        case 1: return [tlq, t, trq, c]
        case 2: return [tl, t, tlq]
        case 3: return [tl, tlq, l]
        case 4: return [l, tlq, c, blq]
        ...
        default: return [tr, trq, t]
        }
    }
}

The geometry is a unit square with y running down, SwiftUI's convention, named at its nine significant points so "the table below reads like the drawing". labelAnchor is the PDF's anchor with a pull-in of 0.12 instead of 0.14, and its comment tells the story the PDF's comment refers to: the first render clipped the retrograde marks off Mercury and half of Jupiter. path(house:in:) scales a polygon into a rect. KundliFrame is a Shape that strokes every line of the chart as one path: the rect, the two diagonals, and the diamond through the four midpoints.

The view is a GeometryReader that takes the smaller of width and height as the side and stacks three layers. First, twelve HouseRegion shapes, each filled (accent at 0.16 when selected, 0.05 for the lagna, a 2 percent white wash on even houses so the regions read as distinct without twelve borders), outlined only for the lagna (accent at half strength) and the selected house (full accent, 1.25 points), each a tappable accessibility button carrying the house's label. Second, the frame stroked in Theme.chartLine at 1 point, hit-testing off. Third, the contents positioned at each anchor: the rashi numeral in a serif at a caption-relative ScaledMetric of 11, and the glyphs two per row at a footnote-relative 15, with a small accent "R" overlaid top-right of a retrograde planet. Both metrics scale with Dynamic Type but are relative to small styles, since "the diagram has fixed geometry, so the scaling is capped."

The comment on stroke(for:) records a visual decision worth keeping: the first version gave the lagna a full-strength outline, and "the result was a large glowing diamond that read as 'this house is selected'", which is the meaning selection needs for itself. The lagna is now marked, not spotlit.

7.6How it works

The diagram's geometry

Read the picture against the tests. "The four kites are an eighth of the square each, the eight triangles a sixteenth. Together that is the whole square and no more" is testTheTwelveHousesTileTheSquareExactly, computed by the shoelace formula. testHouseOneIsAtTheTopAndSevenAtTheBottom asserts house 1's anchor has y below 0.35 and house 7's above 0.65, with 4 on the left and 10 on the right, which the comment calls "the one orientation rule a North Indian chart cannot get wrong". And testEveryLabelAnchorSitsInsideItsOwnHouse runs a winding test on every anchor, since the kites are concave and a centroid test would not do.

Downloading the PDF

  1. On the web the anchor navigates to /api/kundli with the session cookie. On iOS, "Export as PDF" calls SancharaAPI.kundliPDF(), which attaches the Supabase access token as a bearer header; isPreparingPDF relabels the button "Preparing…" and blocks a second tap.
  2. The route reads the row, refuses without a user or a chart, and upgrades a stale chart.
  3. It computes the three numerology numbers from the birth date and full name.
  4. generateKundliPdf lays out both pages and returns the bytes.
  5. The browser saves sanchara-kundli.pdf. iOS writes the data to <first-last>-kundli.pdf in the temporary directory and presents a ShareSheet with that URL; a thrown error becomes the footer's error line.

Opening the kundli from Siri or a control

  1. OpenKundliIntent.perform() writes "kundli" to the pendingDestination key in the App Group UserDefaults suite and returns; openAppWhenRun brings the app forward.
  2. ChatView calls DeepLink.shared.drain() whenever the scene phase becomes active. drain() reads and clears the key in one step through takePendingDestination(), "so a destination is never handled twice", and sets pending = .kundli.
  3. ChatView observes DeepLink.shared.pending, sets showKundli = true and clears pending. The sheet reads profile.chart, which on a warm launch came from ChartCache before any network call.

A widget tap reaches the same place by URL: DeepLink.handle(url:) maps the host kundli of a sanchara:// URL to the same destination, with no App Group hop, and RootView routes such URLs to DeepLink rather than to the auth store so they are not mistaken for an expired sign-in link.

7.7Performance and cost

  • No ephemeris on the hot path. Rendering reads stored JSON. The only time the route computes anything astronomical is the one-off upgrade of a pre-version-2 chart, which chapter 5 describes.
  • Standard fonts, no embedding. The four StandardFonts ship with every PDF reader, so the document carries no font bytes and the test fixture's two pages are small. The price is WinAnsi, which is why the renderer is ASCII-only.
  • No caching, by design. cache-control: no-store. The document is personal, cheap to regenerate, and may reflect an upgrade that happened during this request.
  • The screen draws from disk. ProfileStore.load() reads chart.json from the App Group before its network refresh, so the kundli sheet opens from cache on a warm launch and works offline. The chart is about 4 KB.
  • Houses resolved once per read. NatalChart.houses is a computed property that filters the planet list twelve times; with nine planets that is trivial, and the view calls it inside a ForEach rather than storing it.
  • The widget stays small. Compiling six dependency-free files into the extension keeps the Supabase client, SwiftUI drawing code and the network out of a process that must render in a tight memory budget and cannot sign in.
  • No model call, no cost. Nothing in this chapter calls Claude. The kundli is the one feature that is free at any volume beyond Vercel function time and a few kilobytes of Postgres reads.

Check yourself

Why is the lagna the only input the layout needs?

Because the houses never move. House 1 is always the top kite; the rashi in each house is (asc + house - 1) mod 12; and each planet already carries its house number from the stored chart. Everything else on the diagram is a lookup.

Why does the route call ensureCurrentChart when the drawing code never computes a house?

That is exactly why. The renderers trust planet.house as stored, so a chart written under the old house rule would print numerals and planets that disagree. The upgrade rewrites the row before either renderer sees it.

Why is the triangle's anchor pulled towards the centre, and why by two different amounts?

A triangle's centroid sits two-thirds of the way out to its long edge, so a numeral over a row of glyphs centred there crosses the border. Each renderer chose its own pull-in for its own type sizes: 0.12 on screen, 0.14 on paper.

Why does the PDF mark retrograde with an asterisk when the app uses a symbol?

The PDF uses the standard WinAnsi fonts and pdf-lib throws on any character outside that encoding. The app renders with system fonts and can use the symbol. Neither is wrong; the encoding decided it.

Why can the widget extension compile ChartData.swift but not KundliChartView.swift?

ChartData imports only Foundation and is listed by path in the widget target. The view imports SwiftUI and Theme and is not listed. The extension decodes the cached chart to answer questions; it does not draw the diagram.

Why does the intent write to UserDefaults instead of presenting the kundli itself?

It may be running in the widget extension, a process that can present nothing. The app drains the key when it comes to the front, and reads-and-clears in one step so the destination is never handled twice.
