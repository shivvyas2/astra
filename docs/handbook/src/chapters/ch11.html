Chapter eleven

11Profile, account, and admin

The profile is the birth chart's front door: the details that computed it, a photo, the kundli, and the two account controls that end things. Beside it sits an admin area that can read everything about a user and change nothing.

11.1Intent

This chapter describes the profile, account deletion and the admin area as they are on main on 30 September 2026, version 0.3.0. The profile screen has one job on both clients: show the birth details on file and let a person change them or their photo. Changing the birth data recomputes the chart; that sentence appears verbatim on the web page and in the iOS header, because it is the one consequence a person should know before they edit. Account deletion exists because App Store Review Guideline 5.1.1(v) requires it, and it was built as one route that both clients call. The admin area exists so the author can see what a user's chart, profile and transcripts look like when something goes wrong, without a database console and without any way to alter a user's data from the browser.

Three decisions shape the code. A photo is optional and never travels alone: it rides as one part of the same multipart request as the birth details, and the server overwrites the stored avatar only when a photo part is present. Deletion takes no user id from the request, so a caller can only ever delete themself, and the database's cascades do the rest. And the admin has read access through the service-role client, but the only actions on offer send a password reset email or mint a one-time login link; nothing on any admin page writes to a user's rows.

The profile has no route of its own for reading. The web page reads through getBirthProfile with the cookie client, and the phone reads birth_profiles directly over PostgREST under the owner-only policy. Only writes go through a route or an action, because a write computes the chart with the Swiss Ephemeris and that runs on the server.

11.3Model

birth_profiles

One row per user, enforced by unique (user_id). The columns are the eight birth fields, the computed chart as jsonb, updated_at, and since migration 0002 a nullable avatar_url. user_id references auth.users(id) on delete cascade. 

// lib/data/birthProfile.ts
export type BirthProfileRow = {
  id: string;
  user_id: string;
  first_name: string;
  last_name: string;
  birth_date: string;
  birth_time: string;
  place_name: string;
  lat: number;
  lng: number;
  timezone: string;
  avatar_url: string | null;
  chart: { vedic: unknown; western: unknown } | null;
};

The iOS counterpart is BirthProfileDetails, a Codable struct whose coding keys map the snake-case columns. It deliberately omits the chart: ProfileStore fetches the details and the roughly 4 KB chart in two queries, the second only once the first says a chart exists. Two computed properties matter here. fullName joins and trims the names. birthTimeShort takes the first five characters of the Postgres time, which arrives as HH:mm:ss, giving the HH:mm shape the picker and POST /api/profile both use. The web page does the same with String(p.birth_time).slice(0, 5).

The avatar

The photo lives in a Supabase Storage bucket called avatars, at the path <user id>/avatar.<ext> where the extension is png, webp or jpg by content type. What the row stores is the bucket's public URL for that path with a ?v=<timestamp> query appended; the comment says "cache-bust so a replaced photo shows immediately". Nothing in the migrations creates the bucket or a storage policy: uploads use the service-role client, and reads are plain fetches of the public URL by the browser, AsyncImage, and the admin pages. The code therefore assumes the bucket exists and is public, which is a one-time dashboard step rather than a migration.

The upload contract

// mobile/Sanchara/Sources/Services/SancharaAPI.swift
struct BirthProfileInput {
    var firstName = ""
    var lastName = ""
    var birthDate = ""      // yyyy-MM-dd
    var birthTime = ""      // HH:mm
    var placeName = ""
    var lat: Double = 0
    var lng: Double = 0
    var timezone = ""
    /// Optional profile photo, already downscaled to JPEG. The route uploads it
    /// to the `avatars` bucket and only overwrites the stored URL when one is
    /// sent, so leaving this nil keeps the existing photo.
    var photoJPEG: Data?
}

multipartBody(boundary:) writes the eight text fields as form parts named exactly as the columns, then, only if photoJPEG is non-empty, a part named photo with filename avatar.jpg and content type image/jpeg. The same field names are what the web IntakeForm posts, with a file input named photo that accepts PNG, JPEG and WebP. One server contract, two producers.

admins and the admin rows

admins has two columns, user_id and created_at, and no write policy. AdminUserRow in lib/admin/data.ts is what the user list renders: id, email, created and last sign-in from Auth, first and last name, place, birth date and avatar from birth_profiles, and a conversationCount.

11.4The server side

Saving the profile

Two entry points do the same work. saveIntake in app/(app)/app/intake/actions.ts is a server action the web form posts to; it reads the user from the cookie client, redirects to /login if there is none, uploads the photo if one was sent, calls saveBirthProfile, and redirects to /app. POST /api/profile exists because, as its comment says, a native client cannot invoke a server action. It does the same work with the bearer-aware client, validates the eight required fields and that lat and lng are finite numbers (400 otherwise), and returns { ok: true } instead of redirecting. Both contain an identical uploadAvatar. 

// app/api/profile/route.ts
let avatarUrl: string | null = null;
const photo = form.get("photo");
if (photo instanceof File && photo.size > 0 && photo.type.startsWith("image/")) {
  avatarUrl = await uploadAvatar(user.id, photo);
}
// lib/data/birthProfile.ts, inside saveBirthProfile
// Only overwrite the avatar when a new one was uploaded.
if (input.avatarUrl) row.avatar_url = input.avatarUrl;

const { error } = await supabase.from("birth_profiles").upsert(row, { onConflict: "user_id" });

These two fragments are the whole avatar rule. No photo part, or an empty one, or one that is not an image, means avatarUrl stays null; and a null avatarUrl means the upsert row has no avatar_url key at all, so the existing value is left standing. saveBirthProfile always recomputes both charts (computeChart for vedic and western in parallel) and writes them with the row, so any save, including one whose only purpose is a new photo, is a chart computation. An upload that fails returns null from uploadAvatar and the save proceeds without touching the photo; the failure is not reported to the client.

Deleting the account

// app/api/account/route.ts
export async function DELETE(request: Request) {
  const supabase = await createRouteSupabase(request);
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return new Response("Unauthorized", { status: 401 });

  const admin = createAdminSupabase();
  const { error } = await admin.auth.admin.deleteUser(user.id);
  if (error) {
    console.error("account deletion error", error);
    return Response.json({ error: "Could not delete your account. Please try again." }, { status: 500 });
  }

  return Response.json({ ok: true });
}

Sixteen lines, and the comment above them carries the two rules: the user id comes from the verified session, never from the request body, so a caller can only ever delete themself; and the rows cascade from auth.users. What actually goes, and in what order:

  1. auth.admin.deleteUser removes the row in auth.users. This is the only statement the route issues.
  2. Postgres runs the on delete cascade on every foreign key that points at it. In schema order that is admins, profiles, birth_profiles, conversations, device_tokens, transit_conditions, alerts, daily_readings, life_events, life_event_scans and period_readings.
  3. messages cascades from conversations, one level down, so transcripts go with their conversations.

Two things do not go. The avatar object in the avatars bucket is not deleted; no code removes it, and the public URL that pointed to it was in the row that just cascaded away. And the Apple token is not revoked, the gap described in 4.6. Both are worth knowing before an App Store review that exercises deletion.

What the admin can read

lib/admin/data.ts has three functions, all built on createAdminSupabase, all read-only.

  • adminListUsers calls auth.admin.listUsers for the first page of up to 1000 users, selects six columns from every birth_profiles row and the id, user_id pair of every conversation, joins them in memory into AdminUserRow, and sorts newest first. Three queries regardless of user count.
  • adminGetUser calls auth.admin.getUserById, selects the whole birth_profiles row for that user, and lists their conversations newest first with id, tradition, title and created date. The returned user carries a confirmed boolean derived from email_confirmed_at.
  • adminGetTranscript selects one conversation and its messages in creation order, with role, content and timestamp.

The chart jsonb comes back as part of select("*") in adminGetUser, but the page renders only the six birth fields from it; the chart is never shown. Nothing in the file inserts, updates or deletes.

What the admin can do

app/admin/actions.ts has four server actions. adminSignIn and adminSignOut are covered in 4.8. The other two both begin with await requireAdmin():

  • sendPasswordReset calls resetPasswordForEmail on the cookie client with a redirect to /login. The comment says why this is the shape: the admin never sees or stores the password. The user page repeats this next to the buttons: "Passwords are stored only as secure one-way hashes and cannot be displayed."
  • generateLoginLink calls auth.admin.generateLink with type magiclink for the user's email and a redirect to /app, then redirects back to the user page with the link in the query string, where it is printed with the instruction to open it in a private window. This is the one capability that lets the author act as a user, and it acts through a normal session under RLS, not through the admin client.

11.5The clients

Web

app/(app)/app/profile/page.tsx is a server component. It calls getBirthProfile, redirects to /app/intake if there is no row, and renders a heading, the sentence about recomputing, a "Download kundli (PDF)" link to /api/kundli, and the IntakeForm with action={saveIntake} and every field pre-filled from the row. The form is the same component intake uses (chapter 5); an initial prop switches its button label to "Update my details" and seeds the photo preview from avatarUrl. Choosing a file replaces the preview with an object URL before anything is uploaded.

The sidebar in AppShell has the Profile link, highlighted when the path is /app/profile, and the Sign out form at the bottom. There is no account deletion on the web. The route accepts the cookie client and would work, but no page calls it; deletion was built for the App Store requirement and only the phone offers it today.

iOS: ProfileView

ProfileView is a sheet in a NavigationStack, presented over the chat, and its header comment names it the native counterpart of the web page. It takes a ProfileStore and reads AuthStore from the environment. Top to bottom:

  • The header: a 64-point circular PhotosPicker showing the current photo via AsyncImage, or "Add photo", with a small camera badge and a progress overlay while uploading; then fullName in the light 28-point face and the recompute sentence.
  • The detail card: three rows, Born, Place, Timezone. formattedBirth parses birthDate with a POSIX formatter and renders it long-style with birthTimeShort; the comment gives the target shape, "15 June 1995 at 10:30", the moment as it was where they were born.
  • Buttons: "View your kundli" (disabled and dimmed until profile.chart is loaded), "Edit birth details", and, only when there is no chart yet, "Download kundli (PDF)". The comment explains the ordering: the kundli leads now that there is one to look at in the app, and the PDF is reachable from inside the chart instead of as a second competing button.
  • Suggestions: a status line from SuggestionEngine.onDeviceStatus and a note that follow-up questions are written on the device.
  • Account: Sign out, which calls auth.signOut() and dismisses; and "Delete my account" in the accent colour, which sets confirmDelete and raises an alert with a Cancel and a destructive Delete.

"Edit birth details" presents IntakeView with the current details; on completion the sheet reloads the store and closes. That path is chapter 5's. Changing the photo is deliberately not that path. The header comment says it: routing a photo change through the birth-details form would mean re-submitting a chart to swap a picture.

iOS: the photo

func avatarJPEG(maxDimension: CGFloat = 1024, quality: CGFloat = 0.8) -> Data? {
    let longest = max(size.width, size.height)
    guard longest > 0 else { return nil }

    let scale = min(1, maxDimension / longest)
    let target = CGSize(width: (size.width * scale).rounded(), height: (size.height * scale).rounded())
    ...
    return resized.jpegData(compressionQuality: quality)
}

UIImage.avatarJPEG is the one image function in the app. It scales the longest side down to 1024 points, never up (min(1, ...)), renders at scale 1 so the output is not multiplied by the screen density, and encodes JPEG at 0.8. The comment gives the reason: a modern phone photo is several megabytes and is shown at 72 points, and sending the original would make intake feel broken on a slow connection for no visible gain. SancharaPhotoField, the intake form's circular control, wraps PhotosPicker, which runs out of process; the app never asks for photo library permission because only the one chosen image is handed over. ProfileView uses PhotosPicker directly for the same reason.

AvatarBadge is the 28-point control in the chat top bar: the photo when there is one, otherwise the first letters of the first and last name, and when even those are absent a star glyph. The comment's rule is "never an empty grey circle". AsyncImage uses the initials circle as its placeholder, so the badge never flashes empty while the image loads.

iOS: what is cached

ProfileStore.load() begins by reading the chart and the details from ChartCache in the App Group, so the profile sheet and the badge draw at once; the network fetch that follows refreshes both and writes them back. If the fetch fails and a cache exists, the state is still ready; only a device that has never loaded a profile sees the failure screen. On sign-out ChartCache.clear() removes the chart, details, reading and period files, so the next account on the device does not inherit this one's name or photo URL. The avatar image itself is fetched by AsyncImage from the public URL and is not written to the App Group.

The admin pages

Three pages, each opening with await requireAdmin() and wrapping itself in AdminShell, a sidebar with one menu entry, Users, and a Sign out form. app/admin/page.tsx lists users newest first with avatar or initials, name or "(no profile yet)", email, join date and chat count. app/admin/users/[id]/page.tsx shows an Account card (names, email, joined, last sign-in, email confirmed, user id), the two action buttons, a Birth profile card (date, time, place, timezone, latitude, longitude) or "No birth details entered yet", and the list of chats linking to app/admin/conversations/[id]/page.tsx, which renders the transcript as bubbles labelled User and Astrya. Every page is read from lib/admin/data.ts; there is no form on any of them that changes a user's row.

11.6How it works

Change a photo

ProfileView.uploadPickedPhoto runs when photoItem changes. It loads the item as Data, decodes a UIImage, and calls avatarJPEG; if any step fails the message is "That image could not be read. Try another." It then builds a BirthProfileInput from the details already on file, using birthTimeShort for the time, attaches the JPEG, and calls SancharaAPI.saveProfile. The method's comment states the reason for sending the whole profile: the route takes it as a whole and only replaces the avatar when a photo part is present. On success profile.load() refreshes the details, and the new URL, with its fresh ?v= query, makes AsyncImage fetch the replaced image rather than a cached one. A defer block clears the picker item and the uploading flag on every exit.

Delete the account

  1. The alert's destructive button calls deleteAccount(), which sets isDeleting so the button cannot be tapped twice.
  2. SancharaAPI.deleteAccount() sends DELETE /api/account with the bearer token and checks the status; a non-2xx becomes an error shown under the buttons.
  3. The route deletes the auth user and the cascades run (11.4).
  4. On success the view calls auth.signOut(). Its first step, PushStore.shared.unregister(), has nothing left to act on: the user is gone and the device_tokens row has already cascaded away. The call is wrapped in try?, so whatever the server answers, nothing is lost and nothing is shown. Then the Supabase session is signed out and ChartCache is cleared, which removes the deleted person's chart from the widget and Siri.
  5. The sheet dismisses and RootView shows AuthView.

An admin session

  1. The author opens /admin. The middleware finds no session and redirects to /admin/login.
  2. adminSignIn signs in with a password, checks admins, and redirects to /admin. A non-admin account is signed out again and told "Not authorized".
  3. The users page calls requireAdmin then adminListUsers; each user links to their page, each chat to its transcript. Every read goes through the service-role client because the rows belong to other people.
  4. To see the app as a user, "Generate login link" mints a magic link and prints it. Opened in a private window, it goes through /auth/callback like any other link and produces an ordinary session for that user. From then on the private window is that user, under RLS, with no admin powers.

11.7Performance and cost

  • A photo change costs a chart. saveBirthProfile always runs computeChart twice, so swapping a picture invokes the ephemeris. It runs in process inside the route and completes in the same request, so the cost is server time rather than a slow round trip, but it is the reason the profile route declares runtime = "nodejs". Splitting a photo-only endpoint off would remove it.
  • Uploads are bounded on the phone. 1024 points on the longest side at 0.8 quality; testDownscalesLargePhotos asserts a 3000 by 2000 source comes out under half a megabyte. The web form sends whatever file was chosen, with no client-side resize, and the route accepts any image/* of any size.
  • Reads are cached on the phone. The profile sheet draws from the App Group cache before the network answers, and the details query selects nine columns without the chart, which is fetched separately and only when needed.
  • The public URL carries a cache-buster. The ?v= timestamp is stored in the row, not computed on read, so every client sees the same URL until the next upload and the image is cached by the browser and by URLSession until then.
  • Admin reads are three queries for the list, regardless of user count, joined in memory; and listUsers asks for one page of 1000, so past that the list is silently truncated. The user page is three more, and the chart jsonb rides along in select("*") unused.
  • Deletion is one statement. The cascades run inside Postgres; the route does not enumerate tables and does not need to change when a table is added, provided the new table references auth.users with on delete cascade as all eleven do today.

Check yourself

How does the server know whether to keep or replace the avatar?

By the presence of a photo part that is a non-empty image. If there is none, avatarUrl is null and saveBirthProfile omits avatar_url from the upsert, so the column keeps its value.

Why does the iOS photo change send all eight birth fields?

Because the route takes the profile as a whole and there is no photo-only endpoint. The view builds the input from the details already on file so nothing changes but the picture.

What does DELETE /api/account delete, and what does it leave?

It issues one auth.admin.deleteUser; every table referencing auth.users cascades, and messages cascades from conversations. It leaves the avatar object in storage and does not revoke the Apple token.

Why does the profile save recompute the chart when only the photo changed?

Because saveBirthProfile has one path and it always computes both charts before the upsert. The cost is accepted for simplicity; a separate avatar endpoint would avoid it.

Which admin action changes a user's row?

None. The two actions send a password reset email and mint a magic link; both go through Auth, and neither touches a table.

Why is the upload done with the admin client while the row write is done as the user?

There is no storage policy for users, so the bucket write needs the service role; the path is built from the verified user id. The row is under RLS, so the user's own client is enough and keeps the rule that a user writes only their own row.
