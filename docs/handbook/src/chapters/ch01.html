Chapter one

1Architecture

Astrya is built on one bet: the chart is computed, and only the reading is interpreted. The Swiss Ephemeris runs inside a Next.js route handler and produces every position, house, nakshatra, dasha and dosha as a number. Claude is handed those numbers and asked what they mean. Two clients, a web app and a native iOS app, call the same route handlers, share one Supabase project, and are told apart only by how they prove who they are.

This chapter describes the code on main on 30 September 2026, version 0.3.0. It is the map for everything that follows: where the boundaries are, which side of each boundary a piece of code sits on, and why. The product was called Astra during development, and the repository, the bundle identifier com.shivvyas.astra and the production host still carry that name. Where the code and this handbook disagree, the code is right and this handbook is a bug.

1.1System context

There is one server, and it is the Next.js app deployed on Vercel. A web browser reaches it as pages and as /api/* route handlers; the iOS app reaches only the route handlers. The server talks to four outside parties: the Anthropic API for readings, Supabase for identity and every table, Apple Push Notification service for alerts, and Open-Meteo for birthplace geocoding. The Swiss Ephemeris is not an outside party. It is a WebAssembly module, loaded once per server process, that runs in the same function as the route handler that called it. Vercel Cron is the fifth caller, and it calls the same server twice a day.

Each party, how it is reached, and what proves the request is allowed:

1.2The one bet

The README states it in a sentence: "Nothing about the chart is guessed." Every other decision in the system follows from taking that literally. A language model asked for a birth chart will produce one, and it will be plausible and wrong. So the model is never asked. The chart is computed by computeChart in lib/astrology/chart.ts, which converts the local birth time to Universal Time with luxon, asks the ephemeris for a Julian day, and reads eight bodies with calc_ut. Ketu is Rahu plus 180 degrees. For the Vedic chart the ephemeris is put into sidereal mode with the Lahiri ayanamsa and houses are whole-sign from the ascendant; for the Western chart it stays tropical and houses are Placidus. Vimshottari dasha periods come from the Moon's sidereal longitude. All of this is deterministic and unit tested. 

// lib/astrology/chart.ts
// Lazily initialize the WASM module once per server process.
let swePromise: Promise<InstanceType<typeof SwissEph>> | null = null;
async function getSwe(): Promise<InstanceType<typeof SwissEph>> {
  if (!swePromise) {
    swePromise = (async () => {
      const swe = new SwissEph();
      await swe.initSwissEph();
      return swe;
    })();
  }
  return swePromise;
}

The result is stored, not recomputed per request. saveBirthProfile in lib/data/birthProfile.ts computes both traditions and writes them as one jsonb value, { vedic, western }, into birth_profiles.chart. Every reader of that column goes through ensureCurrentChart, which checks schemaVersion against CHART_SCHEMA_VERSION (currently 2) and recomputes a stale chart on read. There is no migration job for charts: a chart written under an older house system corrects itself the first time its owner opens the app, and both traditions are rewritten together so a profile is never half upgraded.

Only then does the model appear. app/api/chat/route.ts loads the stored chart, derives facts from it (lords, aspects, dignity, combustion, from lib/astrology/derived.ts), computes today's transits, and builds a system prompt in lib/astrology/prompt.ts that is entirely made of computed values. Claude reads that prompt and writes prose. The models are named in one place: 

// lib/anthropic.ts
export const READING_MODEL = "claude-sonnet-5";
export const DEEP_READING_MODEL = "claude-opus-4-8";

export const LOW_EFFORT: { readonly output_config: { readonly effort: "low" } } = {
  output_config: { effort: "low" },
};

The comment above LOW_EFFORT records a measurement on one Vedic reading of the same chart and question: 1,452 output tokens at default effort, 719 at low, 328 with thinking off, and all three cited the same real placements. Routine readings therefore run at low effort; a deep reading keeps the default and upgrades to the larger model. The point for this chapter is the direction of dependency. The prompt depends on the chart. The chart never depends on the prompt.

What the bet rules out No route ever sends a birth date to the model and asks for positions. No client ever computes a chart; the iOS app decodes the stored jsonb into NatalChart and draws it. When the phone answers a question without the network, it answers by looking a value up in that decoded chart, never by reasoning about the sky. See 1.7.

1.4Two clients, one API

The web app and the iOS app do not use the server the same way, and the difference is worth stating plainly because it decides where a feature's code lives.

The web app mostly does not call /api. Its pages are React server components that import lib/data directly and render with the result; its writes are server actions (authenticate, sendMagicLink, saveIntake, signOut) that a browser form posts to. The browser itself touches three routes: POST /api/chat from Chat.tsx, because a streaming reading needs a response body that grows; GET /api/kundli as a plain link, because it returns a PDF; and GET /api/geocode from PlaceAutocomplete.tsx as the user types a birthplace.

The iOS app has no server components and no server actions, so everything it cannot do itself goes through SancharaAPI in mobile/Sanchara/Sources/Services/SancharaAPI.swift. Its own header comment says why the API exists from the phone's point of view: it "holds everything that cannot ship in a client binary: the Anthropic key, the Swiss Ephemeris, and PDF generation." What the phone can do itself, it does directly against Supabase with the anon key and the user's session: it reads birth_profiles, conversations, messages, alerts and daily_readings over PostgREST and marks alerts and readings as read, which the RLS policies in migrations 0004 and 0005 allow.

Every route that runs the ephemeris or the model declares runtime = "nodejs", and next.config.ts lists swisseph-wasm in serverExternalPackages, keeping it external so that Next bundles the .wasm binary for the server runtime.

1.5Two auth channels

Both clients sign in with Supabase Auth, but they carry the session differently, and lib/supabase/ exists mainly to make that difference invisible to route handlers.

Web: cookies

The browser gets a session through a server action. Password sign-in, sign-up, the magic link and the confirmation resend all live in app/(auth)/actions.ts; the email links land on app/auth/callback/route.ts, which calls exchangeCodeForSession and redirects to /app. From then on the session is a set of cookies that @supabase/ssr manages, and two pieces of code keep them fresh. middleware.ts runs updateSession from lib/supabase/middleware.ts on every request that is not a static asset, a Next internal or the .well-known folder. That function calls auth.getUser(), which refreshes the cookies as a side effect, and then redirects an anonymous request for /app to /login and for /admin (other than /admin/login) to /admin/login.

lib/supabase/server.ts is the client server components and actions use. Its setAll is wrapped in a try block whose comment explains the design: a server component cannot set cookies, so the write is ignored there, and the middleware is what actually refreshes them. Reading the two files together is the fastest way to understand the web session.

iOS: a bearer token

The phone never sees a cookie. supabase-swift signs in directly, with a password, with a six-digit emailed code (signInWithOTP then verifyOTP), or with Sign in with Apple, where Supabase verifies Apple's identity token through signInWithIdToken and the nonce the app generated. The session persists in the Keychain, which Supa in Services/Supabase.swift notes is the library's default on Apple platforms. When the app calls the API it reads the current access token and puts it in an Authorization: Bearer header. 

// lib/supabase/route.ts
export async function createRouteSupabase(request: Request): Promise<Db> {
  const token = bearerTokenFrom(request);
  if (!token) return createServerSupabase();

  return createClient(env.supabaseUrl(), env.supabaseAnonKey(), {
    global: { headers: { Authorization: `Bearer ${token}` } },
    auth: { persistSession: false, autoRefreshToken: false },
  });
}

This is the seam. A route handler calls createRouteSupabase(request) and gets back a Db, which is just SupabaseClient; the comment above the type notes that both the cookie client and the bearer client are instances of it, so every function in lib/data and lib/timeline accepts either. With a bearer header the client forwards the JWT on every PostgREST call and Row Level Security evaluates as that user. Without one it falls through to the cookie client and the web is unchanged. bearerTokenFrom is small enough to be fully specified by five tests in lib/supabase/route.test.ts: it accepts a lowercase scheme, and returns null for a missing header, a non-bearer scheme, or an empty token.

Why the anon key ships in the binary

mobile/scripts/make-config.sh reads exactly two values from .env.local, NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY, and writes them into a generated, git-ignored AppConfig.swift along with the API base URL. Its header states the rule: these are "designed to ship in clients (RLS is the security boundary, not secrecy)", and the service-role and Anthropic keys "are never read here and must never reach the app binary." The anon key is safe to publish because it grants nothing by itself. Every one of the eleven tables in supabase/migrations/ has enable row level security, and every policy is keyed on auth.uid(), so an anon-key request without a valid user JWT can read no rows, and one with a JWT can read only that user's rows. The same key is in every web page's JavaScript through lib/supabase/client.ts. Nothing about the phone is special. 

-- supabase/migrations/0001_init.sql
create policy "birth self" on public.birth_profiles
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());

Admin: a third door, same key

The admin area at /admin has its own login page but not its own auth system. A user is an admin if a row for them exists in admins, a table with no insert policy and therefore no self-service path; requireAdmin in lib/admin/guard.ts checks it with the service-role client and redirects otherwise. Admin pages then read other users' transcripts with that same client, which bypasses RLS, and this is the only place a page does so.

1.6The privacy boundary

The boundary in the system-context diagram is a red dashed line between the clients and Vercel. In code it is lib/env.ts. The file begins with import "server-only", and every variable is a function, not a constant, so a missing required value throws at the moment it is used rather than at import.

The service-role client deserves its own rule, and lib/supabase/admin.ts states it in one line: "Bypasses RLS. Only ever import from server code behind an admin auth check." In practice it is imported from exactly the places that need to act as nobody in particular: the two cron modules, the admin queries, and three writes that RLS would correctly refuse. Avatar upload writes to the avatars bucket with it. Account deletion calls auth.admin.deleteUser with it, for the user id taken from the caller's own session. And device registration upserts device_tokens with it because, as the route's comment explains, a phone handed from one account to another has to change owner, and the owner-only policy would refuse that update. In each case the decision of who was made by the caller's own client first.

What crosses the boundary in the other direction is also bounded. The model receives a first name, the computed chart and derived facts, the numerology numbers, today's transits, the timeline description, and the conversation. The extraction route sends only the user's own messages, never the assistant's, and writes nothing until the user confirms; its comment calls filing an inferred death or divorce onto someone's timeline "a bad thing to be wrong about." life_events is the one table holding what a person said about their own life rather than what the ephemeris computed, and migration 0006 gives it no admin read policy for that reason.

What is not enforced The server-only marker is on fourteen files, but not on lib/supabase/server.ts or lib/data/*. They are safe today because they import next/headers or a server-only module and would fail in a client bundle anyway. A new file in lib/data that imported neither would not be caught. Add the marker when you add the file.

1.7What lives on the phone

Astrya is not a local-first app; the server holds the truth and the phone reads it. But one piece is deliberately local, and it exists because three processes on the phone need the chart and only one of them can sign in. mobile/Sanchara/Sources/Services/ChartCache.swift opens with that argument: the app, the App Intents extension Siri runs, and the widget timeline provider all need the data, and neither of the last two can hold a Supabase session or wait on a network round trip. So the app writes and the others only read. 

// mobile/Sanchara/Sources/Services/ChartCache.swift
static let appGroup = "group.com.shivvyas.astra"

private func write<T: Encodable>(_ value: T, to name: String) {
    queue.async {
        guard let data = try? JSONEncoder().encode(value) else { return }
        try? data.write(to: self.url(name), options: [.atomic, .completeFileProtection])
    }
}

The cache is four JSON files in the App Group container, chart, details, reading and period, plus one short string in the App Group's UserDefaults suite, pendingDestination, which an intent or a Control Center button writes milliseconds before the app launches and the app drains once. Writes are atomic and use complete file protection; reads and writes go through one serial queue. If the container is missing, which happens in a simulator build without provisioning, the cache falls back to the caches directory and simply stops sharing with the widget.

Two consequences follow. First, the app launches offline. ProfileStore.load reads the cached chart and details before it fetches, and if the fetch fails but both are present it sets the state to ready anyway; only a device that has never loaded a chart sees the failure screen. The chart is about 4 KB and changes only when birth details are re-saved, so a stale cache is almost never wrong. Second, the widgets never fetch. ReadingWidget asks to be rebuilt at the next six o'clock, morning or evening, because that is when a new reading can exist; PeriodWidget asks for midnight, because a mahadasha changes about once a year but the progress bar should move by a day. WidgetRefresh nudges WidgetKit when the app itself has just received a new reading or a new period meaning, and only then, because reloads are rate-limited.

The cache holds nothing secret, no token and no session, but a birth chart is personal, so AuthStore.signOut unregisters the push token, signs out, and then calls ChartCache.shared.clear(). The comment there says why: the files would otherwise outlive the session, and the widget would go on showing the previous person's chart to whoever signs in next.

On-device answers

The cached chart is also what makes OnDeviceReasoner possible. Questions that are lookups, where a planet sits, what is in the seventh house, which dasha is running, are routed to Apple's on-device model with the chart exposed as a tool, and only interpretive questions escalate to /api/chat. That is the bet from 1.2 applied on the phone: the model looks a value up in a computed table; it is never asked to produce the table.

1.8Time and the twice-daily job

vercel.json schedules /api/cron/daily twice, at 02:30 and 15:30 UTC. Vercel sends Authorization: Bearer $CRON_SECRET with each call, and the route refuses everything when the secret is unset rather than expose a job that spends model tokens to anyone who finds the path. It then runs two functions in order, runDuePredictions and runDailyAlerts, each over up to 500 profiles that have a chart, and returns both summaries as JSON. maxDuration is 300 seconds.

The route's own comment carries the design: "Both halves are decided per user rather than per run." The schedule is in UTC, but nothing about a user's reading is. Each user's timezone column, captured at intake from their birthplace, sets a local clock, and from that clock lib/alerts/slots.ts picks the slot: 

// lib/alerts/slots.ts
export const NIGHT_STARTS_AT_HOUR = 14;

export function slotForHour(localHour: number): Slot {
  return localHour < NIGHT_STARTS_AT_HOUR ? "morning" : "night";
}

/** Whether this user still needs the reading for the slot they are currently in. */
export function isSlotDue(localHour: number, alreadyWritten: Slot[]): Slot | null {
  const slot = slotForHour(localHour);
  return alreadyWritten.includes(slot) ? null : slot;
}

The stored for_date is the user's local date, so "my reading for the 26th" means their 26th. And daily_readings carries unique (user_id, for_date, slot), which migration 0005 describes as "what makes the job safe to run more often than expected, or twice by accident." writeDueReading reads the slots already written for today, returns early when the current one exists, and if two runs race past that check the insert fails with Postgres error 23505, which the code treats as "already done" rather than as an error. That is the whole idempotency argument for the readings: extra runs find nothing to do, and a race costs one wasted model call, never a duplicate row or a duplicate push.

The dosha sweep is idempotent for a different reason. runAlertsForUser recomputes today's sky at the user's birthplace with the same computeChart the chat uses, detects the conditions it forms against the natal chart, and diffs them against the open rows in transit_conditions, where a row is open while ended_on is null. What is in the new set and not the old has started; what is in the old and not the new has ended; what is in both is ignored, which is what stops a standing Sade Sati from becoming a daily nag. A partial unique index, transit_conditions_open_signature on (user_id, signature) where ended_on is null, guarantees one open row per condition however often the sweep runs. Only caution and warning severities reach a lock screen, at most six per alert, and a natal condition is never announced after a user's first sweep, because a natal condition cannot start or end and a change in one is an artifact of the computation changing. deriveHadNatalRows fails closed on a count error for exactly that reason, and its comment names the bug it prevents: pushing "Mangal Dosha has begun" to someone whose chart has not changed since birth.

Pushes go out through ApnsClient, which keeps one HTTP/2 session per environment for the life of a run and reuses a provider token for 45 minutes. A token Apple reports as unregistered is deleted from device_tokens on the spot, since Apple only says a token is dead when you use it. When APNs is not configured the readings and alerts are still written; the phone reads them from the tables and the widget from the cache, and only the notification is missing.

The cost shape Each reading's system prompt has two parts. The chart block is identical for a user on every run and is sent with a one-hour cache marker, so a morning and night reading that land within the hour share it; the today block changes daily and is not cached. The readings run on READING_MODEL at low effort. The alert copy in lib/alerts/compose.ts runs on DEEP_READING_MODEL, also at low effort.

Check yourself

Why is the anon key safe to ship in the iOS binary?

Because every table has Row Level Security with an owner-only policy, so the key grants nothing without a user's JWT and only that user's rows with one. The same key is in every web page.

How does a route handler tell a web caller from an iOS caller?

It does not need to. createRouteSupabase builds a bearer client when an Authorization: Bearer header is present and falls through to the cookie client otherwise; both are a SupabaseClient.

Name the three writes that use the service-role client on behalf of a signed-in user, and what they have in common.

Avatar upload to Storage, account deletion, and device-token registration. In each the user id comes from the caller's verified session first; the admin client only performs a write RLS would refuse.

Which files may the widget extension compile, and what do they have in common?

The six named in project.yml: Theme, ReadingCard, ChartCache, ChartData, BirthProfileDetails and OpenKundliIntent. None imports Supabase or the API client, because the extension has no session.

The cron runs at 02:30 and 15:30 UTC. Why does a user in any timezone still get a morning and a night reading?

The slot is chosen from the user's local hour (before 14:00 is morning), the date stored is their local date, and the unique index on (user_id, for_date, slot) means a run that finds the slot written does nothing.

What makes the dosha sweep safe to run twice in a day?

It diffs today's conditions against the open rows in transit_conditions; a second run finds the same set open, so nothing has started or ended, and no alert is written. The partial unique index enforces one open row per signature.

Where does a stale chart get fixed, and why is there no migration for it?

In ensureCurrentChart, on read. Both traditions are recomputed and rewritten the first time the owner uses the app after a schema change, so no backfill job has to touch every row.
