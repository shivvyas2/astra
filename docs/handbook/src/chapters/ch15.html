Chapter fifteen

15Setup, deployment, and release

One repository produces two artifacts: a Next.js app that Vercel builds from every push to main, and an iOS archive that GitHub Actions uploads to TestFlight on every version tag. Nothing secret is in git, the production build needs no secrets to compile, and every one-time step that lives outside the repo is written down so it can be done again.

This chapter describes the repository on main on 30 September 2026, at version 0.3.0. It is the chapter to read before the first npm run dev, before the first deploy to a fresh Vercel project, and before cutting a release. It covers the local setup for the web app and the iOS app, the one-time Supabase and Apple configuration, the Vercel deployment and its two cron schedules, the production checklist that exists because a cron ran for weeks refusing every request, the three GitHub workflows, the release procedure, and the rules about where secrets may live. Where a document under docs/ names an account, a project reference or a machine, this chapter does not; the procedure is the same for whoever holds the keys.

15.1The shape of a release

A commit takes two roads out of the repository. Every push to main is built by Vercel's Git integration and becomes the production web app; the same push runs .github/workflows/ci.yml, which typechecks, tests and builds the web app and builds and tests the iOS app on a simulator. A tag of the form v* takes the second road: release.yml publishes a GitHub release from the matching section of CHANGELOG.md, and ios-testflight.yml archives the iOS app with the version from the tag and uploads it to App Store Connect. There is no deploy step in Actions for the web app, and nothing in the repository makes Vercel wait for CI.

15.2Local setup

The web app

The README lists the prerequisites: Node.js 24, a Supabase project, an Anthropic API key, and for iOS, Xcode 26, XcodeGen and an Apple Developer account. The web app starts in three commands: npm install, cp .env.example .env.local with the values filled in, and npm run dev, which serves on port 3000. The migrations under supabase/migrations/ are applied to the project either with the Supabase CLI (supabase link then supabase db push) or by pasting each file into the SQL editor, lowest number first. There are seven, and the order matters because later files reference tables the earlier ones create: 

supabase/migrations/
0001_init.sql                admins, profiles, birth_profiles, conversations, messages
0002_avatar.sql              avatar_url and the avatars bucket
0003_numerology_mode.sql     the numerology chat mode
0004_alerts_push.sql         device_tokens, transit_conditions, alerts
0005_daily_readings.sql      daily_readings, one row per user, date and slot
0006_life_events.sql         life_events, life_event_scans
0007_period_readings.sql     period_readings

.env.example is the complete list of environment variables, and the comments in it are the documentation. The split between required and optional is enforced in lib/env.ts, which is the only place process.env is read: 

// lib/env.ts
import "server-only";

function required(name: string): string {
  const v = process.env[name];
  if (!v) throw new Error(`Missing required env var: ${name}`);
  return v;
}

function optional(name: string): string | undefined {
  const v = process.env[name];
  return v && v.length > 0 ? v : undefined;
}

export const env = {
  supabaseUrl: () => required("NEXT_PUBLIC_SUPABASE_URL"),
  supabaseAnonKey: () => required("NEXT_PUBLIC_SUPABASE_ANON_KEY"),
  supabaseServiceRoleKey: () => required("SUPABASE_SERVICE_ROLE_KEY"),
  anthropicApiKey: () => required("ANTHROPIC_API_KEY"),
  cronSecret: () => optional("CRON_SECRET"),
  apnsKeyId: () => optional("APNS_KEY_ID"),
  apnsTeamId: () => optional("APNS_TEAM_ID"),
  apnsBundleId: () => optional("APNS_BUNDLE_ID"),
  apnsPrivateKey: () => optional("APNS_PRIVATE_KEY")?.replace(/\\n/g, "\n"),
};

Two details of this file shape everything downstream. Every entry is a function, not a value, so a variable is read when a request needs it and never at module load or at build time. And the file imports server-only, so the bundler refuses to include it in anything that ships to a browser. Chapter 16 follows both consequences through the failure modes.

The iOS app

The Xcode project is not committed. mobile/project.yml is the XcodeGen spec, and xcodegen generate must be run after every change to it and after every new source file. Before that, mobile/scripts/make-config.sh writes mobile/Sanchara/Sources/Generated/AppConfig.swift from the repo's .env.local. The script reads exactly two variables, the Supabase URL and the anon key, and its header says why: those are publishable, and the service-role key and the Anthropic key "are never read here and must never reach the app binary." A third value, apiBaseURL, comes from the SANCHARA_API_BASE_URL shell variable if it is set and otherwise defaults to the production API, which is how a debug build is pointed at a local or preview server. 

cd mobile
./scripts/make-config.sh       # reads the Supabase URL and anon key from ../.env.local
xcodegen generate
open Sanchara.xcodeproj

project.yml declares three targets: the app, the SancharaWidgets extension and a SancharaTests unit-test bundle. It also declares every entitlement: associated domains for Universal Links, aps-environment for push, Sign in with Apple, and the App Group the widget and Siri read the chart from. Each of those needs a matching capability on the App ID in the Apple Developer portal, which is one-time work covered in the next section. The deployment target is iOS 17; the on-device model features are weak-linked behind #if canImport(FoundationModels) and gated at runtime on iOS 26, so the same build runs on both.

15.3Supabase and Apple, once

Four documents under docs/ describe configuration that lives in dashboards rather than in git. Each names the project it was written for; the steps do not depend on that. In summary:

  • Project and keys (docs/SUPABASE_SETUP.md). Create a project, copy the URL, the anon key and the service-role key into .env.local, enable the Email provider under Authentication, run the migrations, sign up in the app, then make that user an admin with one insert into public.admins using the id from the Users page. The admin area at /admin has its own login and checks this table.
  • Email codes (docs/EMAIL_OTP.md). Sign-in by email sends a six-digit code, not a link. Supabase decides which to send from the template: a template with only {{ .ConfirmationURL }} sends a link and no code, and the app's code screen then has nothing to accept. Two templates, Magic Link and Confirm signup, must include {{ .Token }}. Both keep the link as well, so the web app and the Universal Link path keep working. On the app side the flow is signInWithOTP then verifyOTP(email:token:type:), with .email for passwordless and .signup after a password sign-up.
  • Sign in with Apple (docs/APPLE_SIGN_IN.md). The app signs in natively with signInWithIdToken, so no web redirect is involved and no environment variable is needed. Two switches must be on: the Apple provider in the Supabase project, with the app's bundle identifier in its Client IDs list, and the Sign In with Apple capability on the App ID, which real devices and TestFlight need for signing. The error Issuer https://appleid.apple.com is not enabled means the first switch is off. The document also records a known gap: account deletion does not revoke the Apple token, which Apple's guideline 5.1.1(v) asks for, and lists the three steps closing it would take.
  • Push (docs/PUSH_ALERTS.md). Apply migrations 0004 and 0005, create an APNs key in the Developer portal (it downloads once), and set CRON_SECRET and the four APNS_* variables in Vercel. The document then explains the twice-daily reading and the dosha sweep, which the alerts chapter covers in full.
  • App Groups (docs/SIRI_AND_WIDGETS.md). Register the group, enable it on both the app's and the widget's App IDs, and let Xcode regenerate the profiles. Without it "the widget shows its empty state forever and Siri says there is no chart", because the two processes are reading different containers.

Finally, the auth redirect URLs. docs/DEPLOY.md has Supabase's Site URL set to the production domain and /auth/callback on that domain added to the Redirect URLs, with a wildcard pattern for preview deployments if they should authenticate too. The web app's callback route is app/auth/callback/.

Order of operations Keys first, migrations second, templates and providers third, admin last. The admin insert needs a user id, which needs a sign-up, which needs the Email provider and the templates. Everything else can be done in any order, and the push and App Group steps can be left until the iOS app needs them; the web app and the API run without them.

15.4Vercel and the cron schedules

The web app deploys from main through Vercel's Git integration. The project's environment variables are set for both Production and Preview; docs/DEPLOY.md walks through vercel link and vercel env add for the four required variables, and docs/PUSH_ALERTS.md for the five optional ones. Development is left out of the Vercel store on purpose, because local development reads .env.local. After a variable is added, the running functions do not see it until the next deployment; vercel redeploy --prod is the step people forget.

Two settings in next.config.ts matter for the deployment. serverExternalPackages: ["swisseph-wasm"] keeps the ephemeris out of the bundler so its .wasm binary is shipped intact for the server runtime. And a headers() rule serves /.well-known/apple-app-site-association as application/json, because the file has no extension and Next would otherwise serve it as an octet stream, which Apple rejects; without it Universal Links and the webcredentials association silently fail.

The schedule is the whole of vercel.json:

{
  "crons": [
    { "path": "/api/cron/daily", "schedule": "30 2 * * *" },
    { "path": "/api/cron/daily", "schedule": "30 15 * * *" }
  ]
}

02:30 and 15:30 UTC are 08:00 and 21:00 in India, which is where the first users are. The route handler at app/api/cron/daily/route.ts declares runtime = "nodejs" because the ephemeris is WebAssembly and maxDuration = 300 because it runs the model once per user per half-day. It checks Authorization: Bearer against CRON_SECRET and then runs two halves in order: runDuePredictions, the readings, then runDailyAlerts, the dosha sweep. Each user is handled on their own clock: anything before 14:00 local is the morning slot, anything after is the night slot, and the row is stored against the user's local date under a unique index. That is what makes extra runs harmless, and it is why docs/GO_LIVE_CHECKLIST.md says a mixed-timezone user base can move to an hourly schedule at no extra model cost: each hourly run writes only for users whose current slot is still missing. /api/cron/alerts still exists for running the dosha sweep on its own by hand.

15.5The production checklist

docs/GO_LIVE_CHECKLIST.md exists because of a specific failure. In mid-September 2026 production had written no daily readings for three weeks and had never sent a dosha alert. The code was deployed and the crons were firing on schedule, but CRON_SECRET was not set, so the route refused every request with a 401, and the four APNS_* variables were not set either. Two migrations the timeline feature depended on had also never been applied to the production database. None of that is visible from a green build, which is the point of the checklist. Its steps, generalised:

  1. Log the Vercel CLI into the right account and link the project. The CLI remembers one login, and vercel env against the wrong scope fails in confusing ways. vercel env ls production shows what is already set.
  2. Set the secrets. CRON_SECRET from openssl rand -hex 32, then APNS_KEY_ID, APNS_TEAM_ID, APNS_BUNDLE_ID and APNS_PRIVATE_KEY (the whole .p8, BEGIN and END lines included). Then vercel redeploy --prod.
  3. Apply any migration the deployed code expects, by hand, in order. Nothing in the pipeline applies migrations. The README says it plainly: after deploying a version that adds a migration, apply it before traffic reaches the new code. The checklist confirms with a query against information_schema.tables for the three timeline tables.
  4. Run the cron by hand. A curl with the bearer secret against /api/cron/daily returns JSON with two objects, predictions and alerts. predictions.written should be at least 1; predictions.skipped counts users whose current slot was already written, which is the normal result of a second run in the same half-day; alerts.pushConfigured says whether the APNs variables were seen. A 401 means the secret is missing or does not match. A query on daily_readings grouped by date and slot confirms today's rows.
  5. Check the push environment on each phone. The app reports sandbox or production from its signing entitlement when it registers, and the server sends to the matching APNs host. Rows in device_tokens written by builds from before that fix may carry the wrong environment; the checklist deletes them by updated_at and has each device reopen the app once.
  6. Decide the schedule. Twice a day at fixed UTC times, or hourly.
Two facts a green deployment cannot tell you Whether the environment variables the cron and the pushes need are present, and whether the database has every table the code will query. The first fails closed and silently (a 401 to a scheduled request that nobody is watching). The second fails loudly but only on the code path that reaches the missing table. Check both after every deploy that touches either.

15.6Continuous integration

.github/workflows/ci.yml runs on every push to main and every pull request, under a concurrency group keyed on the ref with cancel-in-progress, so a second push to the same branch cancels the run for the first. It has two independent jobs.

The web job

On ubuntu-latest with Node 24 and the npm cache: npm ci, then npx tsc --noEmit, then npm test (which is vitest run), then npm run build. The build step carries the comment that explains why the job needs no secrets: 

# The build needs no secrets: env vars are read at request time, not at
# build time, so a missing key fails the route rather than the build.
- name: Build
  run: npm run build

This is the consequence of env.ts exposing functions. A next build evaluates every module once to discover routes and pre-render what it can; if env.ts read process.env at the top level, the build would throw on a runner with no variables, and CI would need the production keys just to prove the code compiles. As written, the build succeeds on a bare runner and the first request to a route that needs a missing variable is the thing that fails. The tests, likewise, never need a key: every module that calls the model or the database is stubbed at the boundary, and a single alias in vitest.config.ts points server-only at the package's empty entry so route handlers and lib/env.ts can be imported in a plain Node process.

The iOS job

On macos-26, working in mobile/: select the newest Xcode 26 on the runner, brew install xcodegen, then write a placeholder .env.local and run make-config.sh. The placeholder is the trick worth knowing. The generated AppConfig.swift is never committed, and a build without it does not compile, so the job writes a .env.local containing a stand-in URL and a stand-in key, both obviously fake. The comment in the workflow says exactly what is being proved: "The simulator build only needs the values to be present, not real." No test in the iOS suite reaches the network, so nothing ever tries to use them.

Then xcodegen generate, a cache of mobile/SourcePackages keyed on the hash of project.yml (so the Supabase Swift package is fetched once per dependency change, not per run), and one xcodebuild test against the first available iPhone simulator with CODE_SIGNING_ALLOWED=NO. The output is filtered to errors, warnings in the app's own sources, and test suite lines; the full log is uploaded as an artifact only on failure. The job proves that the spec generates a project, that the app and the widget extension compile, and that the XCTest suite in mobile/Sanchara/Tests/ passes. It cannot prove signing, push, or anything that needs an entitlement, which is what the TestFlight workflow is for.

15.7The release and TestFlight workflows

release.yml

Runs on a pushed tag matching v* with contents: write. An awk program extracts the section of CHANGELOG.md whose heading is ## [X.Y.Z], stopping at the next version heading or at the link references at the foot of the file. If no section exists the workflow warns and falls back to the commit subjects since the previous tag. Then gh release create publishes the release with the tag as its title and the extracted notes as its body. If the release already exists the job exits cleanly, so re-pushing a tag is safe.

ios-testflight.yml

Runs on the same tags, or by hand from the Actions tab, under a concurrency group named testflight that does not cancel in-progress runs, because a half-finished upload is worse than a queued one. The job:

  1. Checks that all five repository secrets are set and fails with a named error for each one missing, before any Xcode work starts.
  2. Selects Xcode 26, installs XcodeGen, writes .env.local from the SUPABASE_URL and SUPABASE_ANON_KEY secrets, runs make-config.sh, and generates the project. These are the same two publishable values a developer's .env.local holds; the API base URL stays at the production default.
  3. Sets the version. On a tag, CFBundleShortVersionString in both the app's and the widget's Info.plist becomes the tag without its v; on a manual run the value in project.yml is kept. CFBundleVersion becomes the workflow run number in both, because App Store Connect requires a unique build number per version.
  4. Sets aps-environment to production in Sanchara/Sanchara.entitlements with PlistBuddy. The committed spec says development, which is right for a debug build on a phone, and wrong for TestFlight: "Push tokens minted under the development environment are rejected by production APNs, so store builds must carry the production entitlement."
  5. Writes the App Store Connect API key from ASC_KEY_P8 to ~/private_keys/AuthKey_<id>.p8 with mode 600.
  6. Archives with -allowProvisioningUpdates and the three authentication key flags. With an API key, Xcode creates or refreshes the distribution certificate and profile itself, which is why no certificate is stored in GitHub.
  7. Exports with mobile/ExportOptions.plist, whose method is app-store-connect and whose destination is upload, so the build goes straight to App Store Connect instead of producing an .ipa. Symbols are uploaded; version management is left to the workflow, not to Apple.
  8. Uploads the archive and export logs as an artifact whether or not the job succeeded.

15.8The release procedure

Releases are tagged from main. The README's "Releasing" section is four steps:

  1. Make sure CI is green.
  2. Add a section to CHANGELOG.md and bump version in package.json.
  3. Commit, then git tag -a vX.Y.Z -m "vX.Y.Z".
  4. git push origin main --tags.

The push of main deploys the web app through Vercel. The tag triggers both release workflows. Nothing else is needed, and nothing in the workflows reads package.json: the web app's version is informational, the iOS version comes from the tag, and the release notes come from the changelog. Keeping the three in step is a discipline, not an enforcement.

CHANGELOG.md follows Keep a Changelog 1.1.0 and the project uses Semantic Versioning; the file says so in its first paragraph. Each version has a heading of the form ## [0.3.0] - 2026-09-18, subsections Added, Changed and Fixed as needed, and a link reference at the foot of the file pointing at the GitHub release for that tag. The awk in release.yml depends on exactly this shape: the heading must start ## [ followed by the bare version, and the link references must be the last thing in the file. Three versions exist: 0.1.0 and 0.2.0 on 16 September 2026, and 0.3.0 on 18 September. The entries are written for the person using the app, in bold lead-ins followed by a sentence or two of plain language; the commit history is where the engineering detail lives.

Versions on the iOS side project.yml pins CFBundleShortVersionString at 1.0 and CFBundleVersion at 1 for local builds. Those are placeholders. A tagged workflow run overwrites both, and the run number guarantees each upload is distinct. A build archived by hand in Xcode would carry 1.0 (1) and would collide with any earlier hand-archived build; upload through the workflow instead.

15.9Secrets discipline

The rule in docs/DEPLOY.md is short: locally, secrets live only in .env.local; in the cloud, only in Vercel's encrypted environment store; and no real key or service-role secret is ever committed. The repository enforces the first two with .gitignore and with where values are read.

Three code-level habits back the table. First, server-only at the top of lib/env.ts, lib/supabase/admin.ts, lib/supabase/route.ts, lib/anthropic.ts, lib/push/apns.ts and every alerts module turns an accidental client import into a build error. Second, the user id in every mutating route comes from the verified session, never from the request body, so a leaked anon key still cannot act as someone else. Third, make-config.sh only knows the names of the two publishable variables; there is no code path by which a server key could be generated into the app.

What a leaked repository exposes The bundle identifier, the team id, the production hostname, the App Group name and the URL scheme. All are already visible in the shipped app. No key, no token, no project reference.

15.10Study notes

Read in this order

  1. .env.example, for every variable and the comment that explains it.
  2. lib/env.ts, for required versus optional and why each is a function.
  3. vercel.json and app/api/cron/daily/route.ts, for the schedule and the guard.
  4. .github/workflows/ci.yml, both jobs; note the two comments about secrets.
  5. .github/workflows/ios-testflight.yml, top to bottom; it is the whole iOS release.
  6. .github/workflows/release.yml, for the changelog contract.
  7. mobile/scripts/make-config.sh and mobile/project.yml, for what the app is handed and which entitlements it claims.
  8. docs/GO_LIVE_CHECKLIST.md, for the failure that motivated it.

Check yourself

Why does npm run build succeed on a CI runner with no environment variables?

Because lib/env.ts exposes functions that read process.env when called, inside a request. Nothing reads a variable at module load, so the build evaluates every module without touching one.

What does the iOS CI job write to .env.local, and why is that safe?

A placeholder URL and a placeholder key. make-config.sh refuses to run without values, the compiler needs the generated file, and no test reaches the network, so the values only need to exist.

Which two things does the TestFlight workflow change in the checked-out tree before archiving?

The version and build number in both Info.plist files, and aps-environment in the app's entitlements, from development to production.

A cron fires on schedule and nothing is written. What are the first two things to check?

That CRON_SECRET is set in the Production environment and a redeploy happened after it was added, and that every migration the code expects has been applied to the production database.

Why can the anon key ship in the iOS binary when the service-role key cannot?

Every table has Row Level Security, so the anon key can only read and write rows the signed-in user owns. The service-role key bypasses RLS entirely; it is read only in server-only modules.

What in CHANGELOG.md does release.yml depend on?

A heading of exactly ## [X.Y.Z] for the tagged version, and the link references being the last block in the file; the awk stops at either the next version heading or the first reference line.
