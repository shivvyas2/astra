Chapter eight

8The life timeline

A person's whole life as Vimshottari divides it, drawn from the stored chart, with the things that actually happened to them pinned into the periods they fell in. The server computes and explains; the phone renders. Nothing reaches the map that the user did not type or confirm.

This chapter describes the code on main on 30 September 2026, version 0.3.0. The timeline is the largest feature in the app and the only one that stores what the user says about their own life rather than what the ephemeris computes. That fact shapes nearly every decision below: why the tables are owner-only in both directions, why a scan of the chat history proposes and never writes, why an extracted moment carries the sentence it was read from, and why a date the user gave to the year is never rendered to the day.

8.1Intent

A dasha is abstract until something real sits inside it. The chart already knows that a person's Saturn period runs from 2019 to 2038; what makes that a life map rather than a table is that they moved house in 2021 and changed jobs in 2024, and both fell in the Mercury sub-period. The timeline answers "why was that year like that" against their year, not a generic one. It does four things:

  • Lays out the twelve mahadashas from birth and places every pinned moment in the mahadasha and antardasha it happened in.
  • Writes a plain-language theme and meaning for each period, for someone who has never heard the word dasha, and caches them until the moments inside a period change.
  • Fills itself in from the user's own chat messages, proposing dated moments with the quote that gave them away, each one confirmed or discarded by hand.
  • Tells the chat, so a reading about 2021 knows what 2021 held.

The idea that shaped it is in the comment at the top of app/api/timeline/scan/route.ts: "this is inferred content about someone's own life, and silently filing an AI's guess about a death or a divorce onto their timeline would be a bad thing to be wrong about." Every path onto the map goes through a confirmation the user taps.

8.3Model

The three tables

life_events holds what the user pinned. The comment in supabase/migrations/0006_life_events.sql calls it "the one table in the schema holding what the user tells us about their own life rather than what the ephemeris computes, so it is owner-only in both directions": one policy for all operations, with using and with check both on user_id = auth.uid(), and no admin read policy. 

-- supabase/migrations/0006_life_events.sql
create table public.life_events (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  occurred_on date not null,
  precision text not null default 'day' check (precision in ('day', 'month', 'year')),
  title text not null check (char_length(title) between 1 and 120),
  note text check (char_length(note) <= 2000),
  source text not null default 'manual' check (source in ('manual', 'extracted')),
  created_at timestamptz not null default now()
);
create index on public.life_events (user_id, occurred_on);

occurred_on is a date, not a timestamp, because "people remember 'March 2021', not an hour, and a false hour would imply the chart says more than it can." precision records how much of the date the user knew; a month-precision event is stored on the 1st, a year-precision one on 1 January, and the precision travels with it. source separates a typed moment from a confirmed extraction, "so a bad extraction run can be undone without touching hand-entered events."

life_event_scans is one row per user (user_id as primary key, scanned_at, found_count), so the offer to mine the chat history appears once, and again only when the user has said enough new things since.

period_readings, from 0007_period_readings.sql, holds the written meanings: one row per mahadasha plus one whose lord is the literal now, keyed on (user_id, lord, period_start). The now row's period_start is the current antardasha's start, "so it goes stale by itself when the sub-period changes." events_hash records which pinned moments the text was written against. The column checks allow 80 and 800 characters; the parser trims to 60 and 600, so the database limit is headroom, never the thing that fails.

The types

// lib/timeline/build.ts
export type Timeline = {
  birthDate: string;
  today: string;
  periods: TimelinePeriod[];
  events: TimelineEvent[];
  now: TimelineNow | null;
  /** Any period, or the now summary, needs (re)writing. */
  needsExplaining: boolean;
};

TimelinePeriod is a DashaPeriod (lord, ISO start and end, nested antardashas) plus isCurrent, isPast, eventCount, theme, meaning and stale. TimelineEvent carries the stored columns plus the two fields that are "the whole point of the feature": mahadasha and antardasha, the lords running when it happened, or null when the event sits outside the computed span. TimelineNow names the current pair and the antardasha's span. The GET route spreads a ScanState (scanned, messagesSinceScan) over the top.

On iOS the same shape is TimelinePayload, decoding into DashaBand, LifeEvent and NowPeriod. Every field that arrived after the first release decodes with decodeIfPresent and a default, "so an app update and an API deploy need not land in the same minute." CandidateEvent is the scan's proposal: an optional occurredOn, a precision that may be unknown, a title, and the evidence quote.

8.4The server side

Building the map without the ephemeris

Vimshottari needs one number: the Moon's sidereal longitude at birth. The chart stores each planet as a sign plus a degree within it, so moonLongitudeFrom reassembles signIndex * 30 + degree: "This is what lets the timeline load without re-running the Swiss Ephemeris, which costs a WASM init per process." It returns null for a chart with no Moon or an unrecognised sign, and the caller treats null as "cannot draw."

loadTimeline in load.ts reads the birth row, reassembles the Moon, fetches life_events and period_readings in parallel, and hands everything to buildTimeline. today is the UTC date: "A dasha band is years wide, so a few hours of skew cannot move an event into the wrong period, unlike the daily readings, where the local date is the whole point."

buildTimeline calls vimshottariTimeline for the raw twelve periods. Each stored event is placed in the period whose [start, end) contains occurred_on, then in the antardasha inside it, and the list is sorted oldest first. Each period gets its event count, its current and past flags, and the stored reading for its (lord, start); the now summary is looked up under NOW_LORD = "now" and the antardasha start. Then: 

// lib/timeline/build.ts
const fresh = !!row && row.events_hash === eventsHashFor(p, events);
...
const needsExplaining = periods.some((p) => p.stale) || (now !== null && now.meaning === null);

A period is stale when it has no reading or when the moments inside it changed since the reading was written. The test is the hash: 

// lib/timeline/build.ts
export function eventsHashFor(period, events): string {
  const keys = events
    .filter((e) => within(e.occurredOn, period.start, period.end))
    .map((e) => `${e.occurredOn}:${e.title.toLowerCase()}`)
    .sort();
  if (keys.length === 0) return "0";
  let h = 2166136261;
  const text = keys.join("\n");
  for (let i = 0; i < text.length; i++) {
    h ^= text.charCodeAt(i);
    h = Math.imul(h, 16777619) >>> 0;
  }
  return h.toString(16).padStart(8, "0");
}

A 32-bit FNV-1a over the sorted date:title keys. Sorting first means the order rows come back from Postgres "can never make a fresh explanation look stale." A small non-cryptographic hash is enough because "this detects change, it does not protect anything," and keeping it pure "keeps this module free of Node-only imports."

Writing the meanings

explain.ts turns the map into one model call. buildExplainSystem addresses the user by first name, tells the model to "write for someone who has never heard the word dasha and will not be told it," and sets the rules that matter on a life map: past chapters in the past tense, the current one in the present, a future one "as what it tends to bring, never as fate, and never as a warning." When the user has pinned a moment inside a chapter, "name it and say in one clause how it fits the chapter. Never invent a moment they did not give you." Jargon is banned outright: no malefic, benefic, exalted, lord, house, transit, dasha, antardasha.

buildExplainTask lists every period as LORD | START | years (state), the current period's sub-periods, and each pinned moment under its period, ending with a now line. The reply is one line per chapter, LORD | START | THEME | MEANING, plus a final line whose LORD is the word now.

parseExplanations is the safety property. It builds a map of every legitimate lord|start key from the computed periods and the now row, and keeps a line only when its key is in that map: "a hallucinated period can never appear on the map." The first line for a key wins, the theme is cut at MAX_THEME = 60, and everything after the third pipe is the meaning, "pipes and all," cut at MAX_MEANING = 600.

explainTimeline calls READING_MODEL with max_tokens: 3000, the shared LOW_EFFORT output config, and the system block marked cache_control: { type: "ephemeral", ttl: "1h" }; any error returns an empty array. POST /api/timeline/explain (maxDuration = 90) asks the model only if needsExplaining, then upserts every returned row on user_id,lord,period_start, stamping each period's events_hash and "0" for the now row, whose freshness "is the antardasha start in its key." One stale period rewrites all of them: "the extra output costs less than a second call would." The route reloads and returns the GET shape, so the client replaces its state and never merges.

Mining the history

selectTranscript decides what the model sees: the user's messages oldest first, each prefixed with the date it was written, whitespace collapsed so one message stays one line, anything under 12 characters dropped, and a hard stop at maxChars = 24_000 that ends before a message rather than through it. Oldest first is deliberate: the early "here's my situation" messages are "where most life history gets told."

buildExtractionSystem says what counts (a job, a move, a marriage or separation, a birth, a death, an illness, a business begun or closed) and what does not: never an event inferred from a question, a hypothetical, or "something you read in an astrological reading." Relative phrases resolve from the message date ("last March" in a 2025-06 message is 2024-03), ages from the birth date ("when I was 25" is the birth year plus 25), always at the precision given. An event that cannot be dated even to a year is kept with ?. The title is in the person's own framing, "'Left the job in Chicago', not 'Career upheaval under Saturn'," and the model must quote the words that told it as EVIDENCE. The reply is DATE | PRECISION | TITLE | EVIDENCE, one per line, or NONE.

parseExtractedEvents trusts none of that. Pipe-delimited lines rather than JSON, "for the reason recorded in lib/alerts/compose.ts: the model reliably breaks JSON string escaping and the whole reply is lost, where a malformed line here costs one event." The date is resolved by shape (YYYY-MM-DD, YYYY-MM, YYYY) and checked to be a real calendar day; the PRECISION field is read and discarded, because "a model that writes '2019 | day | ...' does not know the day, whatever it claims in the second field." Anything before birth or after today is dropped, duplicates are removed on lower-cased date:title (title alone for undated events), titles are cut at 120 characters and evidence at 160. Dated candidates return oldest first, then the undated ones.

POST /api/timeline/scan (maxDuration = 120) reads only the user's own messages, at most MAX_MESSAGES = 400: "Assistant turns are full of astrological narrative that reads like biography and would extract as fiction." Section 8.6 walks through the rest.

Pinning

POST /api/life-events takes { events: [...] }, at most MAX_BATCH = 50, "one confirmation sheet's worth"; a manual add is the same call with one element. The date must match YYYY-MM-DD, must not be before the birth date ("That date is before you were born.") or after today ("The timeline only holds what has happened."), and the title must be non-empty, cut at 120; the note is cut at 2000. Precision falls back to day and source to manual. Dates are checked here as well as in the extractor "because this route is reachable directly, and an event before someone was born would render as a period that does not exist." DELETE filters on both the id and the caller's user_id, belt and braces over RLS.

The block the chat sees

describeTimelineForPrompt renders the timeline as text, or returns "" so the caller can append it unconditionally. In Vedic mode it opens with a Now: line naming the current period and sub-period, then lists up to MAX_MOMENTS = 30 moments, most recent first, each with the pair it fell in. Western readings have no dashas, so they get the moments alone, and nothing at all when there are none. app/api/chat/route.ts appends it to stableSystem in the chart branch (Vedic and Western) inside a try/catch that logs "chat timeline context skipped" and carries on. It lives in the cached block because "it only changes when they pin or remove a moment."

8.5The clients

The web app has no timeline screen. Everything below is the iOS feature, reached from the chat toolbar as a sheet (ChatView presents TimelineView()) and from a tap on the period widget, which opens sanchara://timeline and lands as DeepLink.Destination.timeline.

The store

TimelineStore is an @Observable, main-actor class with four states: loading, ready, needsProfile, failed(String). load() calls SancharaAPI.timeline(), applies the payload, and then, if needsExplaining, spawns explain() as a separate task, so the bands are on screen before the meanings exist. A failure there is silent, because "the timeline without meanings is still the timeline." A server reply containing "birth details" maps to needsProfile. 

// mobile/Sanchara/Sources/Features/Timeline/TimelineStore.swift
static let rescanThreshold = 10
var canOfferScan: Bool { !scanned || messagesSinceScan >= Self.rescanThreshold }
var isRescan: Bool { scanned }

Never scanned: offer. Scanned, and at least ten user messages since: offer again with different copy. scan() sets scanned = true and messagesSinceScan = 0 locally on success, so the offer disappears even when nothing was found. confirm resolves the chosen candidates through CandidateResolver, posts them as one batch, clears the list and reloads. add is the same with one event. remove is optimistic: the row disappears under the finger, the delete is sent, and the reload restores it if the delete failed.

What is cached

Every applied payload also writes ChartCache.CachedPeriod: the current lord, the running antardasha and its span, the period's theme and the now row's meaning, then calls WidgetRefresh.reloadPeriod(). TimelineStore.warmCache() does the same fetch without a screen, and ChatView runs it once per launch so "the widget fills in without the timeline ever being opened." The widget, the shared PeriodProgress helper and the App Group file are chapter 10's; the timeline is the one writer of that file's period entry.

The views

TimelineView is titled "Your life." Bands are laid out "in information proportion, not time proportion: a period is as tall as what happened in it. A 20-year mahadasha with nothing pinned should not dwarf the year the user got married." Time is carried by the year range and the "N years" caption. From the top: the scan offer when canOfferScan; the NowCard when there is a now; one BandRow per period; a footer naming the technique and offering "What are these periods?"

NowCard is "the one place the meaning of now is spelled out": the pair, the years, a progress capsule, and the now meaning, or "Writing what this means for you..." while isExplaining. BandRow shows the lord, a NOW pill on the current period, the years, the theme, and the moment count; expanding reveals the meaning and the sub-periods. A stale meaning is shown at 60 percent opacity, "dimmed, and about to be replaced." Future periods sit at 45 percent because they "recede rather than disappear." Each EventRow shows the title, the date at the precision given, the "during" label naming the pair, and a Remove item behind a confirmation dialog.

AddMomentView asks for a title, a date bounded from birth to today, a segmented precision ("That day", "That month", "That year") and an optional note, and on save snaps the date to the precision so the server "stores a real date either way; this keeps it from implying a day the user never gave." PeriodExplainerView is five static paragraphs, "static on purpose," so the page explaining the idea can "be trusted the way a caption is trusted."

CandidatesView is where proposals become moments, and its doc comment is the policy: "Nothing reaches the timeline without passing through here. These are inferred claims about someone's own life, a wrong one is not a wrong prediction, it is the app telling a person something untrue about their father's death, so every candidate is opt-in rather than opt-out." Each row shows the title, its date or "When was this?", and the evidence quote in italics. Dated candidates arrive pre-ticked ("the work of confirming a good list should be one tap, not twelve"); undated ones show a year menu from the birth year to this year instead. The add button is live only when CandidateResolver.canAdd says so: something is chosen and every chosen undated candidate has a year.

TimelineDate pins every formatter to UTC, because "parsing in the device's zone would slide a morning event onto the previous day west of Greenwich," and LifeEvent.dateLabel picks a day, month or year formatter by precision "so a year-precision memory never claims a day it does not have."

8.6How it works

Opening the timeline

  1. TimelineView.task calls store.load(), which calls GET /api/timeline. The route loads the timeline and the scan state in parallel; a missing chart or an unreadable Moon answers 400 with "Complete your birth details first."
  2. The store applies the payload, writes the period cache, and shows the bands. If needsExplaining it starts explain() in the background.
  3. On appear, if there is no now card the scroll jumps to the current band: "'where am I now' is the question people arrive with."

Writing meanings

  1. explain() calls POST /api/timeline/explain. The route checks needsExplaining itself, so a needless call costs two reads and no model call.
  2. explainTimeline runs; parseExplanations keeps only lines naming a real period or the now row; the rows are upserted with their hashes.
  3. The route returns the GET shape, the store applies it, and the card that said "Writing what this means for you..." shows the now meaning.

Because the now row is keyed on the antardasha start, the day a sub-period turns over the lookup finds no row, now.meaning is null, needsExplaining is true, and the next open rewrites the map with a fresh now line. No cron and no expiry column; the key is the expiry.

Pinning a moment by hand

  1. The plus button opens AddMomentView, bounded to the birth date and today the store already holds.
  2. Save snaps the date to the chosen precision and posts one NewLifeEvent with source: "manual"; the route validates against the birth row again and inserts.
  3. The store reloads. The new moment sits in its band; that band's hash no longer matches its reading, so it is stale, needsExplaining is true, and the reload's explain() rewrites every meaning, this time naming the moment.

The scan

Following the numbered arrows in the figure:

  1. The offer's button calls store.scan(), with a 120-second timeout on the phone and maxDuration = 120 on the server.
  2. The route loads the birth row; without one it answers 400.
  3. It selects the user's conversation ids, then their own messages, oldest first, at most 400. No conversations short-circuits: the scan is recorded with found_count = 0 and an empty list returns.
  4. selectTranscript trims to 24,000 characters; extractLifeEvents sends them at max_tokens: 2000. An empty transcript returns before any call.
  5. The model replies with pipe-delimited lines or NONE.
  6. parseExtractedEvents validates, deduplicates, trims and orders.
  7. The route drops any candidate whose lower-cased occurred_on:title is already pinned. An undated candidate "has no date to match on, so a pinned moment with the same name is taken to be the same moment."
  8. recordScan upserts life_event_scans on user_id; an error here is logged, not raised.
  9. The candidates come back with nothing written to life_events; the store's non-empty list presents CandidatesView.
  10. The user unticks what is wrong, picks a year for anything undated, and taps add. confirm posts the batch with source: "extracted" to /api/life-events and reloads.

What makes the scan idempotent

Pressing the button twice, or a week later, cannot damage the map, for four reasons that stack. The scan route never inserts into life_events; its only write is the one-row-per-user upsert into life_event_scans, which overwrites rather than accumulates. The parser deduplicates within a reply. The route filters against what is already pinned, so "a re-scan after more chatting proposes only what is genuinely new." And the store clears its candidate list after a confirmation or a cancel, so a stale sheet cannot be re-submitted. The one thing not guarded is a user who confirms the same candidate in two separate sheets: life_events has no unique constraint, and the next scan would suppress the candidate, not the duplicate row. That is the user's own action on their own data, and Remove is one long press away.

The chat sees the timeline

On every chat turn in a chart mode the route calls loadTimeline and appends describeTimelineForPrompt to stableSystem. That block is part of the cached prefix, so "why was 2021 so hard" is answered against a prompt that lists what the user pinned in 2021 and which pair it fell in. When a moment is pinned or removed the block changes and the cache misses once; until then it is free. A failure to load is logged and the turn proceeds without it.

8.7Performance and cost

  • No ephemeris on the read path. moonLongitudeFrom reassembles the Moon from the stored chart, so GET /api/timeline is two parallel Postgres reads plus arithmetic. The WASM engine is never initialised for the timeline.
  • One model call per rewrite, not per period. Twelve periods and the now line come from a single max_tokens: 3000 call at low effort, with the system prompt cached for an hour. Rewrites happen only when the hash or the now key changes; opening the timeline ten times a day with nothing new makes zero model calls.
  • The scan is bounded three ways. 400 messages from the database, 24,000 characters to the model, 2,000 output tokens back, and only user turns, which are the shorter half of any transcript.
  • The chat pays two reads per turn. loadTimeline runs on every chart turn to build the block, which costs input tokens only when it changes.
  • The phone caches one thing. The period entry for the widget. The map itself is a few kilobytes, fetched on every open, always current.
  • Long timeouts where earned. Explain and scan carry a 120-second client timeout and 90- and 120-second maxDuration on the server; both run longer than a chat turn.

Check yourself

Why can the timeline load without the Swiss Ephemeris when every other chart feature needs it?

Vimshottari needs only the Moon's sidereal longitude at birth, and the stored chart carries the Moon's sign and degree. moonLongitudeFrom reassembles signIndex * 30 + degree, which saves a WASM init per process.

How does the "where you are now" meaning expire when the sub-period changes, with no expiry column?

Its row is keyed on the antardasha start. When the sub-period turns over the lookup uses a new start, finds no row, and needsExplaining becomes true.

Why are the events sorted before hashing?

Postgres does not promise an order, and a different order would give a different hash for the same moments, making a fresh reading look stale and costing a needless model call.

Why does the scan route never write to life_events?

The candidates are an inference about someone's own life, and a wrong one about a death or a divorce would be filed as fact. Every candidate passes through CandidatesView, and only the user's confirmation calls /api/life-events.

Why is the PRECISION field read and then discarded?

The date's own shape is the evidence. A model that writes a year and claims day precision does not know the day; trusting the shape keeps the map from drawing a marker it cannot justify.
