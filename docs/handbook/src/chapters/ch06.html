Chapter six

6Chat

One question in, one reading out, streamed as plain text while it is written. The server owns the prompt, the model and the transcript; the two clients own nothing but the optimistic bubble and the conversation id they were handed in a response header.

6.1Intent

Chat is the product. Every other feature either feeds it (intake computes the chart it reads from, the timeline gives it the user's life) or is a scheduled version of it (the morning and night readings). A conversation is a sequence of turns in one mode, Vedic, Western or numerology, and the mode is fixed per conversation because it decides which chart, and which system prompt, the whole transcript was read from. A user can hold many conversations; the web lists them in a sidebar, iOS in a sheet, and either client can reopen one and continue it.

This chapter describes the code on main on 30 September 2026, version 0.3.0. The prompt builders, the model settings, the cache breakpoints and the history budget that the route applies are chapter 3; this chapter takes them as given and follows one turn from a tap to a stored row. The iOS files that answer some questions on the phone without a server call, OnDeviceReasoner, OnDeviceSuggestions and ChartFacts, live in the same folder as the chat feature but belong to chapter 10; here they appear only where ChatStore hands a question to them.

The two clients share no code and are written in two languages, but they are the same program: the iOS store's doc comment says it mirrors components/Chat.tsx, the intro prompt is one string copied verbatim, and the mode dot colours in ChatModels.swift are the hex values from the web component. 6.3Model

Two tables

-- supabase/migrations/0001_init.sql
create table public.conversations (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  tradition text not null check (tradition in ('vedic','western')),
  title text,
  created_at timestamptz not null default now()
);
create index on public.conversations (user_id, created_at desc);

create table public.messages (
  id uuid primary key default gen_random_uuid(),
  conversation_id uuid not null references public.conversations(id) on delete cascade,
  role text not null check (role in ('user','assistant')),
  content text not null,
  created_at timestamptz not null default now()
);
create index on public.messages (conversation_id, created_at);

A conversation is an owner, a mode and a title; a message is a role and a body. There is no updated_at, no token count, no model name and no deep flag on either row. The transcript is the only thing stored, which is what lets any client, and the timeline's moment extraction, read it back without knowing how it was produced. Migration 0003_numerology_mode.sql drops and re-adds the tradition check so it accepts 'numerology'; the column is still called tradition although the TypeScript type that fills it is ChatMode. The two indexes are exactly the two queries: a user's conversations newest first, and a conversation's messages oldest first.

Row Level Security is owner-only on both. "conv self" checks user_id = auth.uid() for every operation. "msg self" has no owner column to check, so it joins: a message is visible or writable only if a conversation row with that id and the caller's user_id exists. Deleting a user cascades to their conversations and from there to their messages, which is what the account deletion route relies on.

The wire shape

The request body is four fields, typed inline in the route: conversationId (optional; absent starts a new conversation), tradition (a ChatMode), message and deep (optional). The response is text/plain; charset=utf-8, the model's text deltas concatenated with no framing, plus two headers: x-conversation-id, which is the id to send back on the next turn, and cache-control: no-store. There is no SSE, no JSON envelope and no final event; the stream closing is the end of the reading. Both clients read the header first and the bytes second.

The client-side types

On the web the transcript is Msg[], a role and a content string. On iOS it is [ChatMessage], which adds two things: a UUID identity assigned at creation, so SwiftUI keeps a row in place while its content grows during streaming, and a Source of .server or .onDevice. The doc comment on Source is worth reading in full: the source is shown in the transcript, not merely tracked, because the two behave differently in ways a person can feel, and an on-device answer is not saved with the rest of the reading. Conversation and StoredMessage are Decodable views of the two tables, read straight from Supabase; Conversation.mode maps an unknown tradition string to .vedic rather than failing to decode.

6.4The server side

The route, in order

app/api/chat/route.ts exports one POST and declares runtime = "nodejs", because the ephemeris is a WebAssembly module loaded from disk and the streaming SDK wants a full Node runtime. The handler runs in two phases: a preparation phase inside one try, where any failure returns a status and a sentence, and a streaming phase after the response has already begun, where a failure can only be written into the stream.

  1. Auth. createRouteSupabase(request) returns a bearer client if the request carries Authorization: Bearer, otherwise the cookie client. auth.getUser() with no user is a 401 with the body Unauthorized.
  2. Validation. An empty or whitespace message is a 400 Empty message; a tradition outside vedic, western, numerology is a 400 Invalid mode.
  3. The profile. One select on birth_profiles (RLS returns only the caller's row, so maybeSingle() with no filter is correct). A database error is a 500; a row with no chart is a 400 No chart. Complete intake first.; and ensureCurrentChart recomputes and rewrites a chart whose schema version is behind or which lacks derived facts, so an old profile gets the current prompt without the user doing anything.
  4. Today. Luxon renders the date in profile.timezone, and describeToday coarsens it to a part of day.
  5. The prompt. Numerology builds buildNumerologySystem plus a today block carrying the personal year and month. The two chart modes pick profile.chart[tradition], compute factsFor (undefined for Western), fetch the day's transit chart and describe it against the natal chart inside a try that degrades to no transit text, build buildChartSystem, append the timeline inside another try that logs and moves on, and build the today block with the deep-dependent word limit.
  6. The conversation. getOrCreateConversation either verifies the given id belongs to this user or inserts a row with the message's first 80 characters as its title.
  7. History. getMessages then selectHistory; the last retained turn gets the cache breakpoint; the new message is pushed on the end; and the new user message is written to messages before the model is called.

Anything thrown in those seven steps is caught once, logged as chat pre-stream error, and answered with a 500 whose body is a sentence a client can show. The "Conversation not found" thrown for a foreign id surfaces this way, as a 500 rather than a 403 or 404; the clients treat any non-2xx the same, so the distinction is not lost on anyone.

The stream

// app/api/chat/route.ts
const stream = new ReadableStream({
  async start(controller) {
    let full = "";
    try {
      const s = anthropic().messages.stream({ /* model, thinking, effort, system, messages */ });
      for await (const event of s) {
        if (event.type === "content_block_delta" && event.delta.type === "text_delta") {
          full += event.delta.text;
          controller.enqueue(encoder.encode(event.delta.text));
        }
      }
      const usage = (await s.finalMessage()).usage;
      console.log(`chat usage conv=${conversationId} model=${model} ...`);
    } catch (err) {
      console.error("chat stream error", err);
      controller.enqueue(encoder.encode("\n\n[The stars are momentarily clouded. Please try again.]"));
    } finally {
      if (full.trim()) await appendMessage(conversationId, "assistant", full, supabase);
      controller.close();
    }
  },
});

Only text_delta events are forwarded. Thinking blocks, which both models produce under adaptive thinking, are consumed and never sent, so the client sees the reading and not the reasoning. The accumulator full holds exactly what was streamed, and the finally stores it as the assistant turn only if it is non-blank. Two consequences follow. If the model fails before producing anything, the user turn is stored, the apology line goes down the wire, and no assistant row is written, so the next turn's history ends on a user message and selectHistory passes it through. If the model fails part-way, the partial text is stored and the apology is not, because the apology is enqueued to the client but never appended to full. A conversation therefore never contains the bracketed error text.

The data helpers

lib/data/chat.ts is four functions, each taking an optional db?: Db and building the cookie client when none is given. getOrCreateConversation is the only one with logic: given an id it selects it with both id and user_id filters and throws if nothing comes back, defence in depth on top of RLS, per its comment; without one it inserts and returns the new id. appendMessage is one insert. getMessages selects role, content and time for one conversation, ascending. listConversations selects id, tradition, title and time for the caller, descending, with no user filter because RLS supplies it.

6.5The clients

Web: the page

app/(app)/app/chat/page.tsx is a server component. It loads the birth profile and redirects to /app/intake when there is no chart, so the composer can never be shown to someone the route would reject. It reads ?c= from the search params. With an id it loads that conversation's messages and renders Chat with key={c}, the stored messages, and the conversation's own tradition as the initial mode (falling back to Vedic if the row is not in the list). Without one it renders Chat with key="new" and autostart set only when the user has no conversations at all. The key is what makes switching between readings in the sidebar remount the component rather than mutate it. The surrounding app/(app)/layout.tsx calls listConversations and hands the result to AppShell, whose sidebar links each one as /app/chat?c=<id>.

Web: the component

components/Chat.tsx is a client component holding the mode, the deep flag, the messages, the input and a busy flag in state, and the conversation id in a ref, because it changes during a fetch and must not trigger a render. send(textArg, silent) is the whole feature: append the user bubble (unless silent) and an empty assistant bubble, post the body, take the id from the header, then loop on res.body.getReader() with a TextDecoder in streaming mode and append each chunk to the last message. A non-OK response, a missing body or a thrown fetch all replace the last bubble with "Something went wrong. Please try again." In finally, busy clears and, if this was the first turn of a new conversation, router.refresh() re-runs the layout so the sidebar shows the new reading.

The composer is one input and three buttons: a mode pill that cycles Vedic, Western, Numerology; a Deep toggle, hidden below the sm breakpoint; and send, disabled while busy or while the input is blank. Enter sends. Under it is the one line of copy that appears in the same words on iOS: "For guidance and reflection. Not a substitute for professional advice." The empty state shows a greeting with the first name and the composer centred; once there is a message, the transcript scrolls above and the composer pins to the bottom with a safe-area inset. An assistant message renders through ReactMarkdown with remark-gfm inside the prose-reading styles; while it is still empty it shows "Reading your chart…" with a shimmer, and while it is still growing it shows a caret. An effect scrolls to the bottom on every change to messages.

iOS: the store

ChatStore is @Observable and @MainActor. Its state matches the web component's field for field (messages, input, mode, deep, a streaming flag, an error string, the conversation id) and adds the list of past conversations, a streamTask so a turn can be cancelled, and a chart whose didSet builds an OnDeviceReasoner. send(text, silent:, forceServer:) appends the bubbles, then in a task does one thing the web does not: if the turn is not silent, not forced to the server and the mode is Vedic, it asks the reasoner to route the question, and if the answer comes back .answered, writes it into the assistant bubble with source .onDevice and stops. The comment says why only Vedic: the router reads a Vedic chart, so a Western or numerology question has nothing local to answer from. Everything else goes to SancharaAPI.chatStream, and the loop over its events either records the conversation id or appends text.

The other entry points are short. start() loads the conversation list and, for a brand-new account with nothing to show, sends the intro prompt silently; the web does the same through autostart. newReading() cancels any stream and clears the transcript without touching the server, since the previous reading is already stored. open(conversation) cancels, adopts the conversation's id and mode, and reads its messages straight from the messages table through Supa.client. loadConversations() reads the conversations table the same way and keeps the last known list on failure rather than raising an error. expandLastAnswer() removes an on-device answer and resends the same question with forceServer, so a misrouted lookup costs one tap.

iOS: the views

ChatView is mounted by RootView with the ProfileStore, and owns the store plus the alerts, daily readings and suggestion engines that share its toolbar. Its body is the web layout in SwiftUI: an opening screen with the greeting and the composer when the transcript is empty, otherwise a ScrollViewReader transcript, the suggestion chips, and the composer. Three .task modifiers run on appear: one hands profile.chart to the store and calls start(); one loads the inbox and, only now that the user has a chart, asks for push permission; one warms the timeline cache for the widget. The composer is a vertical-axis TextField of one to four lines, the mode pill, the Deep pill and an arrow button disabled while streaming or blank, followed by the same disclaimer line. An assistant row is ShimmerText while empty, then MarkdownText with a StreamingCaret on the last row while streaming, and, when the source is on-device, a footer that says so and offers "Ask for a full reading". All three motion views take an active flag that is false under Reduce Motion.

The toolbar carries history (a clock), the wordmark, new reading, the inbox bell with an unread dot, and an avatar menu. HistoryView is a sheet listing chat.conversations with title, mode dot and time; tapping one calls open and dismisses; New calls newReading. Deep links and push taps are handled here too: an .ask(question) destination, which is how a question Siri declined arrives, starts a new reading and sends with forceServer.

MarkdownText exists because AttributedString(markdown:) handles inline syntax but collapses block structure. It splits the text into headings, paragraphs, bullets (with the ordinal kept for numbered items) and rules, gives each the spacing the web's CSS gives it, and parses only the inline runs with Foundation. A parse failure falls back to the plain text.

iOS: the API call

SancharaAPI.chatStream returns an AsyncThrowingStream<ChatEvent, Error>. The request is built by the shared request(_:method:), which asks Supa.accessToken() for the current session token and throws .unauthorized without one, so a signed-out client never reaches the network. The body is a ChatRequest with the same four fields as the web, and the timeout is 120 seconds because, as the comment says, readings can think for a while before the first byte. It uses URLSession.shared.bytes(for:). A non-2xx status reads the whole body as the error sentence (401 becomes .unauthorized); a 2xx yields .conversationId from the header, then bytes.

The byte loop handles the two problems a raw text stream has. A chunk boundary can split a multi-byte character, so bytes accumulate in undecoded until they decode as UTF-8. And a redraw per byte would repaint the transcript thousands of times for one reading, so decoded text is batched and yielded at 24 characters, with the remainder flushed at the end. onTermination cancels the task, which is how newReading() stops a reading in flight.

What is cached on the device

For chat, nothing durable. The transcript and the conversation list live in the store's memory and are re-read from Supabase on open. The chart the store hands to the reasoner comes from ProfileStore, which is the same chart ChartCache keeps in the App Group for Siri and the widget; that cache is described in chapter 10. An on-device answer is never written anywhere.

6.6How it works

A new conversation

The client sends no conversationId. The route inserts a conversation titled with the first 80 characters of the message, stores the user turn, and starts a stream whose history is that one turn. The response header carries the new id; the web stores it in the ref and iOS in conversationId, and both send it on every later turn. When the stream ends the web calls router.refresh() and iOS calls loadConversations(), so the new reading appears in the list. On this first turn the whole prefix is a cache write; the route's comment notes that a first turn is short enough that missing the cache costs little.

A later turn

The client sends the id. The route verifies ownership, loads every stored message, trims to the budget, marks the last retained turn as the cache breakpoint, appends and stores the new message, and streams. The mode is whatever the client sends; the row's tradition is not consulted and not updated. Both clients keep the mode with the conversation (the web page passes the row's tradition as the initial mode; iOS's open sets mode = conversation.mode), but nothing on the server prevents a client from continuing a Vedic conversation in numerology, and the stored transcript would then be a mix.

Reopening a past reading

The web reopens through the URL: the sidebar link sets ?c=, the page loads the messages on the server and renders them as initialMessages, and the new key remounts the component. iOS reopens through ChatStore.open, which reads the messages table directly with the Supabase client under RLS, no route involved. Both then continue with the later-turn flow above.

The intro reading

A brand-new account opens on a reading rather than an empty room. When the user has no conversations, the web mounts with autostart and iOS's start() finds an empty list, and each sends the same string silently: "Welcome me with a short reading for today based on my chart. Two or three short sections." Silent means the prompt itself is not shown as a user bubble, because, as the iOS comment puts it, the question is scaffolding the user never asked. It is stored, though: the route sees an ordinary message and writes it to messages, so reopening that conversation later shows the scaffolding line. On iOS a silent turn also bypasses the on-device router.

Deep

The toggle sends deep: true. The route switches to DEEP_READING_MODEL, keeps the default thinking effort, raises the length rule to 320 words and the ceiling to 3,000 tokens. Nothing about the conversation records that a turn was deep, and the next turn can be standard.

6.7Performance and cost

  • Every reading is billed on the server, and the mechanics are chapter 3: two cache breakpoints, low effort on standard readings, a 6,000 character history budget and a length rule. The measured mid-conversation turn is about $0.008 on Sonnet 5.
  • Two profile reads per turn, not more. The route selects birth_profiles once and, only when the timeline is loaded, loadTimeline reads what it needs. The transit chart is memoised per day and neighbourhood, so the ephemeris runs once per city per day rather than once per message.
  • Whole history loaded, then trimmed in memory. getMessages has no limit clause; every turn loads every message of the conversation and selectHistory discards most of it. On a conversation of hundreds of turns this is a larger read than it needs to be, though the index on (conversation_id, created_at) makes it cheap. A limit is the obvious improvement and has not been needed.
  • Time to first byte is thinking time. With adaptive thinking on, the model reasons before the first text_delta. Both clients show a shimmer rather than nothing, and iOS sets a 120 second request timeout for it.
  • Redraw cost is bounded on iOS. The 24 character batch in chatStream is the difference between a few hundred transcript updates per reading and several thousand. The web appends per network chunk, which the browser already coalesces.
  • The cheapest turn is one the phone answers. A Vedic lookup on a device with Apple Intelligence never posts at all. See chapter 10 for what qualifies.
  • The intro reading costs a turn per new account, and it is a first turn, so it is also the one that writes the cache rather than reading it.

Tests

The chat feature is covered by the tests of the modules it is built from, not by a test of the route or the views. There is no app/api/chat/route.test.ts, and no Swift test constructs a ChatStore or calls chatStream. What does exist:

  • lib/astrology/prompt.test.ts: everything the route puts in the system blocks, listed in section 3.7. For chat the load-bearing cases are that the stable half carries no date, sky or length rule, and that a Western chart gets Placidus houses and no Vedic technique.
  • lib/data/history.test.ts: the five budget rules, including that a window never begins on an assistant turn, which is what keeps a conversation whose last model call failed valid on the next turn.
  • lib/data/injection.test.ts: appendMessage writes { conversation_id, role, content } through the injected client and never builds the cookie client when one is given. This is the test that stands between an iOS turn and a silent RLS failure.
  • app/smoke.test.ts: the app layout module imports and exports a function. It proves the Next.js scaffold loads under Vitest and nothing more.
  • Swift: SuggestionTests, OnDeviceRoutingTests and ChartFactsTests exercise the three on-device files in the Chat folder. They belong to chapter 10; none touches the transcript, the store or the stream.
What is not pinned The two behaviours in the stream's finally, that a failed first turn stores no assistant row and that a partial reading is stored without the apology, are read from the code and not from a test. The same is true of the 24 character batch and the UTF-8 hold-back in chatStream. They are the first things to cover if the route or the client ever changes shape.

Check yourself

Why is the user message stored before the model is called rather than after, alongside the reply?

So that a failed model call still leaves the question in the transcript. The assistant row is written in finally only if text arrived, and selectHistory tolerates a history that ends on a user turn.

Why does the response carry the conversation id in a header rather than in the body?

The body is the reading, streamed as bare text with no framing. A header arrives before the first byte and does not need parsing out of the stream; both clients read it first and then loop on bytes.

The iOS app reads conversations and messages directly. Why is that safe?

Both tables are owner-only under RLS, and the Supabase client carries the user's session, so the read can only ever return that user's rows. Writes still go through the route, which is the only code that builds a prompt.

What happens to the intro reading's prompt text?

It is hidden in the client (silent) but stored on the server as an ordinary user message, so a reopened first conversation shows it.

Why does Chat take a key from the page?

Switching readings must remount the component so its state (messages, mode, the id in the ref) starts from the new conversation rather than carrying the old one's ref forward.

Why does the route forward only text_delta events?

Adaptive thinking produces thinking blocks first. The client should see the reading, not the reasoning, and the stored assistant turn should be what the user saw.
