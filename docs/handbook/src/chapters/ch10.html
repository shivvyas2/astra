Chapter ten

10On-device answers, Siri, and widgets

A birth chart is fixed at birth and about four kilobytes. Once the phone holds a copy, the questions that are lookups ("where is my Saturn", "what is in my seventh", "which dasha am I in") can be answered by the phone itself, out loud through Siri, on the Home Screen, or in the chat, with no session, no network and no paid call. One cache in an App Group makes all three surfaces possible.

This chapter describes the code on main on 30 September 2026, version 0.3.0. ChartCache writes the chart, the birth details, the latest daily reading and the current dasha period into the App Group container after every successful load in the app. The widget extension and the App Intents only ever read from it. On top of the cache sit Apple's on-device model, which restates the chart when a question is a retrieval and hands everything else to Claude, and a small deep-link protocol that lets a process with no UI tell the app where to land.

10.1Intent

A large share of what people ask Sanchara is not interpretation. The doc comment at the top of mobile/Sanchara/Sources/Features/Chat/OnDeviceReasoner.swift puts it plainly: every one of those questions "was a paid Claude call answering from a chart the phone could have read itself". The same split runs through Siri. Positions and periods are records, so an intent answers them instantly and for nothing. Readings are written by Claude, so an intent can hand back one already written but never commissions a new one: a voice phrase should not silently spend money or take thirty seconds. The widgets follow the rule in its strictest form. They never fetch. A widget that waits on a network call is a widget that shows a placeholder at exactly the moment someone glanced at it.

10.3Model

What the cache holds

// mobile/Sanchara/Sources/Services/ChartCache.swift
final class ChartCache: @unchecked Sendable {
    static let shared = ChartCache()
    static let appGroup = "group.com.shivvyas.astra"

    private let queue = DispatchQueue(label: "com.shivvyas.astra.chartcache")
    private let directory: URL

    private init() {
        let shared = FileManager.default.containerURL(
            forSecurityApplicationGroupIdentifier: Self.appGroup
        )
        // Without the entitlement (a simulator build with no provisioning, say)
        // the app still works, it just stops sharing with the widget.
        directory = shared ?? URL.cachesDirectory
        try? FileManager.default.createDirectory(at: directory, withIntermediateDirectories: true)
    }

    private func write<T: Encodable>(_ value: T, to name: String) {
        queue.async {
            guard let data = try? JSONEncoder().encode(value) else { return }
            try? data.write(to: self.url(name), options: [.atomic, .completeFileProtection])
        }
    }

    private func read<T: Decodable>(_ type: T.Type, from name: String) -> T? {
        queue.sync {
            guard let data = try? Data(contentsOf: url(name)) else { return nil }
            return try? JSONDecoder().decode(type, from: data)
        }
    }
}

Four JSON files live in the group container, each behind a save-and-load pair. Writes are asynchronous on one serial queue and reads are synchronous on the same queue, so a read issued after a write sees the write. Every file is written atomically with complete file protection. Nothing secret goes in: no token, no session. Those stay in the Keychain, where supabase-swift already keeps them.

CachedReading.isFresh is true when savedAt is today or within the last 86,400 seconds: "A widget should not keep insisting on yesterday's morning reading." CachedPeriod carries what the chart alone cannot, the server's one-line theme for the mahadasha and the nowMeaning, which only /api/timeline writes. A fifth value is not a file. pendingDestination is one short string in UserDefaults(suiteName: appGroup), because it is written from the widget extension milliseconds before the app launches and the suite gives both processes the same store without coordination. takePendingDestination() reads and clears in one step, so a destination is never handled twice. clear() removes all four files and the key, and runs on sign-out.

The chart the phone reasons over

NatalChart in mobile/Sanchara/Sources/Features/Kundli/ChartData.swift mirrors lib/astrology/types.ts: ascendant, nine ChartPlanet rows (name, sign, degree, house, retrograde, nakshatra), Moon and Sun signs, ayanamsa, an optional DashaInfo and an optional DerivedFacts. The derived block mirrors lib/astrology/derived.ts: per planet the houses it rules, its dignity, combustion and distance from the Sun, aspects and conjunctions; per house its lord and where that lord sits; per running dasha level the lord's placement. The top-level block is optional for the reason the type's comment gives: "A widget or a Siri intent must never fail to decode a chart it has already stored." Doshas are deliberately not carried into the app's type; they are interpretive, and the on-device model is only allowed to restate records.

The two entities

SancharaEntities.swift defines the only two things Siri, Shortcuts and Spotlight may know about. DailyReadingEntity is what a reading intent returns and what Spotlight indexes; its attributeSet puts the body in contentDescription so a half-remembered phrase finds the reading again. PlacementEntity is one body's position built from a ChartPlanet, with the Sanskrit sign from Rashi(english:), and a spoken sentence: "Saturn is in Meena, Pisces, at 3°15', in house 5, nakshatra Uttara Bhadrapada. It is retrograde." The file's comment sets the boundary: "Nothing interpretive is an entity. A prediction is not a record and should not be searchable as though it were one."

10.4The server side

There is none. No route handler, table or cron job exists for the widget, for Siri or for the on-device model. Everything they read was put in the cache by the app from three sources that belong to other chapters: the birth_profiles.chart jsonb column, read directly through supabase-swift under the owner-only RLS policy (roughly 4 KB, changing only when birth details are re-saved); the daily_readings table, read the same way; and GET /api/timeline, whose payload carries the period bands with their themes and the now meaning. The on-device model is Apple's, not Sanchara's: FoundationModels is a system framework, no weights ship in the bundle, and no request leaves the phone. Where the model declines or is absent, the question goes to /api/chat exactly as it did before the feature existed.

10.5The clients

Filling the cache

Three stores write, each at the moment its data is confirmed. ProfileStore.load() first seeds chart and details from the cache so the kundli draws immediately, then fetches and saves both on success; if the fetch fails and the cache had both, the state is still .ready. DailyStore.load() saves the newest of 60 readings and calls WidgetRefresh.reload(). TimelineStore.cache(_:) finds the band marked isCurrent, picks the antardasha whose range contains payload.today, saves a CachedPeriod and calls WidgetRefresh.reloadPeriod(). Because the period file is only written when a timeline arrives, ChatView calls TimelineStore.warmCache() once per launch, so the period widget fills in without the timeline screen ever being opened. WidgetRefresh is two static calls to WidgetCenter.shared.reloadTimelines(ofKind:), for "SancharaReading" and "SancharaPeriod", and its comment carries the discipline: reloads are rate-limited by the system, "so this is called when a reading actually changes, never on every load."

ChartFacts: the chart as a reference table

ChartFacts turns positions into sentences and does nothing else. It has no dependency on FoundationModels, which is what makes it testable on any machine. The wording is the load-bearing part. Apple's on-device model refuses anything it reads as fortune telling, a result found by testing against the real model, so every row uses a neutral vocabulary and never names a tradition, a practice or a meaning:

Four lookups exist. body(named:) returns one planet's row and demands at least two characters, because hasPrefix("") is true of every row and an empty argument from the model "would otherwise come back as whichever body happened to be first, a wrong answer delivered with complete confidence". section(_:) lists everything filed under one house, names its controller when derived facts exist, and says "No entries are filed under it." when nothing is. currentPeriod() renders both dasha levels with their date ranges and, from the derived block, where the running lord is filed. header() is the three lines every answer is indexed by, and everything() joins them all. Two helpers are shared beyond the file: sectionNumber(in:) finds a house number written as "seventh", "house 7", "7th house" or a bare "12th", and only accepts 1 to 12; calendarDay(_:format:) parses and formats a yyyy-MM-dd string in UTC, because formatting a bare ISO date anywhere west of Greenwich hands back the day before, "the kind of wrong that nobody reports and everybody notices."

OnDeviceReasoner: the router

// mobile/Sanchara/Sources/Features/Chat/OnDeviceReasoner.swift
func route(_ question: String) async -> Route {
    #if canImport(FoundationModels)
    if #available(iOS 26.0, *), Self.isAvailable {
        // A question that names no part of the table cannot be a lookup, so
        // the cheap check runs before the model does.
        guard Self.mentionsTheTable(question) else { return .escalate }
        guard await isLookup(question) else { return .escalate }
        if let answer = await answer(question) { return .answered(answer) }
    }
    #endif
    return .escalate
}

Three gates, cheapest first. mentionsTheTable is a string scan with no model call: true if the question contains one of the nine body names, a house number sectionNumber(in:) can find, or one of a short list of period and derived words ("dasha", "mahadasha", "antardasha", "period", "lagna", "ascendant", "rising", "nakshatra", "moon sign", "sun sign", "rashi", "lord", "ruler", "rules", "exalted", "debilitated", "combust"). The comment records two words tried and dropped, "aspect" and "strength": every question they usefully caught already routed via a body name or an ordinal, so they added only false positives such as "what aspects of my life".

isLookup is the first model call. It opens a LanguageModelSession on SystemLanguageModel(guardrails: .permissiveContentTransformations) with the instruction "You sort incoming questions into two buckets. You never answer them." and asks for a @Generable struct, Classification, whose single field is isRetrieval: Bool. Constrained decoding means the answer is always one of two values, never prose to be parsed; sampling is greedy. Any thrown error, a refusal included, returns false, and the question goes to Claude, "which is where it went before".

answer is the second model call, and it uses a tool rather than a stuffed prompt. TableLookupTool is registered as lookupTableEntry with four optional arguments: body (constrained to the nine names by .anyOf), section (constrained to 1...12), currentPeriod and wholeTable. The instructions tell the model to call the tool before answering, report only what it returned, say the table does not record something when the tool returns nothing, never explain what an entry means, and answer in two or three plain sentences. Generation runs at temperature 0.3 with at most 220 response tokens. Every tool result is prefixed with the header, because "which section is that" is the follow-up to almost every row. 

// mobile/Sanchara/Sources/Features/Chat/OnDeviceReasoner.swift
let text = response.content.trimmingCharacters(in: .whitespacesAndNewlines)
// An answer that never consulted the table is a guess. Drop it.
guard !text.isEmpty, tool.wasCalled else { return nil }
return text

wasCalled is a flag behind an NSLock, written on whatever executor the framework calls the tool from and read on the main actor afterwards. An answer composed without a single lookup is thrown away rather than shown.

Where the chat meets the router

if !silent, !forceServer, mode == .vedic, let reasoner {

        return
    }
}

ChatStore.chart has a didSet that builds the reasoner, and its comment limits the scope: "Vedic only: the router reads a Vedic chart, so a Western or numerology question has nothing local to answer from and goes straight to Claude." A locally answered turn is marked ChatMessage.Source.onDevice and is never saved to the conversation. ChatView renders it with a footer, "Read from your chart on this device", and under the last one a button, "Ask for a full reading", which calls expandLastAnswer(): the local answer is removed and the same question re-sent with forceServer: true. The disclosure and the escape hatch are both required; if the router guesses wrong, one tap undoes it.

OnDeviceSuggestions: what to ask next

SuggestionEngine owns the chips under a reading. ChatView calls refresh(after:mode:) whenever streaming stops with a non-empty assistant turn. On a device where SystemLanguageModel.default.availability == .available, the engine sends the last 1,200 characters of the reading (the tail carries the conclusion) to a session instructed "You rewrite and summarise text. You never add facts of your own, and you never answer the questions you raise." and asks for a @Generable FollowUpQuestions: three first-person questions the passage leaves unanswered, trimmed, capped at 90 characters, cut to three. The prompt never mentions astrology: asked to act as an astrologer's assistant the model refuses outright; asked to list what a passage leaves unanswered, it answers well. Everywhere else, and whenever generation throws, starters(for:) supplies three written questions per ChatMode, so the feature degrades rather than disappears. onDeviceStatus turns the availability enum into a sentence for the profile screen, and OnDeviceReasoner.isAvailable reads the same flag.

DeepLink and the sanchara:// scheme

// mobile/Sanchara/Sources/Intents/DeepLink.swift
func drain() {
    guard let raw = ChartCache.shared.takePendingDestination() else { return }
    if raw == "kundli" {
        pending = .kundli
    } else if raw == "timeline" {
        pending = .timeline
    } else if raw.hasPrefix("ask:") {
        let question = String(raw.dropFirst("ask:".count))
        if !question.isEmpty { pending = .ask(question) }
    }
}

Intents run without a UI, sometimes in a different process, so none of them can present anything. They write a destination into the App Group and the app drains it when it next comes to the front, mirroring PushStore.pending on purpose: "one habit, two sources." A widget tap is the other way in. PeriodWidgetView sets .widgetURL(URL(string: "sanchara://timeline")), the scheme is declared under CFBundleURLTypes in mobile/project.yml, and RootView.onOpenURL hands a URL whose scheme is sanchara to DeepLink.shared.handle(url:) and everything else to the auth store, which would otherwise report an expired link. handle(url:) accepts the hosts timeline and kundli and ignores unknown paths rather than guessing. ChatView consumes the destination on onAppear (a cold launch sets it before the view exists), on scenePhase == .active (which calls drain()), and on onChange(of: DeepLink.shared.pending). .kundli and .timeline present the matching sheet; .ask starts a new reading and sends the question with forceServer: true.

The widget extension

// mobile/SancharaWidgets/ReadingWidget.swift
/// The next 6am or 6pm. Asking to refresh twice a day, rather than every
/// fifteen minutes, is what keeps the widget inside its energy budget while
/// still being right whenever anyone looks.
static func nextBoundary() -> Date {
    let calendar = Calendar.current
    let now = Date()
    for hour in [6, 18] {
        if let candidate = calendar.date(bySettingHour: hour, minute: 0, second: 0, of: now),
           candidate > now {
            return candidate
        }
    }
    let tomorrow = calendar.date(byAdding: .day, value: 1, to: now) ?? now.addingTimeInterval(86_400)
    return calendar.date(bySettingHour: 6, minute: 0, second: 0, of: tomorrow)
        ?? now.addingTimeInterval(43_200)
}

SancharaWidgets is the @main WidgetBundle in ReadingControl.swift. It vends ReadingWidget, PeriodWidget and, on iOS 18, ReadingControl. Both widgets use a StaticConfiguration and a provider whose timeline holds exactly one entry. ReadingWidget (kind SancharaReading; small, medium and accessoryRectangular) reads loadReading() and rebuilds at the next 06:00 or 18:00, the cadence of the content. The Home Screen families draw the shared ReadingCard with a body limit of 3 lines on small and 5 on medium; the Lock Screen family draws two lines of its own because the Lock Screen tints everything to one colour. The empty state names the next action: "Open Sanchara to get your first reading."

PeriodWidget (kind SancharaPeriod; the same three families plus accessoryInline) prefers loadPeriod() and, failing that, the dasha pair inside the cached chart with no theme, "shown without a theme rather than as an empty state, the dates are true". It computes today as a UTC calendar day, the API's convention, and derives the bar and the "N years left" caption from PeriodProgress.fraction and yearsRemaining in ChartData.swift, which lives there "because the period widget needs it too, and this file is one of the few compiled into both targets". The timeline rebuilds after the next local midnight so the bar moves by a day when a day has passed. ReadingControl is a ControlWidget of kind SancharaReadingControl: one ControlWidgetButton whose action is OpenKundliIntent(), labelled "Kundli", displayed as "Open kundli". The type and kind keep "Reading" in their names and the file's leading comment still describes the reading; what the button does today is open the kundli, from the extension's own process.

10.6How it works

A question in the chat

  1. ChatStore.send appends the user turn and an empty assistant turn, then, when the preconditions hold, awaits reasoner.route(text).
  2. mentionsTheTable rejects "should I take the job" without a model call. "Where is my Saturn" passes on the body name; "who rules my 7th" passes on the ordinal and on "rules". isLookup then escalates "what does my Saturn mean" as not a retrieval.
  3. answer opens a session with TableLookupTool. The model calls lookupTableEntry(body: "Saturn"), receives the header and Saturn's row, and restates them in two or three sentences.
  4. The assistant turn is filled and marked .onDevice; isStreaming goes false; SuggestionEngine.refresh runs on the answer like any other reading. Nothing was sent anywhere. If any gate fails, SancharaAPI.chatStream streams the reading from /api/chat and the turn is saved server-side.

A Siri phrase

  1. "Where is my Saturn in Sanchara" matches the ChartPositionIntent shortcut. iOS resolves the spoken parameter through PlacementQuery.entities(matching:), which matches the lowercased string against the planet name or Sanskrit sign of each placement in ChartCache.shared.load(). perform() returns the entity and its sentence; the app is not opened.
  2. "Ask Sanchara about my chart" runs AskSancharaIntent, which reads the chart from the cache and runs the same three gates. On .escalate it writes "ask:" + question to pendingDestination and says the question is saved. The next time ChatView becomes active, drain() turns it into .ask(question) and the view sends it with forceServer: true.
  3. "What's my reading in Sanchara" runs TodaysReadingIntent. A fresh cached reading answers with no query; a stale one triggers a ten-row fetch that also rewrites the cache.

A widget refresh, a tap, and sign-out

  1. DailyStore.load() writes reading.json and calls WidgetRefresh.reload(). WidgetKit, within its rate limit, asks ReadingProvider.getTimeline for a new timeline; the provider reads the cache synchronously and returns one entry with a .after(nextBoundary()) policy. With the app closed, the night cron job's reading reaches the widget only after the app, or an intent's fetch, has rewritten the cache.
  2. A tap on the period widget opens sanchara://timeline; RootView recognises the scheme and handle(url:) sets pending = .timeline directly, with no App Group hop. A tap on the Control Center button runs OpenKundliIntent inside the extension, which writes "kundli" to the group's UserDefaults; openAppWhenRun = true brings the app forward, and ChatView presents the kundli sheet on onAppear or on becoming active.
  3. AuthStore.signOut() unregisters the push token, signs out of Supabase, then calls ChartCache.shared.clear(), because the cached files "are on disk in the app group, and the widget would go on showing them to whoever signs in next." The next widget rebuild draws the empty state.

10.7Performance and cost

  • Zero network on every read path. Widgets, entity queries and IntentData.chart() read a JSON file from disk synchronously. The only intent that can touch the network is a reading intent with a stale cache, capped at ten rows.
  • Model calls are gated by a string scan. The two on-device sessions run only for questions that name a body, a house or a period word, so an interpretive question costs nothing locally and goes straight to the server.
  • Every on-device answer is a Claude call not made, and it is never written to messages on the server, so there is no storage cost either.
  • Two widget rebuilds a day, plus one after midnight. Explicit reloads are sent only when a cache file actually changed.
  • Bounded generation. The lookup answer is capped at 220 tokens at temperature 0.3; the classifier is greedy and returns one Boolean; the suggestion prompt sees at most 1,200 characters.
  • No extension bloat. The widget binary compiles six app files and no package. Keeping the Supabase client out is what keeps its launch inside WidgetKit's budget.

All in mobile/Sanchara/Tests, all runnable on the simulator, none needing Apple Intelligence. The model itself is not tested: it cannot be on a machine without Apple Intelligence, and its answers are not deterministic. What is tested is everything that decides whether it runs.

  • OnDeviceRoutingTests: the cheap filter admits "where is my saturn", "what's in house 12", "what is my lagna" and the derived vocabulary ("which planet rules my chart", "is anything combust"), and rejects "should I take the job", "when will I get married" and the two dropped words. sectionNumber reads "7th house", "house 12", "my fourth house" and "the 1st", and rejects "my 40th birthday". A body row carries sign, degree, section, segment and retrograde; lookups are case-insensitive; "Pluto" and "" return nil; an empty section says so; the period row names both lords and "1 April 2032". testNothingHandedToTheModelNamesAstrology sweeps everything() for fourteen forbidden words including "house", "planet", "dasha" and "nakshatra". If the framing slips, the feature stops answering silently, and this is the test that notices.
  • ChartFactsTests: with a derived block, a body row says "Controls sections 7, 12", "Strength rating: highest" and "Linked to sections 1"; a combust Mars 4.6 degrees from the Sun renders "Within 5 degrees of Sun" and "Filed alongside Jupiter"; a section row names its controller; the period row names where the running lord is filed. Without a derived block every row still renders and the "controlled by" and "filed in section" sentences stay silent. A second forbidden-word sweep covers every row builder.
  • DerivedFactsTests: a chart JSON with no derived key decodes with it nil; one with the block decodes the planet, house and dasha values in place; an undeclared conditions key does not fail the decode; a DerivedPeriod with no placement decodes to nil.
  • SuggestionTests: every mode has three non-empty starters; where the model is unavailable refresh falls straight back to them with isThinking false; onDeviceStatus is never empty; where the model reports itself available, refresh settles within a minute on at most three usable questions.
  • PeriodProgressTests: testCachedPeriodSurvivesTheRoundTrip writes a CachedPeriod through the real cache and reads it back equal; testClearRemovesTheCachedPeriod proves clear() removes it.
A gate no test can run docs/SIRI_AND_WIDGETS.md section 6 describes a manual check against the real model on a device with Apple Intelligence on: six lookup questions, each of which must be answered on device, not refused, and restated rather than interpreted. As of this version the document marks its status as not yet run. The vocabulary in ChartFacts was arrived at by testing, and the table has grown since; the guardrail can trip back into "May contain sensitive content" on wording no unit test can see.

Check yourself

Why does the widget never fetch, even when its cache is a day old?

A widget that waits on the network shows a placeholder at the moment someone looks. The app and the intents refresh the cache; the widget only reads, and asks to be rebuilt at the next 06:00 or 18:00.

Which intent opens the app, and why is it the only one compiled into the widget extension?

OpenKundliIntent. A diagram is the answer and Siri cannot show one. The Control Center button runs it from the extension's process, so it must be compiled there, and it must import nothing but ChartCache.

Why does the on-device table say "section" and "segment" instead of "house" and "nakshatra"?

Apple's on-device model refuses anything it reads as fortune telling. Framed as a reference table of positions it answers; testNothingHandedToTheModelNamesAstrology pins the wording.

What happens to an on-device answer that never called lookupTableEntry?

It is discarded. wasCalled is false, answer returns nil, and the question escalates to Claude. An answer composed from memory is a guess.

Why is pendingDestination in UserDefaults rather than a JSON file like the rest of the cache?

It is one short string written from the extension milliseconds before the app launches; the shared suite gives both processes the same store with no coordination, and takePendingDestination reads and clears it in one step.

Why does a Siri question that needs interpretation get queued instead of answered?

Answering would mean a thin restatement or a paid call the person did not ask for and a wait Siri will not sit through. The question is written as ask: and the app sends it to Claude with forceServer on next launch.

Why must NatalChart.derived be optional?

A chart cached in the App Group before derived facts shipped has no derived key, and the widget and intent processes cannot report a decode failure; a required field would turn an old cache into a blank widget.
