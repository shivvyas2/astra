Chapter twelve

12The landing page and the web shell

Four colours on :root, one photograph of a planet, and a sidebar that lists past readings. Everything a person sees before and around a reading is in this chapter, and the native app copies its tokens from the same stylesheet so that a screen on the phone and a page in the browser read as one product.

This chapter describes the web surface of Sanchara as it is on main on 30 September 2026, version 0.3.0. It covers the root layout, the marketing page at /, the signed-in shell under /app, the auth form, the two build-time configuration files that shape the whole site, and, for comparison, the iOS design system that translates the site's tokens into SwiftUI. The chapters before this one each own a feature; this one owns the frame the features sit in.

12.1Intent

The web app has two audiences and one theme. A stranger arriving at / should understand in one screen that the astrology is computed, not guessed, and be one tap from an account. A signed-in person should never see the marketing again: / sends them straight to /app, where the shell shows their readings, a button to start another, and a link to their profile. Both audiences see the same dark cosmic theme, because there is only one. The site has no light mode, and the iOS app is pinned dark in its Info.plist for the same reason: a reading card that turned white inside Siri while the app stayed black would look like someone else's product.

Three decisions shaped the code. The theme is four CSS custom properties and nothing else, so it can be copied by hand into Swift and checked by a test. The landing page's animation is loaded on the client only, after the HTML has arrived, so the first paint is a photograph and never a blank canvas. And the shell is the only client component in the signed-in frame; every page inside it is a server component that reads Supabase directly and hands props down.

12.3Model

The theme is four numbers

/* app/globals.css */
@import "tailwindcss";

:root {
  --bg: #0a0a0b;
  --fg: #f4f1ea;
  --muted: #9a978f;
  --accent: #e8663d;
}

@theme inline {
  --color-bg: var(--bg);
  --color-fg: var(--fg);
  --color-muted: var(--muted);
  --color-accent: var(--accent);
  --font-display: ui-sans-serif, system-ui, sans-serif;
}

Near-black, warm off-white, a grey with the same warmth, and one orange. The @theme inline block is how Tailwind 4 learns about them: it turns each --color-* variable into a utility family, so bg-bg, text-fg, text-muted and bg-accent exist without a configuration file. There is no tailwind.config.* in the repo. postcss.config.mjs is one line, registering @tailwindcss/postcss, and everything else about the theme is CSS.

The rest of globals.css is small and each rule carries its reason. html, body set the background and foreground from the tokens and overflow-x: hidden with max-width: 100%, because a landing page with a headline wider than a phone otherwise scrolls sideways. Form controls get max-width: 100%; min-width: 0, with the comment that iOS date and time inputs have a large intrinsic width that otherwise overflows the screen. Below 768 pixels every input is forced to 16px, because iOS Safari zooms the page when a smaller control takes focus. Then the animations: fade-up, fade-in, glow-pulse, heartbeat, blink and shimmer, exposed as .animate-* classes with three delay steps of 0.08, 0.16 and 0.24 seconds. .prose-reading styles the Markdown that the chat renders (chapter 6). A prefers-reduced-motion block turns off fade-up, fade-in and glow; the heartbeat, shimmer and caret animations are not in that block and keep running.

The Swift copy

// mobile/Sanchara/Sources/Design/Theme.swift
enum Theme {
    /// `--bg: #0a0a0b`
    static let bg = Color(hex: 0x0A0A0B)
    /// `--fg: #f4f1ea`
    static let fg = Color(hex: 0xF4F1EA)
    /// `--muted: #9a978f`
    static let muted = Color(hex: 0x9A978F)
    /// `--accent: #e8663d`
    static let accent = Color(hex: 0xE8663D)

    /// Tailwind `border-white/10`, used for every hairline on the site.
    static let hairline = Color.white.opacity(0.10)
    /// Tailwind `bg-white/[0.04]`, the fill behind form controls.
    static let fieldFill = Color.white.opacity(0.04)
    /// Tailwind `rounded-lg` is 0.5rem.
    static let cornerRadius: CGFloat = 8
    static let chartLine = Color.white.opacity(0.22)
    /// The site's easing: `cubic-bezier(0.22, 1, 0.36, 1)`.
    static let ease = Animation.timingCurve(0.22, 1, 0.36, 1, duration: 0.6)
}

The file's own header says it is "translated verbatim from app/globals.css", and the doc comment above each token quotes the CSS line it copies. The Color(hex:) initialiser exists so a token can be written the way it appears in CSS, as a 24-bit literal in sRGB. Two things are added that the CSS never names as tokens: the hairline and the field fill are Tailwind opacity utilities on the site (border-white/10, bg-white/[0.04]), and Swift has to give them a name. chartLine is heavier than the hairline, at 0.22 white, and the comment explains why: the kundli square "all but vanished on an OLED screen in daylight" at 0.10. Text.eyebrow() reproduces the site's eyebrow style (text-xs uppercase tracking-[0.3em] text-muted) as 12 points with 3.6 points of tracking, which is 0.3em at that size.

12.4The server side

The root layout

// app/layout.tsx
export const metadata: Metadata = {
  title: "Sanchara: Your chart, read by the stars",
  description: "Sign up, share your birth details, and chat with an astrologer powered by your real birth chart.",
};

export const viewport = {
  width: "device-width",
  initialScale: 1,
};

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body className="min-h-screen antialiased">{children}</body>
    </html>
  );
}

That is the whole file, plus the import "./globals.css" above it. It is a server component with no data access; the title and description are the only metadata the site declares, and no page overrides them. The viewport export is what keeps iOS from rendering the site at a desktop width and shrinking it.

The landing route

// app/page.tsx
export default async function Landing() {
  const supabase = await createServerSupabase();
  const { data: { user } } = await supabase.auth.getUser();
  if (user) redirect("/app");
  return <CosmicLanding />;
}

/ is a server component that does one thing before rendering: it asks Supabase who the visitor is, using the cookie client from lib/supabase/server.ts. A signed-in visitor is redirected on the server and never receives the landing HTML. Everyone else receives <CosmicLanding />, which is a client component, so the server's contribution to the page is the root layout and whatever the client component's fallback renders on the server (12.5).

The middleware

middleware.ts runs updateSession from lib/supabase/middleware.ts on every request except static assets, images, the favicon and .well-known/. It creates a server client over the request cookies, calls getUser() so the session cookie is refreshed, and then applies one rule: a request to a path starting with /app, or with /admin other than /admin/login, with no user is redirected to /login or /admin/login. This is why none of the pages under (app) check for a session themselves. They check for a birth profile, which is a different question, and one the middleware cannot answer.

The signed-in layout and home

// app/(app)/layout.tsx
export const dynamic = "force-dynamic";

export default async function AppLayout({ children }: { children: React.ReactNode }) {
  const conversations = await listConversations();
  return <AppShell conversations={conversations as never}>{children}</AppShell>;
}

force-dynamic tells Next never to cache any page under this layout; every request renders fresh, which is right for a frame whose sidebar lists the person's own conversations. listConversations (in lib/data/chat.ts) selects id, tradition, title, created_at ordered newest first, with no user filter in the query: Row Level Security supplies it (chapter 13). The as never cast is there because the query returns loosely typed rows and the shell declares a stricter Conv type; it is a cast, not a validation, and if a column were renamed the shell would receive undefined rather than an error.

The home at app/(app)/app/page.tsx calls getBirthProfile() and branches on the result. With no profile it shows "Let's build your chart" and a button to /app/intake in the foreground colour. With a profile it shows the avatar if there is one, "Hello," followed by the first name, an accent-coloured "Start a reading" button to /app/chat, and a plain link to /api/kundli that downloads the PDF (chapter 7). The avatar is a plain <img>, with an ESLint disable comment above it, because it is a public Supabase Storage URL and next/image would need the host allow-listed. Behind both states sits Glow, a blurred radial gradient from a violet at 22% opacity through the accent at 6% to transparent. The same gradient string appears in app/(auth)/layout.tsx and app/(app)/app/intake/page.tsx; it is copied, not shared.

The two configuration files

// next.config.ts
const nextConfig: NextConfig = {
  // swisseph-wasm ships a .wasm binary; keep it external so Next bundles it for the server runtime.
  serverExternalPackages: ["swisseph-wasm"],

  async headers() {
    return [
      {
        source: "/.well-known/apple-app-site-association",
        headers: [{ key: "content-type", value: "application/json" }],
      },
    ];
  },
};

Two settings, each for a different chapter. serverExternalPackages keeps the Swiss Ephemeris package out of the bundler so its .wasm file is loaded from node_modules at run time (chapter 2). The header fixes a platform quirk: Apple requires the app-site-association file to be served as JSON, the file has no extension, and Next would otherwise serve it as application/octet-stream. That file is what lets iOS open universal links in the app (chapter 14). The middleware matcher excludes .well-known/ so the session code never runs for it.

12.5The clients

The landing, in two client components

// components/marketing/CosmicLanding.tsx
"use client";
import dynamic from "next/dynamic";

const CosmicHero = dynamic(() => import("./CosmicHero"), {
  ssr: false,
  loading: () => (
    <div className="min-h-[100svh] bg-cover bg-center" style={{ backgroundImage: "url(/images/planet-sun.jpg)" }} />
  ),
});

export function CosmicLanding() {
  return <CosmicHero />;
}

CosmicLanding exists only to do this import. ssr: false means the server never renders CosmicHero; the HTML for / contains the loading element, a full-height div with the planet photograph as its background, and nothing else. The browser downloads the hero's chunk, which carries GSAP and its ScrollTrigger plugin, and swaps it in. The design intent in the file's comment is that "nothing looks blank" while that happens, and the photograph does that job.

CosmicHero is data plus one effect. The data is a HERO constant (eyebrow "Computed astrology, never guessed", title "SANCHARA", one line of copy, two links: "Get your reading" to /signup and "Log in" to /login) and three SECTIONS ("THE SCIENCE", "YOUR CHART", "YOUR FUTURE"), the last with a "Create your free account" button. The hero section is min-h-[100svh] with the planet photograph as a CSS background; each dark section is another full viewport in bg-bg. The title is split into one <span class="ch"> per character and starts with visibility: hidden as an inline style, so the letters are not seen before they animate. 

// components/marketing/CosmicHero.tsx
useEffect(() => {
  const reduce = window.matchMedia?.("(prefers-reduced-motion: reduce)").matches;
  if (reduce) {
    if (titleRef.current) titleRef.current.style.visibility = "visible";
    return;
  }
  gsap.registerPlugin(ScrollTrigger);
  const ctx = gsap.context(() => {
    if (titleRef.current) {
      gsap.set(titleRef.current, { visibility: "visible" });
      gsap.from(titleRef.current.querySelectorAll(".ch"), {
        y: 120, opacity: 0, duration: 1.1, stagger: 0.05, ease: "power4.out",
      });
    }
    gsap.utils.toArray<HTMLElement>(".reveal").forEach((el) => {
      gsap.from(el.children, {
        y: 60, opacity: 0, duration: 1, stagger: 0.12, ease: "power3.out",
        scrollTrigger: { trigger: el, start: "top 78%" },
      });
    });
  }, root);
  return () => ctx.revert();
}, []);

The effect reads the reduced-motion preference first and, if set, makes the title visible and does nothing else: no plugin registration, no tweens, no scroll listeners. Otherwise the eight letters rise 120 pixels over 1.1 seconds with a 50 millisecond stagger, and each .reveal block's children rise 60 pixels when the block's top crosses 78% of the viewport height. Everything is created inside gsap.context scoped to the root element, so the cleanup is one call to ctx.revert() when the component unmounts. No three.js scene is created anywhere; the "cosmic" in the name is the photograph and the black sections.

The shell

AppShell is the one client component in the signed-in frame, and it is a client component for three reasons only: it holds the open state of the mobile drawer, it reads the ?c= search parameter to highlight the active conversation, and it reads the pathname to highlight Profile. It receives the conversation list as a prop and fetches nothing.

The navigation column is built once as nav and placed twice. On a medium screen and up it is a 256 pixel aside with a hairline right border. Below that it is hidden, a header with a hamburger button (labelled "Open menu" for assistive technology) appears, and tapping it renders a fixed overlay: a 60% black backdrop that closes on click, and a drawer 288 pixels wide, capped at 82% of the screen. Every link in the column closes the drawer on click, so navigating on a phone never leaves it open over the new page. The column holds the brand link to /app, a "New reading" link to /app/chat, a Profile link, the "Past readings" list, and a sign-out form whose action is the signOut server action imported from app/(auth)/actions.ts. A conversation is highlighted when its id matches ?c= and the pathname is exactly /app/chat; a conversation with no title is shown as "Reading". The outer frame is h-dvh with overflow-hidden, and <main> is min-h-0 flex-1, which is what lets the chat transcript scroll inside the frame instead of the page scrolling under the sidebar.

The auth form

// components/AuthForm.tsx (props)
{
  title: string;
  subtitle?: string;
  primaryLabel: string;
  primaryAction: (fd: FormData) => void;
  magicAction?: (fd: FormData) => void;
  footer: React.ReactNode;
  error?: string;
  notice?: string;
}

AuthForm has no "use client" directive and no state. It is a server component rendering one form with an email field, a password field, a primary button with formAction={primaryAction} and, when magicAction is given, a second button "Email me a magic link instead" with its own formAction. Two buttons in one form, each bound to a different server action, is how a single email field serves both a password sign-in and a magic link without any client JavaScript. /login and /signup both render it with the same authenticate action; only the title and subtitle differ, because the action itself decides whether to sign in or sign up (chapter 4). Errors arrive as ?error= in the URL and are printed in the accent colour above the form; ?sent=1 prints the magic-link notice in muted text. The inputs use the same recipe as every field on the site: bg-white/[0.04], border-white/10, rounded-lg, and the border turns accent on focus.

The iOS design system

The Swift files under mobile/Sanchara/Sources/Design/ are the same recipe written for SwiftUI. SancharaField is the input: 16 point text, 12 by 14 points of padding, Theme.fieldFill behind it, a Theme.hairline stroke, and an 8 point radius. Its doc comment notes that the web forces 16 pixels on phones so Safari does not zoom, that native has no such bug, and that "the size is the look". SancharaPrimaryButton is bg-fg text-bg rounded-lg: foreground fill, background-coloured text, full width, a spinner in place of the label while loading and disabled while it shows. SancharaSecondaryButton is the outlined button with white at 0.15 for its stroke and muted 14 point text. SancharaSecureField adds an eye toggle the web form does not have, with the comment that choosing a password you cannot see "is the most common reason a sign-up attempt fails twice".

ReadingCard is the one component shared by the Siri snippet and the Home Screen widget (chapter 10): an eyebrow at 10 points with 2 points of tracking, a serif headline in Theme.fg, and body text at 13 points in Theme.muted with a line limit that defaults to 6 because "widgets get less room than a Siri snippet does". It sets its own colours rather than reading the environment, and its header comment gives the reason this chapter opened with: the app is dark-only by design, UIUserInterfaceStyle: Dark in Info.plist and in mobile/project.yml, and a card that went light inside Siri would read as a different product. Its accessibility label concatenates the three strings so VoiceOver reads the card as one element.

12.6How it works

An anonymous visit to /

  1. The middleware runs. There is no session cookie, the path is not under /app or /admin, so the request passes through.
  2. app/page.tsx renders on the server, calls getUser(), finds nobody, and returns <CosmicLanding />.
  3. The HTML that leaves the server is the root layout around the loading fallback: a full-viewport div showing planet-sun.jpg. No headline, no links.
  4. The browser hydrates, requests the CosmicHero chunk, and mounts it. The title's spans exist but are hidden.
  5. The effect runs. Without a reduced-motion preference GSAP makes the title visible and the letters rise; three ScrollTriggers wait for the dark sections. With the preference set, the title is simply shown.
  6. "Get your reading" and "Log in" are ordinary next/link anchors to /signup and /login. Both routes render AuthForm inside the (auth) layout's centred grid with the glow behind it.

A signed-in visit to /

  1. The middleware refreshes the session cookie by calling getUser().
  2. app/page.tsx calls getUser() again, finds a user, and redirect("/app") throws before any component renders. The landing chunk is never requested.
  3. app/(app)/layout.tsx renders: listConversations() runs under RLS for that user and the result is handed to AppShell.
  4. app/(app)/app/page.tsx renders inside it: getBirthProfile() runs, and if the stored Vedic chart predates the whole-sign change, ensureCurrentChart recomputes both traditions and rewrites the row before the page is returned (chapter 2).
  5. The home shows either the intake prompt or the greeting with "Start a reading".

Signing out from the shell

The "Sign out" button is inside a <form action={signOut}>. Submitting it calls the server action, which creates the cookie client, calls supabase.auth.signOut(), and redirect("/login"). The next request to anything under /app has no session and the middleware sends it to /login as well. No client code is involved beyond the form submission.

12.7Performance and cost

  • The landing ships one animation library. The client chunk for the hero carries GSAP 3.15 and ScrollTrigger and nothing else of note. three.js 0.169 is installed and unused, and Next bundles only what is imported, so it costs install time, not bytes on the wire. Removing it from package.json would be a one-line cleanup with no behaviour change.
  • The first paint is a 141,888 byte JPEG. CosmicHero and its fallback both load planet-sun.jpg as a CSS background, so next/image does no resizing or format conversion for it. The unused Hero.tsx did use next/image with priority; that optimisation went away with the component. starfield.jpg is referenced only by the unused components and is never requested.
  • Nothing above the fold is server-rendered on /. With ssr: false the headline and the two calls to action exist only after hydration. A crawler that does not run JavaScript sees a photograph and the metadata title. That is a trade the code makes for a paint that is never blank; it is worth knowing when reading a search report.
  • Two session checks per request. The middleware calls getUser() on every matched request and app/page.tsx calls it again. With a session cookie present, each is a verification round trip to Supabase Auth.
  • Every /app page is dynamic. force-dynamic on the layout means each render runs listConversations(); the home, chat and profile pages each add getBirthProfile(). Two queries per navigation, both indexed (conversations (user_id, created_at desc), birth_profiles unique on user_id), and the shell itself makes no client fetch.
  • The chart upgrade is on the read path. A stale stored chart costs two Swiss Ephemeris computations and one update the first time its owner loads any page that reads the profile. It happens once per profile.
  • Reduced motion is free. The preference short-circuits the effect before GSAP registers its plugin, so nothing is created that then has to be reverted.
  • The theme costs nothing to keep in sync. Four hex values copied by hand and pinned by four unit tests. There is no build step between the CSS and the Swift.

Check yourself

Why is the hero loaded with ssr: false, and what does the visitor lose?

GSAP needs the DOM and the code was written for a browser-only scene, so the component is rendered only on the client. The visitor loses server-rendered headline text: before hydration the page is the photograph alone.

Where does the sidebar's list of readings come from, and why does the query have no user_id filter?

From listConversations() in the (app) layout, run on the server with the cookie client. Row Level Security restricts the rows to the signed-in user, so the query does not need to.

Why do the (app) pages not check for a session?

The middleware redirects any request under /app without a user to /login before a page renders. The pages check for a birth profile instead, which is the question the middleware cannot answer.

What would happen if someone changed --accent in globals.css?

The site would change and the iOS app would not. ThemeTests compare Swift against constants copied from the CSS, not against the CSS itself, so the test would still pass until Theme.swift was edited to match.

Why are there two getUser() calls on a signed-in visit to /?

The middleware calls one to refresh the cookie and decide whether to redirect protected paths; app/page.tsx calls another to decide whether to redirect the landing itself. The landing is not a protected path, so the middleware cannot make that second decision.

Why is the reading card in iOS given explicit colours instead of the environment's?

It renders inside Siri and inside a widget, where the environment's colour scheme may be light. The app is dark-only, and a card that changed with its host would look like another product.
