Chapter fourteen

14The iOS app

Astrya for iOS is a SwiftUI app that talks to the same route handlers and the same Supabase project as the web app, holds no secret the web does not also publish, and is built from a 127-line YAML spec rather than a checked-in Xcode project. Everything about how it is assembled, configured, signed and shipped follows from that.

This chapter describes the code on main on 30 September 2026, version 0.3.0. It covers the plumbing under the features: the generated project and its three targets, the generated configuration file, the entry point and the routing state machine, the design tokens, the API client and its streaming reader, the plist and entitlement choices, how the XCTest suite is organised, and the two GitHub Actions workflows that build it on every push and ship it to TestFlight on every tag. The features themselves (chat, kundli, timeline, alerts, on-device answers) live in their own chapters; chapter 10 in particular covers the widget extension and the App Group cache.

14.1One spec, three targets

The Xcode project is generated. mobile/project.yml is the whole description of the app for XcodeGen, and .gitignore excludes mobile/Sanchara.xcodeproj/, mobile/build/, mobile/SourcePackages/ and the generated sources folder. The comment in the ignore file is the rule: "Run cd mobile && xcodegen generate after changing the spec." The practical consequence is that adding a Swift file means regenerating the project, and that two engineers can never diverge on a project.pbxproj merge, because there is no such file to merge.

The app has no secrets file and no build-time environment; it has one generated Swift file, mobile/Sanchara/Sources/Generated/AppConfig.swift, written by mobile/scripts/make-config.sh from the repo's .env.local. The script reads exactly two variables, the same two the web app ships to browsers: NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY. Its header comment states the boundary: those values "are designed to ship in clients (RLS is the security boundary, not secrecy)", while SUPABASE_SERVICE_ROLE_KEY and ANTHROPIC_API_KEY "are never read here and must never reach the app binary." The script fails loudly if either value is missing. A third value, SANCHARA_API_BASE_URL, is read from the shell environment rather than the file and defaults to the production host, which is how a developer points a build at a local or preview API without touching the checked-in code. The output folder is gitignored, so the generated file exists on every machine that built the app and in no commit.

Three places consume the three constants. Supa.client is constructed from supabaseURL and supabaseAnonKey. SancharaAPI.request builds every URL by appending a path to apiBaseURL. And AuthStore uses apiBaseURL to form the auth/callback redirect for magic-link email.

make-icon.py

The app icon is not a design file; it is mobile/scripts/make-icon.py, a Pillow script that writes Sanchara/Resources/Assets.xcassets/AppIcon.appiconset/AppIcon.png. The docstring describes the mark: "a warm disc with a soft corona on the near-black ground, using the same tokens as app/globals.css." The three colours are literally the site's tokens (BG 0x0A0A0B, ACCENT 0xE8663D, FG 0xF4F1EA). The script renders on a 4096-pixel canvas and downsamples to 1024 with Lanczos so the edges stay clean at small sizes. It builds the image in four passes: sixty concentric translucent rings blurred into a glow for the corona, the disc itself with a warm vertical falloff so it reads as lit, a thin bright limb along the upper edge masked by its own falloff so it fades toward the equator, and the final resize. The disc sits at 46 percent of the height rather than centred, with a radius of a fifth of the canvas. Changing the icon means changing numbers in a script and re-running it, which is the same discipline as the generated project and the generated config: nothing binary is hand-made.

14.3Entry point and routing

// mobile/Sanchara/Sources/SancharaApp.swift
@main
struct SancharaApp: App {
    // APNs callbacks have no SwiftUI equivalent, so the app keeps a delegate.
    @UIApplicationDelegateAdaptor(SancharaAppDelegate.self) private var appDelegate
    @State private var auth = AuthStore()

    var body: some Scene {
        WindowGroup {
            RootView()
                .environment(auth)
                .preferredColorScheme(.dark)
        }
    }
}

Sixteen lines. One AuthStore is created here and passed down through the environment; nothing else in the app creates one. The app delegate exists for one reason the comment gives, APNs token and notification callbacks, and it lives in Services/Push.swift. The dark colour scheme is forced at the root and again in Info.plist, which section 14.6 returns to.

RootView is a switch over AuthStore.State, and SignedInView is a switch over ProfileStore.State. Between them they are the whole routing policy of the app: there is no tab bar and nothing at the root remembers a screen. ChatView owns the one NavigationStack that matters and presents history, profile, kundli, timeline and alerts as sheets. 

// mobile/Sanchara/Sources/RootView.swift
var body: some View {
    Group {
        switch auth.state {
        case .loading:
            LoadingScreen()
        case .signedOut:
            AuthView()
        case .awaitingCode(let email, let purpose):
            VerifyCodeView(email: email, purpose: purpose)
        case .signedIn:
            SignedInView()
        }
    }
    .task { await auth.start() }
    .onOpenURL { url in
        // Two kinds of URL arrive here: Supabase's auth callback, and our
        // own scheme from a widget tap. Only the first is for the auth
        // store; handing it a sanchara:// URL would show "link expired".
        if DeepLink.isDeepLink(url) {
            DeepLink.shared.handle(url: url)
        } else {
            Task { await auth.handle(url: url) }
        }
    }
}

AuthStore.start() sets the first state from whether supabase-swift has a session in the Keychain, then loops over authStateChanges for the life of the app: .signedIn and .tokenRefreshed with a session move to .signedIn, .signedOut moves to .signedOut. The awaitingCode state carries the email and a CodePurpose, either .signIn (a passwordless code) or .confirmSignUp (confirming the address on a password account), which decides which Supabase OTP type verifies it. A password sign-in that fails with "not confirmed" lands in awaitingCode rather than an error, which is how an unconfirmed account recovers.

SignedInView owns a ProfileStore and calls load() in a .task. The store seeds the chart and details from the App Group cache, fetches the birth_profiles row that has a non-null chart, and lands on .needsIntake when there is none or .ready when there is one. IntakeView is handed a closure that calls load() again once the profile is saved, so the same switch carries the person from intake to chat without any navigation code. .failed is reached only when the fetch throws and the cache had nothing; it shows the message, a "Try again" button that reloads, and a "Sign out" button. The web app makes the same decision in a redirect: /api/chat refuses a user with no chart and the chat page sends them to intake.

The web app defines exactly four colours on :root in app/globals.css, and Theme carries the same four hex values with the CSS variable quoted above each. The file's comment gives the reason: matching them exactly "is what makes the native app read as the same product as the site." ThemeTests asserts each of the four against its CSS token, so a careless edit fails the build rather than drifting. The Color(hex:) initialiser exists so tokens can be written the way they appear in CSS. Two derived values are documented as departures: chartLine is heavier than hairline because the kundli's rule lines are the content, not a divider, and at 0.10 white "the square all but vanished on an OLED screen in daylight". A Text.eyebrow() extension reproduces the site's eyebrow style at 12pt with 3.6 points of tracking, which is 0.3em.

Components.swift holds four controls, each a transcription of a Tailwind class list: SancharaField (the site's input, 16pt text because that is the size the web forces on phones so Safari does not zoom, and "the size is the look"), SancharaPrimaryButton (foreground on background, with a spinner that replaces the title while loading and disables the button), SancharaSecondaryButton (a white-at-15-percent border and muted text), and SancharaSecureField, a password field with an eye toggle, because "choosing a password you cannot see is the most common reason a sign-up attempt fails twice."

ReadingCard.swift is the third file and the only one that leaves the app: it is compiled into the widget extension and rendered by the Siri snippet, so an eyebrow, a serif headline and a muted body look the same in three places. Its body parameter is named text rather than body, because body is the View requirement. It sets its own colours rather than reading the environment, for the reason given in its comment: the app is dark-only, "and a card that went light inside Siri while the app stayed dark would read as a different product."

14.5Services: the client and the session

One Supabase client

// mobile/Sanchara/Sources/Services/Supabase.swift
enum Supa {
    static let client = SupabaseClient(
        supabaseURL: AppConfig.supabaseURL,
        supabaseKey: AppConfig.supabaseAnonKey
    )

    /// The current access token, for `Authorization: Bearer` against the
    /// Astrya API on Vercel. Returns nil when signed out.
    static func accessToken() async -> String? {
        try? await client.auth.session.accessToken
    }
}

supabase-swift persists the session in the Keychain by default on Apple platforms, which the comment notes is what the design requires: never UserDefaults. The stores read tables directly through this client (birth_profiles, daily_readings, conversations, messages) under the owner-only RLS policies, and everything that needs a secret or the ephemeris goes through SancharaAPI with the session's access token as a bearer.

SancharaAPI

// mobile/Sanchara/Sources/Services/SancharaAPI.swift
enum APIError: LocalizedError {
    case unauthorized
    case server(String)

    var errorDescription: String? {
        switch self {
        case .unauthorized: "Your session expired. Please sign in again."
        case .server(let message): message
        }
    }
}

private static func request(_ path: String, method: String) async throws -> URLRequest {
    var req = URLRequest(url: AppConfig.apiBaseURL.appendingPathComponent(path))
    req.httpMethod = method
    guard let token = await Supa.accessToken() else { throw APIError.unauthorized }
    req.setValue("Bearer \(token)", forHTTPHeaderField: "Authorization")
    return req
}

private static func check(_ response: URLResponse, _ data: Data) throws {
    guard let http = response as? HTTPURLResponse else { return }
    switch http.statusCode {
    case 200..<300: return
    case 401: throw APIError.unauthorized
    default:
        let message = String(data: data, encoding: .utf8) ?? "Something went wrong."
        throw APIError.server(message)
    }
}

The client is an enum of static functions, one per route handler, each a few lines: request builds the URL and attaches the bearer, URLSession.shared performs it, check maps the status. There are two error cases and no more. A 401 is unauthorized, which every screen renders as a sign-in prompt; anything else outside 2xx is server(message) carrying the response body verbatim, because the route handlers already write their errors as sentences. A missing token throws before any network call. The route handlers themselves are the same ones the web app calls; the /api/geocode call is the one exception to the bearer rule because that route is public, and the comment on it says so.

Streaming a reading

// mobile/Sanchara/Sources/Services/SancharaAPI.swift
if let id = http.value(forHTTPHeaderField: "x-conversation-id") {
    continuation.yield(.conversationId(id))
}

var undecoded = Data()
var batch = ""
for try await byte in bytes {
    undecoded.append(byte)
    guard let piece = String(data: undecoded, encoding: .utf8) else { continue }
    undecoded.removeAll(keepingCapacity: true)
    batch += piece
    if batch.count >= 24 {
        continuation.yield(.text(batch))
        batch = ""
    }
}
if !batch.isEmpty { continuation.yield(.text(batch)) }
continuation.finish()

/api/chat answers with plain UTF-8 text chunks rather than server-sent events, so the client reads raw bytes with URLSession.shared.bytes(for:). Two things follow. A chunk boundary can split a multi-byte character, so bytes are held in undecoded until they decode as a whole string. And byte-at-a-time updates would redraw the transcript thousands of times for one reading, so text is coalesced into batches of at least 24 characters before being yielded. The conversation id arrives first, from the x-conversation-id response header, before any text; ChatStore keeps it and sends it back on the next turn so the server appends to the same conversation, exactly as components/Chat.tsx does on the web. The request timeout is 120 seconds because readings can think for a while before the first byte. A non-2xx status is read to the end and thrown as server(body); a 401 is unauthorized. The stream's onTermination cancels the underlying task, which is what lets a new reading supersede one still streaming without leaking the connection.

14.8CI and TestFlight

The CI job

.github/workflows/ci.yml runs on every push to main and every pull request, with a concurrency group per ref so a newer push cancels an older run. It has two jobs; the ios job runs on macos-26 with mobile as its working directory and does, in order:

  1. Selects the newest Xcode 26 on the runner with xcode-select and prints its version.
  2. Installs XcodeGen with Homebrew.
  3. Writes a placeholder .env.local with a fake Supabase URL and anon key, then runs ./scripts/make-config.sh. The comment explains: the generated file "is never committed. The simulator build only needs the values to be present, not real."
  4. Runs xcodegen generate.
  5. Restores mobile/SourcePackages from the Actions cache, keyed on the hash of project.yml, so the Supabase package is not re-cloned on every run.
  6. Picks the first available iPhone simulator by name and runs xcodebuild test against it with CODE_SIGNING_ALLOWED=NO and -clonedSourcePackagesDirPath SourcePackages. Output is teed to xcodebuild.log and filtered to errors, warnings from the app's own sources, and the test suite and test case result lines, with set -o pipefail so the filter cannot hide a failure.
  7. Uploads the full log as an artifact, but only on failure.

No signing, no secrets, no device. The whole XCTest suite runs unsigned on a simulator, which is possible because nothing in it needs an entitlement to be present: ChartCache falls back to the caches directory when the App Group container is missing, and the tests that need Apple Intelligence skip.

The TestFlight workflow

.github/workflows/ios-testflight.yml runs on every tag matching v* and by hand from the Actions tab, in a single concurrency group that does not cancel in progress. It needs five repository secrets, checked up front so a missing one fails in the first step with its name: SUPABASE_URL and SUPABASE_ANON_KEY, which are baked into AppConfig.swift through the same script the CI job uses; and ASC_KEY_ID, ASC_ISSUER_ID and ASC_KEY_P8, an App Store Connect API key with the App Manager role and its .p8 contents. The header comment states the consequence: "Signing is automatic: with the API key, Xcode creates or refreshes the distribution certificate and profile itself. No certificates are stored here." 

# .github/workflows/ios-testflight.yml
- name: Set version and build number
  run: |
    BUILD="${GITHUB_RUN_NUMBER}"
    for plist in Sanchara/Info.plist SancharaWidgets/Info.plist; do
      if [[ "${GITHUB_REF_TYPE}" == "tag" ]]; then
        /usr/libexec/PlistBuddy -c "Set :CFBundleShortVersionString ${GITHUB_REF_NAME#v}" "$plist"
      fi
      /usr/libexec/PlistBuddy -c "Set :CFBundleVersion ${BUILD}" "$plist"
    done

- name: Use production push environment
  run: /usr/libexec/PlistBuddy -c "Set :aps-environment production" Sanchara/Sanchara.entitlements

After the same Xcode, XcodeGen, config and generate steps as CI, the workflow edits three files in place. The marketing version comes from the tag with its v stripped (v0.3.0 becomes 0.3.0); on a manual run the value in the plist is kept. The build number is the workflow run number, which App Store Connect requires to be unique per version, and it is written to both the app's and the extension's plist because the two must agree. Then aps-environment is switched to production in the entitlements file, because "push tokens minted under the development environment are rejected by production APNs, so store builds must carry the production entitlement." The API key is written to the runner's private_keys folder with mode 600.

Two xcodebuild invocations follow. archive builds the Astrya scheme in Release for generic/platform=iOS into build/Sanchara.xcarchive, with -allowProvisioningUpdates and the three authentication-key flags so Xcode can mint the distribution profile. -exportArchive then reads mobile/ExportOptions.plist and, because that file sets method to app-store-connect and destination to upload, sends the build straight to App Store Connect instead of writing an .ipa. The plist also sets automatic signing, uploadSymbols true so crash logs symbolicate, and manageAppVersionAndBuildNumber false so the numbers the workflow just wrote are the ones that ship; it names the team, which this handbook does not print. Both logs are uploaded as an artifact whether or not the run succeeded.

Why the version lives in the tag The web app deploys from main on every push, and the changelog and package.json carry the version. The iOS build number cannot come from those, because two uploads of the same version need different build numbers, and the marketing version should not be edited by hand in two plists. Deriving one from the tag and the other from the run number means a release is git tag v0.3.0 && git push --tags and nothing else on the iOS side.

Check yourself

Why is there no Sanchara.xcodeproj in the repository?

XcodeGen generates it from mobile/project.yml, and both CI and the TestFlight workflow run xcodegen generate themselves. A generated project cannot suffer a pbxproj merge conflict.

Which two environment variables reach the app binary, and which two never do?

NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY, which the web already ships to browsers and RLS protects. SUPABASE_SERVICE_ROLE_KEY and ANTHROPIC_API_KEY are never read by make-config.sh.

What decides whether a signed-in user sees intake or chat?

ProfileStore.load(): a birth_profiles row with a non-null chart means .ready and ChatView; none means .needsIntake and IntakeView, whose completion closure calls load() again.

Why does chatStream hold bytes back before yielding text?

The route streams raw UTF-8 and a chunk boundary can split a multi-byte character; bytes are kept until they decode, then coalesced into batches of at least 24 characters so the transcript is not redrawn per byte.

The entitlements file says aps-environment: development. How does a TestFlight build end up with production?

The TestFlight workflow edits the file with PlistBuddy before archiving. At runtime ApsEnvironment.current reads the embedded provisioning profile rather than the build configuration, so the server is told the environment the token was actually minted under.

Where does the iOS build number come from?

The GitHub Actions run number, written into both the app's and the extension's Info.plist; the marketing version comes from the tag with the v stripped. ExportOptions.plist sets manageAppVersionAndBuildNumber to false so App Store Connect keeps them.

Why can the whole XCTest suite run unsigned on a simulator?

Nothing in it needs an entitlement: ChartCache falls back to the caches directory without the App Group, and the tests that need Apple Intelligence skip instead of failing.
