Chapter sixteen

16What breaks, and how it is handled

A catalogue of the ways the system fails, and for each one the code that meets it. The organising rule is that a failure should cost the user the least thing it can: a push rather than a reading, a reading rather than a chart, a chart upgrade rather than a request, and never a wrong number presented as a right one.

This chapter describes the code on main on 30 September 2026, version 0.3.0. Every item below was read from the file it names, and every test named exists in the repository under that name. Where a failure mode has no test, the item says "untested" rather than implying one. Items are grouped by the layer they belong to: configuration, authentication, the model, place and time, stored data, push, the device, untrusted text, and deletion. A table at the end puts the whole catalogue on one page.

16.1Where the guards sit

Three kinds of request enter the system and each passes a fixed sequence of guards. A user request, from the web app or the iOS app, reaches a route handler, which builds a Supabase client for the caller (reading two environment variables as it does so), asks that client who the user is, validates the body, and only then touches the database and the external services. A scheduled request from Vercel Cron passes one guard, the cron secret, and then runs under the service-role client with its own guards against repetition. A request on the phone from a widget, a Siri intent or the chat's local router never leaves the device unless the on-device path cannot answer, in which case it becomes the first kind.

16.2Configuration

A required environment variable is missing

Symptom. The build succeeds and the deployment is green; the first request to a route that needs the variable returns a 500, and the function log carries Missing required env var: NAME.

Handling. lib/env.ts exposes one function per variable. required() reads process.env when called and throws with the name; optional() returns undefined for an absent or empty value. Because the read happens inside a request, a missing key fails that request rather than the build, which is the property .github/workflows/ci.yml relies on when it runs next build with no secrets at all (section 15.6). The variable is first touched where a client is built: createRouteSupabase reads the URL and anon key, createAdminSupabase the service-role key, anthropic() the model key. In a route handler that throw happens before the handler's own try, so Next.js turns it into a 500. The file also imports server-only, which makes any import from client code a build error rather than a leak; the same alias in vitest.config.ts is what lets tests import it.

Test. Untested. Nothing exercises required() against an empty environment.

The cron route is called without CRON_SECRET

Symptom. The schedule fires, nothing is written, and the invocation log shows a 401. docs/GO_LIVE_CHECKLIST.md records production in exactly this state for three weeks.

Handling. Both app/api/cron/daily/route.ts and app/api/cron/alerts/route.ts begin the same way: 

const secret = env.cronSecret();
if (!secret || request.headers.get("authorization") !== `Bearer ${secret}`) {
  return new Response("Unauthorized", { status: 401 });
}

An unset secret and a wrong secret are the same case. The alerts route's comment gives the reason: with no secret the route "refuses everything rather than exposing a job that spends model tokens to anyone who finds the path." Failing closed is deliberate; the cost is that a forgotten variable is silent until someone looks at the logs or the tables, which is what the checklist's curl step exists to do.

Test. Untested. There is no route.test.ts under either cron directory.

APNs credentials are absent

Symptom. Locally, or on a deployment before the four APNS_* variables were set: readings and alerts appear in the app's inbox but no notification arrives. The cron's JSON reports alerts.pushConfigured: false and pushesSent: 0.

Handling. isPushConfigured() in lib/push/apns.ts requires all four values. Both jobs write their rows first and call pushToDevices last, and that function returns 0 before it reads any device row when push is not configured. Should ApnsClient.send be reached anyway, it returns { ok: false, status: 0, reason: "APNsNotConfigured" } without opening a connection. .env.example says the same in one line: "Leave blank locally: alerts are still written, pushes are skipped." The client also survives Apple being unreachable: the HTTP/2 session installs an error handler so a socket failure cannot become an unhandled event, each request has a ten-second timeout, and the provider token is minted once and reused for 45 minutes because Apple rate-limits regeneration.

Test. Untested. lib/push/apns.ts has no test file, and the pushConfigured flag in the summaries is not asserted anywhere.

16.3Authentication

A bad, expired or missing bearer token

Symptom. The iOS app gets a 401 with the body Unauthorized from any authenticated route. The web app, which sends cookies, is unaffected.

Handling. Two functions in lib/supabase/route.ts. bearerTokenFrom returns null when the header is absent, when the scheme is not bearer (case-insensitively), or when the scheme is present but the token is empty. createRouteSupabase then chooses: no token means the cookie-backed client from lib/supabase/server.ts, so a web caller never notices this code exists; a token means a fresh supabase-js client that forwards it as an Authorization header with persistSession and autoRefreshToken off. The route does not inspect the token itself. It calls supabase.auth.getUser(), and a forged, expired or revoked token yields no user, at which point every mutating route returns 401 before reading the body. For a valid token, Row Level Security evaluates as that user for the rest of the request, which is the reason the anon key can ship in the binary. On the web, pages under /app and /admin (except /admin/login) are redirected to the login page by updateSession in lib/supabase/middleware.ts when there is no user; the API routes still check for themselves.

Tests. lib/supabase/route.test.ts: "extracts the token from an Authorization header", "accepts a lowercase scheme", "returns null when the header is absent", "returns null for a non-bearer scheme", "returns null when the scheme is present but the token is empty". The 401 on a missing user is pinned per route: app/api/devices/route.test.ts "rejects an unauthenticated caller", app/api/account/route.test.ts "returns 401 and deletes nothing when unauthenticated", app/api/profile/route.test.ts "returns 401 when there is no user". An expired token reaching getUser is not itself tested; the tests stub the user as absent.

16.4The model

The model API fails during a chat reading

Symptom. One of two things, depending on when. Before the stream starts: a 500 whose body reads "Something went wrong preparing your reading. Please try again." After it starts: the reply stops and a final line appears in the transcript, [The stars are momentarily clouded. Please try again.].

Handling. app/api/chat/route.ts does all its preparation, the profile read, the chart upgrade, the transit chart, the timeline context, the conversation and the history, inside one try that ends in the 500 above. Two of those steps have their own softer handling first: a failed transitChart sets transits to undefined and the reading proceeds without today's sky, and a failed loadTimeline is logged and skipped. lib/astrology/transits.ts also deletes a rejected promise from its per-day cache, with the comment "never cache a failure", so one bad ephemeris call does not poison the day for every user in that degree cell.

Once the ReadableStream has been returned the status is already 200 and the x-conversation-id header has been sent, so a mid-stream error cannot change the response code. The stream's start wraps the model call in a try/catch/finally: the catch enqueues the apology line, and the finally saves whatever assistant text had arrived, if any, and closes the stream. A partial reading is therefore kept in the conversation rather than lost, and the user's own message was already saved before the stream began. On iOS, ChatStore.send in mobile/Sanchara/Sources/Features/Chat/ChatStore.swift catches a thrown stream error and puts its description into the still-empty assistant bubble, or into errorMessage if text had already arrived; a CancellationError from a superseding message leaves the transcript as it was.

Tests. Untested on the chat route; there is no test file under app/api/chat/. The bounded-history rule the route depends on is tested in lib/data/history.test.ts: "keeps everything when it fits the budget", "drops the oldest turns first", "never starts on an assistant turn", "keeps the newest turn even when it alone exceeds the budget", "returns nothing for an empty conversation".

The model fails while composing a reading or an alert

Symptom. A push arrives, or a row appears in the inbox, with plain wording: "Your reading for today" and a sentence inviting the user to open the app, or for a dosha change, "Sade Sati is active" with the condition's own detail. Nothing is skipped.

Handling. Both composers treat the model as optional. In lib/alerts/compose.ts, composeAlert catches any error, and also treats output that parseAlertCopy cannot read as a failure, then returns fallbackCopy(started, ended), which names the conditions from the facts the engine already decided. In lib/alerts/predictions.ts, composePrediction does the same and returns fallbackPrediction(slot, firstName). The parser accepts a delimited TITLE/BODY/DETAIL shape and, failing that, the older JSON shape, because markdown inside a JSON string was found to break two replies in seven. The comment above fallbackPrediction states the rule: "Never leave the slot empty: a plain prompt to open the app still beats silence."

Tests. lib/alerts/compose.test.ts: "still names the condition when the model call fails", "reads as relief when a condition has ended", "returns null when neither shape is present", "rejects a delimited reply missing its detail", "still accepts a JSON reply", "rejects output missing a field". lib/alerts/predictions.test.ts: "still says something useful when the model call fails".

16.5Place and time

A birthplace that cannot be geocoded

Symptom. The user types a town and the suggestion list stays empty, or the geocoder is down.

Handling. geocodePlace in lib/geo.ts returns an empty array for a query under two characters, for a non-OK response from the geocoder, and for a response with no results; it never throws for those. GET /api/geocode is public and returns that array. The web form in components/IntakeForm.tsx offers a second path: "Can't find your birthplace? Enter coordinates manually", which takes a latitude and longitude and derives the timezone in the browser with resolveTimezone, the same tz-lookup call the server uses, so a chart can still be computed for a village no geocoder knows. The iOS form in mobile/Sanchara/Sources/Features/Intake/IntakeView.swift debounces the search by 300 milliseconds, turns a thrown request into an empty list with try?, and keeps Save disabled until a place has been picked; it has no manual coordinate entry. On the server, POST /api/profile rejects a missing field or a non-finite coordinate with a 400 before any chart is computed, and a chart computation that throws returns a 500 reading "Could not compute your chart. Please try again." The web app's saveIntake server action in app/(app)/app/intake/actions.ts has no equivalent catch: a compute failure there surfaces as a Next.js error page.

Tests. app/api/profile/route.test.ts: "returns 400 when a required field is missing", "returns 400 when lat is not a number", "saves the profile and returns 200 for a valid payload". The empty-result paths of geocodePlace are untested; lib/geo.test.ts covers only resolveTimezone.

Timezone edge cases

Symptom. A reading lands at the wrong hour, or a chart is computed for the wrong instant.

Handling, and where it stops. The timezone is never typed by anyone. It is derived from coordinates by tz-lookup, stored with the profile, and reused: the iOS form's prefill keeps the stored coordinates and zone on edit because "the birthplace has not moved." computeChart in lib/astrology/chart.ts parses birthDate and birthTime with Luxon in that zone and converts to UT before the ephemeris sees them. The scheduled jobs read profile.timezone || "UTC", decide the slot from the user's local hour with slotForHour (before 14:00 is morning), and store for_date as the user's local date, so "my reading for the 26th" means their 26th. The transit chart is sampled at midday UTC once per day per whole-degree cell of latitude and longitude, which keeps the prompt text stable for the cache; the comment notes only the Moon moves enough within a day to matter. Two edges are not guarded. tzlookup throws RangeError("invalid coordinates") outside the valid range, and the web form's manual mode calls it with any finite numbers, so a latitude of 95 throws in the browser. And Luxon given an unknown zone name returns an invalid DateTime, whose fields are NaN, and nothing checks validity before julday; in practice the zone always comes from tz-lookup, so the path is unreachable through the forms. Users far from the fixed UTC schedule can have both cron runs land in the same half of their day and get one reading instead of two, which docs/PUSH_ALERTS.md documents together with the hourly schedule that would fix it.

Tests. lib/geo.test.ts: "maps New Delhi coordinates to Asia/Kolkata", "maps New York coordinates to America/New_York". lib/alerts/slots.test.ts: "splits the user's local day in two", "returns the current slot when it has not been written", "returns nothing when the current slot already exists", "does not backfill a slot the user has moved past". The invalid-coordinate and invalid-zone paths are untested.

16.6Stored data

A chart stored before whole-sign houses

Symptom. None visible, which is the design. Before 0.3.0 the stored Vedic chart carried Placidus house numbers under whole-sign labels, so the kundli and the PDF could draw a planet in a house whose sign it was not in.

Handling. Every chart now carries schemaVersion, and CHART_SCHEMA_VERSION in lib/astrology/constants.ts is 2. isChartStale in lib/astrology/derived.ts is true when the stored version (1 if absent) is lower, or when the chart has no derived facts. ensureCurrentChart in lib/data/birthProfile.ts recomputes both traditions together with Promise.all, writes them back in one update, and returns the upgraded row; the comment explains that both are recomputed "so a profile is never half upgraded", and that doing it on read "means no migration and no backfill job." It runs from getBirthProfile, which the three server-component pages use, and from the chat route. Any failure, whether the compute throws or the write comes back with an error, is logged with its stage and the original profile is returned, because an upgrade that cannot be written is not a reason to fail the request that triggered it. Readers that only need facts do not wait for the upgrade: factsFor derives them in process from the stored positions, and deriveFacts recomputes houses whole-sign regardless of the stored numbers. The alerts job has a companion guard: partitionForAlerts in lib/alerts/run.ts never notifies a natal condition once the user has natal rows on record, because a natal condition "cannot start or end, so a change in one is always an artifact of the computation changing."

Tests. lib/data/birthProfile.test.ts: "returns the profile unchanged when there is no stored vedic chart", "returns the profile unchanged when the stored chart is already current", "recomputes and writes both traditions together for a stale chart", "swallows a thrown compute/write exception and returns the original profile", "swallows a resolved write error (RLS/constraint) and returns the original profile unchanged", "returns an upgraded profile when the stored chart is stale". lib/astrology/derived.test.ts: "recomputes houses whole-sign, ignoring the stored numbers". lib/alerts/run.test.ts: "alerts natal conditions on a first read, when no natal rows exist", "never alerts a natal condition once the user has natal rows", "keeps transit conditions alertable in both cases".

A failed profile read that looked like a missing profile

Symptom. Fixed in 0.3.0. A user with a chart opened the app during a database hiccup and was sent to the intake form as though they had never filled it in.

Handling. supabase-js resolves { data: null, error } on a failed read rather than throwing, and the old getBirthProfile ignored error and returned data ?? null. It now throws with the error's message, matching saveBirthProfile in the same file, while a genuine no-row result, which maybeSingle() reports as { data: null, error: null }, still returns null. The three pages that read through it (app/(app)/app/page.tsx, chat/page.tsx and profile/page.tsx) now surface an error instead of the intake form. The chat route does its own read and checks profileError explicitly, returning a 500 that says "Something went wrong loading your profile."

Tests. lib/data/birthProfile.test.ts: "throws on a genuine read failure instead of reporting it as no profile", "returns null when there is no stored profile".

Duplicate cron runs

Symptom. None. The job can be fired twice in a minute, or moved to an hourly schedule, and a user still gets one morning reading, one night reading and one alert per change.

Handling. Three mechanisms. First, daily_readings has unique (user_id, for_date, slot) from supabase/migrations/0005_daily_readings.sql, and writeDueReading reads the slots already written for today before deciding anything through isSlotDue. If two runs race past that read, the insert fails with Postgres code 23505, which the code treats as "already done" and counts as skipped. Second, transit_conditions has a partial unique index, (user_id, signature) where ended_on is null, from 0004_alerts_push.sql, and runAlertsForUser diffs today's condition signatures against the open rows, so an unchanged sky inserts nothing, closes nothing and sends nothing. Third, deriveHadNatalRows fails closed: if the count of natal rows errors, the user is treated as already having them, so a transient database error cannot turn a standing natal dosha into a "has begun" push. Both jobs also bound their work to 500 profiles per run and count a failing user in failures rather than aborting the run.

Tests. lib/alerts/slots.test.ts, the four names above. lib/alerts/run.test.ts: "is false when the count query succeeds with zero natal rows", "is true when the count query succeeds with at least one natal row", and the test whose name begins "fails CLOSED", which passes an errored count and expects true. The 23505 branch is untested.

Account deletion ordering

Symptom. The user taps Delete on the profile screen and confirms.

Handling. DELETE /api/account takes the user id from the verified session, never from the body, so a caller can only delete themselves, then calls admin.auth.admin.deleteUser(user.id) with the service-role client. Every table references auth.users(id) on delete cascade: admins, profiles, birth_profiles, conversations (and through it messages), device_tokens, transit_conditions, alerts, daily_readings, life_events, life_event_scans and period_readings. One call removes everything the database holds, and because device_tokens goes with it the next cron cannot push to the phone. If the call fails the route returns a 500 with a message and the account is untouched. On the phone, ProfileView.deleteAccount calls the API first and only on success runs AuthStore.signOut, which unregisters the device (a no-op now, but the same path sign-out always takes), signs out of Supabase, and clears the App Group cache so the widget stops showing the deleted chart. Two things are not removed: the avatar object in the avatars storage bucket, which the route never touches, and the Sign in with Apple grant, which docs/APPLE_SIGN_IN.md lists as a known gap against guideline 5.1.1(v).

Tests. app/api/account/route.test.ts: "returns 401 and deletes nothing when unauthenticated", "deletes only the calling user", "returns 500 when deletion fails". The cascade itself is a database constraint and is not tested from code.

16.7Push

A token minted under the wrong APNs environment

Symptom. The cron reports pushesSent: 0 for a device that is registered, and the function log shows apns send failed 400 BadDeviceToken. Before 0.2.0 a Release build run from Xcode produced exactly this: it reported production from its build configuration while carrying a development entitlement.

Handling. The environment is read from the truth APNs itself uses. ApsEnvironment.current in mobile/Sanchara/Sources/Services/Push.swift opens embedded.mobileprovision, finds the plist inside the signed envelope by searching for <plist and </plist>, and returns production only when aps-environment is exactly that string; anything else, including no profile at all (the simulator), is sandbox. The app sends that word with every registration. POST /api/devices checks the token is 64 to 200 hex characters, maps anything other than sandbox to production, and upserts on the token with the admin client so a phone handed to a new account changes owner. ApnsClient.send picks the host from the row's environment, and when Apple answers 410, Unregistered or BadDeviceToken, the row is deleted: "Apple only tells you a token is dead when you use it." A token registered under the wrong host is therefore dropped on first use and written back correctly at the next launch, since PushStore.register runs whenever iOS hands the app a token. The TestFlight workflow removes the remaining way to get this wrong by setting the entitlement to production before archiving.

Tests. mobile/Sanchara/Tests/ApsEnvironmentTests.swift: testDevelopmentProfileIsSandbox, testProductionProfileIsProduction, testProfileWithoutThePushEntitlementIsSandbox, testNoPlistAtAllIsSandbox, testAnUnknownValueIsNotTrustedAsProduction, testSimulatorBuildReportsSandbox. app/api/devices/route.test.ts: "rejects a malformed token", "stores the token against the session user, not the body", "defaults an unknown environment to production", "deletes only this user's row for that token". The dead-token deletion in the jobs is untested.

16.8The device

A widget with no cached chart

Symptom. A freshly installed app, a signed-out phone, or an App Group that was never enabled. The widget must draw something.

Handling. Neither widget fetches. ReadingProvider in mobile/SancharaWidgets/ReadingWidget.swift reads ChartCache.shared.loadReading(), and when that is nil the entry's reading is nil and the view shows its empty state, "Open Sanchara to get your first reading." PeriodProvider in PeriodWidget.swift tries three sources in order: the cached period with its theme, then the cached chart's dasha without a theme ("the dates are true"), then the empty state "Open Sanchara to map your periods." Both empty states name the next action rather than apologising. ChartCache itself, in mobile/Sanchara/Sources/Services/ChartCache.swift, falls back to the app's own caches directory when the App Group container is unavailable, so the app keeps working and only the sharing stops; docs/SIRI_AND_WIDGETS.md names that as the symptom of a missing App Group capability. Every read is a try?, so a corrupt file reads as absent. The reading cache carries an isFresh flag so a widget "should not keep insisting on yesterday's morning reading"; today the Siri snippet in IntentData.swift checks it and the widget provider does not. Sign-out calls clear(), which removes all four files, so the widget of a shared phone cannot show the previous account.

Tests. mobile/Sanchara/Tests/PeriodProgressTests.swift: testCachedPeriodSurvivesTheRoundTrip, testClearRemovesTheCachedPeriod, testFractionClampsOutsideThePeriod, testZeroLengthAndMalformedDatesGiveZero. The empty views themselves are untested.

The on-device model is unavailable

Symptom. An iOS 17 phone, an iOS 26 phone without Apple Intelligence, or a model that refuses. The question must still be answered.

Handling. Three layers, each of which falls through to the server. OnDeviceReasoner.route in mobile/Sanchara/Sources/Features/Chat/OnDeviceReasoner.swift is wrapped in #if canImport(FoundationModels) so the app builds for iOS 17, then gated on #available(iOS 26.0, *) and on isAvailable, which is SystemLanguageModel.default.availability == .available; any of those false means .escalate. When the model runs, a refusal or a thrown error in isLookup returns false and in answer returns nil, with the comment that this "is not an error worth surfacing: the question simply goes to Claude, which is where it went before." An answer that never called the lookup tool is discarded as a guess. ChatStore.send only tries the reasoner for a Vedic question that is not the opening reading and not an explicit request for the server; on .escalate it streams from /api/chat exactly as before. Because Apple's model refuses astrology, everything it is shown is framed as a reference table by ChartFacts, and a test guards that framing because a slip would make the feature stop answering silently.

Tests. mobile/Sanchara/Tests/OnDeviceRoutingTests.swift: testQuestionsAboutLifeNeverReachTheModel, testQuestionsNamingPartOfTheChartGetOffered, testInterpretiveQuestionsStillDoNotReachTheTable, testAMissingBodyReturnsNothingRatherThanAGuess, testNothingHandedToTheModelNamesAstrology. The availability gate needs a device and is untested.

16.9Untrusted text

Prompt injection through chat history

Symptom. A user, or text pasted by a user, tells the model to ignore its instructions or to invent a placement.

Handling, honestly stated. There is no explicit prompt-injection defence in the repository, and the file the name suggests, lib/data/injection.test.ts, is about dependency injection: its describe is "data helpers accept an injected client", and its three tests are "saveBirthProfile writes through the injected client", "appendMessage writes through the injected client" and "falls back to the cookie client when none is injected". What does exist limits the blast radius. User messages are sent to the model in the user role and are never spliced into the system prompt; the system prompt in lib/astrology/prompt.ts instructs the model to "Never state a placement, lordship, aspect, dasha, condition or number that is not listed above" and to "Interpret only this data"; and the model cannot act, since it has no tools and its output is text that is stored and shown. History is bounded by selectHistory to 6,000 characters, newest first, never starting on an assistant turn. The one place chat history is mined for facts, the timeline scan in app/api/timeline/scan/route.ts, reads only rows with role = 'user' ("Assistant turns are full of astrological narrative that reads like biography and would extract as fiction"), tells the model to "Never infer one from a question they asked, from a hypothetical, or from something you read in an astrological reading", quotes the user's own words as evidence, and writes nothing until the user confirms each candidate; POST /api/life-events then rejects a date before birth or in the future.

Tests. Prompt injection as such: untested. The surrounding limits are: lib/data/history.test.ts, the five names in 16.4; lib/timeline/extract.test.ts: "drops events outside the person's life", "drops impossible dates", "reads a fourth field as evidence, so a pipe in a title becomes the quote", "tells the model how to resolve relative dates and ages, and to keep undated events".

16.11Study notes

Read in this order

  1. lib/env.ts, for the one decision that makes the build secret-free and the first request the place a missing key fails.
  2. lib/supabase/route.ts and its test, for the bearer and cookie split.
  3. app/api/chat/route.ts, the stream's catch and finally, for what a partial reading becomes.
  4. lib/alerts/compose.ts and predictions.ts, the two fallbacks and the parser that feeds them.
  5. lib/data/birthProfile.ts, for the on-read upgrade and the read that now throws.
  6. lib/alerts/run.ts, for the signature diff, the natal partition and the fail-closed count.
  7. lib/push/apns.ts and mobile/Sanchara/Sources/Services/Push.swift, both ends of the environment question.
  8. mobile/SancharaWidgets/PeriodWidget.swift and OnDeviceReasoner.swift, for the device's two fallbacks.

Check yourself

Why does a missing ANTHROPIC_API_KEY fail a request and not the build?

Because env.anthropicApiKey is a function called inside anthropic() during a request; nothing reads process.env at module load.

What does the chat route do with text the model had already streamed when the call fails?

Saves it as the assistant turn in finally, after enqueuing the apology line, then closes the stream. The status was already 200.

Why does the alerts job treat an errored natal-row count as "has natal rows"?

Because the naive reading would be "first-time reader" and every standing natal dosha would be pushed as news; suppressing natal alerts costs nothing real, since natal conditions cannot change.

A phone registers a sandbox token and the server is configured for production. What happens on the next cron?

The row carries sandbox, so the server sends to the sandbox host; environments are per row, not per server. Only a token registered under the wrong word fails, and Apple's BadDeviceToken gets that row deleted until the next launch re-registers it.

The mahadasha and antardasha from the cached chart, with a progress bar and no theme; only with no chart at all does it show the empty state.
