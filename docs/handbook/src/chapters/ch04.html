Chapter four

4Identity and access

One Supabase project, two ways in, and a single rule under both: the database decides who may read a row, not the code that asked for it. The web app carries its session in cookies, the iOS app carries a bearer token, and every table refuses anyone but its owner.

This chapter describes identity and access as they are on main on 30 September 2026, version 0.3.0. Nothing here is a framework of its own. Supabase Auth issues the sessions, Postgres Row Level Security enforces ownership, and the application code is a thin set of clients that make sure a request reaches Postgres as the person who sent it. The interesting decisions are about where each key is allowed to be, which paths bypass the rule and why, and how the phone gets a session without ever leaving the app.

4.1Two channels

A browser and a phone reach the same Postgres through different doors. On the web, the session lives in cookies that @supabase/ssr reads and refreshes; a server component, a server action, a route handler and the middleware all build a client from those cookies and Postgres sees the request as that user. On iOS, supabase-swift holds the session in the Keychain and the app does two things with it: it reads a few tables directly over PostgREST, and it calls the same /api/* route handlers the web uses, sending the access token as Authorization: Bearer. A route handler builds a client that forwards that header, and again Postgres sees the request as that user.

The design follows from one sentence in the README: every table is protected by Row Level Security, so the anon key is safe to ship in the iOS binary. The anon key and the project URL are public by design. What must never ship is SUPABASE_SERVICE_ROLE_KEY, which bypasses RLS, and ANTHROPIC_API_KEY. Both are read only through lib/env.ts, which begins with import "server-only", and the script that generates the iOS configuration (mobile/scripts/make-config.sh) reads only the two public values and says so in its header.

4.3Session on the web

createServerSupabase in lib/supabase/server.ts wraps createServerClient from @supabase/ssr with the Next.js cookie store. Its setAll is wrapped in a try block with a comment that explains the whole arrangement: when the client is created from a Server Component, cookies cannot be written, so the write is ignored and the middleware is what refreshes them. That is why the root middleware.ts exists at all. 

// lib/supabase/middleware.ts
const { data: { user } } = await supabase.auth.getUser();

const path = request.nextUrl.pathname;
const isProtectedApp = path.startsWith("/app");
const isProtectedAdmin = path.startsWith("/admin") && path !== "/admin/login";
if ((isProtectedApp || isProtectedAdmin) && !user) {
  const url = request.nextUrl.clone();
  url.pathname = isProtectedAdmin ? "/admin/login" : "/login";
  return NextResponse.redirect(url);
}
return response;

updateSession does two jobs on every request. It calls getUser, which verifies the token with Supabase Auth rather than trusting the cookie's contents, and in doing so refreshes an expiring session and writes the new cookies onto the response. Then it redirects anyone signed out away from /app and /admin, sending the two areas to their own login pages. The matcher in the root file excludes _next/static, _next/image, favicon.ico, images/ and .well-known/, so static assets and the Apple association file are served without a session lookup.

One form, two outcomes

The login and signup pages render the same AuthForm with the same authenticate action; only the title differs. The action is the web's "smart" sign-in, and its comment states the intent: an existing account with the right password logs in, a new email creates an account, and an existing email with the wrong password is told so.

  1. Try signInWithPassword. A session means a returning user; redirect to /app.
  2. If the error message contains "not confirmed", the account exists but the address was never confirmed; redirect to /check-email with the address in the query string.
  3. Otherwise call signUp with emailRedirectTo set to <origin>/auth/callback. If Supabase answers that the address is already registered, the first step failed because of the password, and the form shows "Incorrect password for this account. Try again, or use a magic link."
  4. A new account with a session (email confirmation switched off in the project) goes to /app; without one it goes to /check-email.

The order matters. Trying sign-in first makes the common case one round trip, and using the sign-up error to distinguish "wrong password" from "new person" means the form never has to ask which the visitor is. The cost is that the message strings from Supabase are matched by substring ("already registered", "already exists", "already been registered"), which is fragile by nature and is the reason the iOS app chose a different shape (4.4).

sendMagicLink calls signInWithOtp with the same redirect and bounces back to /login?sent=1. resendConfirmation calls auth.resend with type signup. signOut signs out and redirects to /login; the form that calls it lives in components/AppShell.tsx at the bottom of the sidebar.

The callback

// app/auth/callback/route.ts
const code = searchParams.get("code");
if (code) {
  const supabase = await createServerSupabase();
  await supabase.auth.exchangeCodeForSession(code);
}
return NextResponse.redirect(`${origin}/app`);

Every link Supabase sends (confirmation, magic link, the admin's one-time link) resolves to this route with a code. The route exchanges it for a session, which writes the cookies, and redirects to /app unconditionally. If the code was missing or the exchange failed, the redirect still happens and the middleware bounces the visitor to /login. There is no error page for a bad link on the web; the login page is the error page.

lib/supabase/client.ts exports a createBrowserClient wrapper for client components. No file imports it today. Every read on the web goes through server components and server actions, so the browser never holds a Supabase client. Keep that in mind before reaching for it: adding a browser client would mean the anon key and the session start being used from JavaScript, which is safe under RLS but is a second channel to reason about.

4.4Session on the phone

Supa.client in mobile/Sanchara/Sources/Services/Supabase.swift is the app's single SupabaseClient, built from the generated AppConfig. The file's comment records the requirement that made supabase-swift the right choice: it persists the session in the Keychain by default, never in UserDefaults. Supa.accessToken() returns the current access token or nil, and that is the whole bridge to the API. 

// mobile/Sanchara/Sources/Services/SancharaAPI.swift
private static func request(_ path: String, method: String) async throws -> URLRequest {
    var req = URLRequest(url: AppConfig.apiBaseURL.appendingPathComponent(path))
    req.httpMethod = method
    guard let token = await Supa.accessToken() else { throw APIError.unauthorized }
    req.setValue("Bearer \(token)", forHTTPHeaderField: "Authorization")
    return req
}

Every call in SancharaAPI goes through this function except geocode, whose comment says why: the route is public, so it carries no token. A 401 from any route maps to APIError.unauthorized, whose description is "Your session expired. Please sign in again."

The bearer channel on the server

// lib/supabase/route.ts
export async function createRouteSupabase(request: Request): Promise<Db> {
  const token = bearerTokenFrom(request);
  if (!token) return createServerSupabase();

  return createClient(env.supabaseUrl(), env.supabaseAnonKey(), {
    global: { headers: { Authorization: `Bearer ${token}` } },
    auth: { persistSession: false, autoRefreshToken: false },
  });
}

This is the file that lets one set of route handlers serve both clients. bearerTokenFrom reads the Authorization header, accepts the scheme case-insensitively, and returns null for a missing header, a different scheme, or an empty token. With a token, the handler gets a plain supabase-js client that forwards the header on every request, so RLS evaluates as that user; the client neither persists nor refreshes anything, because the phone owns the session. Without a token, the handler falls through to the cookie client and the web behaves as it always did. The exported Db type is SupabaseClient, and the comment notes that both clients are instances of it, which is what lets lib/data/birthProfile.ts accept either.

Nine route handlers use createRouteSupabase: account, chat, devices, kundli, life-events, profile, timeline, timeline/explain and timeline/scan. Each begins the same way, getUser then a 401 when there is no user, and the user id used afterwards always comes from that verified session, never from the body.

Direct reads

Not everything on the phone goes through Vercel. ProfileStore reads birth_profiles straight from Supabase with Supa.client.from(...), and the alerts and daily-reading stores do the same for their tables. There is no user id in those queries. The birth self policy already restricts the result to the caller's own row, so the query is simply "select from birth_profiles where chart is not null, limit 1". That is the practical meaning of RLS as the boundary: the client does not filter by owner because it cannot see anyone else's rows to begin with.

The state machine

AuthStore is an @Observable class on the main actor with four states: loading, signedOut, signedIn, and awaitingCode(email:purpose:). start() sets the initial state from whether a session exists, then listens to authStateChanges: signedIn and tokenRefreshed with a session mean signed in, signedOut means signed out. RootView switches on the state and shows LoadingScreen, AuthView, VerifyCodeView or SignedInView.

The store's header comment explains the one deliberate divergence from the web. Sign-in and sign-up are separate paths: "a person who mistypes a password should be told that, not silently pushed into creating a second account." AuthView has a two-segment picker, and a device that has never signed in opens on "Create account" (AuthStore.hasSignedInBefore, a UserDefaults flag under a key that keeps the pre-rename prefix so that returning users are not shown the first-run screen). signIn maps "not confirmed" to awaitingCode with purpose confirmSignUp; signUp maps "already registered" to an error and sets shouldSwitchToSignIn, which the view watches to flip the picker with the email still filled in. Both validate the address and the password length (minimumPasswordLength = 6, Supabase's default) before spending a round trip.

signOut does three things in a fixed order: unregister the push token while the bearer token is still valid, sign out, then ChartCache.shared.clear(). The comment says why the third step exists: the chart, the birth details and the last reading live on disk in the App Group, and without clearing them the widget would keep showing them to whoever signs in next.

4.5Email code

On the phone, the passwordless path sends a six-digit code rather than a link. docs/EMAIL_OTP.md gives the reason and the one setting it depends on. The reason: a code is typed into the app that is already open, with no hop out to a mail client and no Universal Link that a browser might swallow. The setting: Supabase decides link-versus-code by what the email template contains. A template with only {{ .ConfirmationURL }} sends a link and no code, and the app's code screen would have nothing to accept. Both the "Magic Link" and "Confirm signup" templates therefore include {{ .Token }} and keep the link as well, so the same email serves the phone (type the code) and the web (tap the link).

Three details in AuthStore decide how this feels in practice.

  • Which code was sent decides how it is verified. CodePurpose has two cases. signIn verifies with EmailOTPType.email; confirmSignUp, reached when a password sign-up needs its address confirmed, verifies with .signup. resendCode re-sends through the matching path: signInWithOTP for the first, auth.resend(type: .signup) for the second.
  • Digits only. normalizedCode keeps the numeric characters and takes the first six, because people paste codes with spaces and mail clients wrap them in punctuation. VerifyCodeView applies it on every change, and once six digits are present it submits on its own; the comment calls a separate button "ceremony". The field is marked .textContentType(.oneTimeCode), so iOS offers the code from the email above the keyboard.
  • The link still works. sendEmailCode passes redirectTo pointing at auth/callback on the API host, so anyone who taps the link instead of typing the code lands back in the app through a Universal Link (4.6).

A failed verification whose message contains "expired" or "invalid" is reported as "That code didn't work. It may have expired, send a new one." Codes expire after an hour by default. The screen also offers "Use a different email", which simply calls signOut to return to signedOut.

The web has no code screen. Its magic-link button calls the same signInWithOtp and so receives the same email, but the only thing it can do with it is follow the link to /auth/callback. The code in that email is for the phone.

4.6Sign in with Apple and Universal Links

Apple

Sign in with Apple is fully native. Apple returns an identity token and Supabase verifies it directly through signInWithIdToken; there is no web sheet, no redirect, no password and no confirmation email. The header of AppleSignIn.swift calls it the fastest way onto Astrya, and docs/APPLE_SIGN_IN.md records the two one-time steps it needs: the Apple provider enabled in the Supabase project with the bundle id com.shivvyas.astra as a client id, and the Sign In with Apple capability on the App ID. The entitlement com.apple.developer.applesignin is already in mobile/project.yml. For the native flow no Services ID, secret key or key id is needed; those exist only for Apple's web OAuth, which the site does not offer. 

// mobile/Sanchara/Sources/Features/Auth/AppleSignIn.swift
SignInWithAppleButton(.continue) { request in
    let nonce = AppleSignIn.randomNonce()
    rawNonce = nonce
    request.requestedScopes = [.fullName, .email]
    request.nonce = AppleSignIn.sha256(nonce)
} onCompletion: { result in
    let nonce = rawNonce
    Task { await auth.completeAppleSignIn(result: result, rawNonce: nonce) }
}

The nonce is the part worth understanding. randomNonce draws 32 characters from a 64-character alphabet using SecRandomCopyBytes, rejecting any byte of 252 or above so the modulo does not bias the distribution. Its SHA-256 goes to Apple, which signs it into the identity token; the raw value goes to Supabase, which hashes it and compares. The comment states what this buys: a captured token cannot be replayed against the project, because the replayer does not hold the raw nonce that produced its hash.

completeAppleSignIn treats a cancelled sheet (ASAuthorizationError.canceled) as a normal action and reports nothing. On success it extracts the identity token, calls signInWithIdToken(credentials: .init(provider: .apple, idToken:, nonce:)), and then keeps credential.fullName if Apple sent one. Apple sends the name only on the very first authorization for this App ID, ever, so AppleSignIn.remember stores it in UserDefaults and the intake screen (chapter 5) pre-fills the first and last name from it. The keys keep their pre-rename prefix on purpose: the bundle id did not change, existing installs upgrade in place, and a renamed key would lose a name Apple will never send again.

Known gap Apple's guideline 5.1.1(v) asks apps that offer Sign in with Apple to revoke the Apple token when a person deletes their account. DELETE /api/account deletes the Supabase user and everything that cascades from it, but it does not call Apple's revoke endpoint. docs/APPLE_SIGN_IN.md lists the three steps to close this (a Services ID and key to mint a client secret, capturing the authorization code at sign-in, and posting the refresh token to the revoke endpoint before the Supabase user is removed) and says it is worth doing before the first App Store submission that includes Apple sign-in. As of 0.3.0 it is open.

Universal Links

Every email Supabase sends carries a link that resolves to /auth/callback on the production host. On a phone with the app installed, that URL should open the app, not Safari. Two files make that happen. The entitlements in mobile/project.yml declare applinks:astra.shivvyas.com and webcredentials:astra.shivvyas.com. And the site serves public/.well-known/apple-app-site-association, which names the app as the team id joined to com.shivvyas.astra, and claims exactly two paths: /auth/callback and /auth/callback?*. The webcredentials entry is what lets the iOS password autofill offer credentials saved for the site to the app.

When iOS hands the URL to the app, RootView.onOpenURL receives it. Two kinds of URL arrive there, and the comment is explicit: Supabase's auth callback and the app's own sanchara:// scheme from a widget tap. DeepLink.isDeepLink checks the scheme; a deep link goes to DeepLink.shared.handle, anything else goes to AuthStore.handle(url:), which calls Supa.client.auth.session(from: url) and moves to signedIn. Handing a widget URL to the auth store would produce "That link has expired", which is the failure the check prevents. Without the app installed, the same URL reaches the web route in 4.3 and the person is signed in on the web instead.

4.7Row Level Security

RLS is the boundary. The clients above exist only to make sure a request reaches Postgres with the right identity; what that identity may then see is decided entirely by the policies in supabase/migrations/. Every table has enable row level security, and every policy is written in terms of auth.uid(). Here is all of them.

Every for all policy carries both using and with check with the same predicate, so a user can neither read another person's row nor insert a row that claims another owner. The three tables with select-only or select-and-update policies are the ones the scheduled jobs write: transit_conditions, alerts and daily_readings. The comments in 0004 and 0005 say it directly: the daily job writes them with the service-role client, and the policies exist so the app can read its own rows and mark them read. A user cannot insert an alert. admins has no insert, update or delete policy at all; the comment on the table reads "presence in this table = admin. No self-service path". The only way in is the SQL statement in docs/SUPABASE_SETUP.md, run by hand.

Two functions complete the picture. public.is_admin() is security definer and checks for the caller's row in admins; it is used by the admins policy so an admin can see the whole list. public.handle_new_user() runs on after insert on auth.users and creates the profiles row, taking a display name from the sign-up metadata or the part of the email before the @. Every table with a user_id references auth.users(id) on delete cascade, which is what makes account deletion one call (chapter 11).

Where the service-role key is allowed

// lib/supabase/admin.ts
import "server-only";
// Bypasses RLS. Only ever import from server code behind an admin auth check.
export function createAdminSupabase() {
  return createClient(env.supabaseUrl(), env.supabaseServiceRoleKey(), {
    auth: { persistSession: false, autoRefreshToken: false },
  });
}

import "server-only" makes the bundler fail if a client component ever imports this file, so the key cannot leak into a browser bundle by accident. Beyond that the rule is convention, and the convention is narrow. These are the only production files that call createAdminSupabase, and each has a reason RLS cannot serve.

Note what every entry has in common: the row being written is still scoped to a user id that came from getUser on the caller's own client, or the code is a scheduled job with no caller at all. The admin client is never used to act on a user id taken from a request body.

4.8The admin boundary

The admin area at /admin has its own login page, its own sign-in action, and a guard on every page. Being an admin is not a role or a claim; it is a row in admins. Three layers check it.

  1. The middleware redirects any signed-out request under /admin, except /admin/login itself, to /admin/login. This proves a session exists, not that it is an admin's.
  2. adminSignIn in app/admin/actions.ts calls signInWithPassword with the cookie client, then isAdminUser. A valid account that is not in admins is signed out again immediately and sent back with "Not authorized". There is no sign-up on this form, no magic link, and no way to become an admin from it.
  3. requireAdmin in lib/admin/guard.ts is the first line of every admin page and every admin action. It reads the user from the cookie client, redirects to /admin/login if there is none, and redirects with "Not authorized" if isAdminUser is false. The layering means a person removed from admins while signed in loses access on their next request, not at their next login.
// lib/admin/guard.ts
export async function requireAdmin() {
  const supabase = await createServerSupabase();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) redirect("/admin/login");
  if (!(await isAdminUser(user.id))) redirect("/admin/login?error=Not+authorized");
  return user;
}

The admin session is an ordinary Supabase session in the same cookies as the app's. What separates the two areas is the guard, the separate login page, and the layout: app/admin/layout.tsx is a passthrough with force-dynamic, and each authenticated page wraps itself in AdminShell so the sidebar never appears on the login screen. What an admin can read and do once inside is chapter 11's subject; the short version is that the admin reads users, birth details and transcripts, can send a password reset and mint a one-time login link, and writes nothing to a user's data.

Two things to keep straight The web's user login accepts a magic link; the admin login does not. And is_admin() in SQL and isAdminUser in TypeScript answer the same question by different routes: the SQL function runs inside a policy as security definer, the TypeScript function runs on the server with the service-role client. Change one without the other and the admins list becomes visible to the wrong people or the guard starts lying.

4.9Tests

Identity is the part of a system where a test is cheapest to write and most expensive to lack, and the coverage here is narrow but exact. Nothing in it needs a network or a Supabase project.

  • lib/supabase/route.test.ts pins bearerTokenFrom with five cases: a token is extracted from a Bearer header; a lowercase scheme is accepted; a missing header returns null; a Basic scheme returns null; a Bearer scheme with an empty token returns null. The last two are what keep a malformed header from falling through to the cookie client with a garbage token attached.
  • mobile/Sanchara/Tests/AuthValidationTests.swift covers the pure functions on AuthStore and AppleSignIn. testAcceptsOrdinaryAddresses and testRejectsMalformedAddresses pin emailLooksValid (no leading @, a dot in the domain, no leading or trailing dot, no spaces). testCodeNormalisationKeepsOnlyDigits pins normalizedCode against "123 456", "Code: 123-456.", a ten-digit paste that must be cut to six, and letters. testAppleNonceIsRandomAndHashed pins the 32-character nonce, that two nonces differ, and that the SHA-256 hex is 64 characters and stable.
  • The route handler tests for account, devices and profile each begin with a case that a request with no user gets a 401 and touches nothing, which is the bearer channel's contract exercised from the other side. Chapter 11 lists them.

What is not tested: the middleware redirect, the smart sign-in's error-string matching, the callback route, and requireAdmin. All four depend on a live Auth server or on Next.js request plumbing, and none has a test today. The error-string matching in app/(auth)/actions.ts is the one most likely to break silently if Supabase rewords a message, and would be the first to cover.

Check yourself

Why can the anon key ship inside the iOS binary?

Because it grants nothing by itself. Every table has RLS enabled and every policy is written against auth.uid(), so a request with the anon key and no session sees no rows, and a request with a session sees only its owner's rows.

What does createRouteSupabase do when the header is Authorization: Bearer with nothing after it?

bearerTokenFrom returns null for an empty token, so the handler falls through to the cookie client. On a phone that means getUser finds no user and the route answers 401.

Why does the iOS app separate sign-in from sign-up when the web merges them?

The web's merged form tells a wrong password from a new address by matching Supabase's error strings after a sign-up attempt. On the phone the store's comment says a person who mistypes a password should be told that, not pushed toward a second account, so the screen picks the path and the store never guesses.

Which tables can a user read but never insert into, and who inserts?

transit_conditions, alerts and daily_readings. The scheduled jobs in lib/alerts/ write them with the service-role client; the user can only select, and update read_at on the last two.

Why does randomNonce reject bytes of 252 and above?

The alphabet has 64 characters and 256 is a multiple of 64, but the loop discards bytes at or above 252 so that a future change to the alphabet size cannot bias the modulo; the comment says every character must be equally likely.

Why does RootView.onOpenURL check the URL scheme before handing it to the auth store?

A widget tap opens the app with a sanchara:// URL. Passing that to session(from:) would fail and show "That link has expired" for something that was never a link.

How does someone become an admin?

Only by a row inserted into public.admins by hand in the SQL editor. The table has a select policy and no write policy, and no code path inserts into it.
